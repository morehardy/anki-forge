# 媒体检查的并行哈希优化

本次只改变成品检查中的 SHA-1 调度。媒体注册仍然同步读取全部内容，导出前仍检查源文件变化，成品仍经过独立读取、CRC、解码、累计资源限额和策略检查。

## 定位依据

在与 README 原三轮一致的冻结输入和原版 release 二进制上进行分段诊断。1000 条独立图片的注册哈希约 28.4 ms、打开文件约 19.1 ms、注册读取约 5.5 ms；成品媒体检查中的 SHA-1 约 28.4 ms，解码/读取约 3.4 ms。数字来自五次诊断样本的中位数，带计时探针，仅用于定位，不作为正式性能分数。

这解释了为什么缓冲区和文本微调没有解决主要问题：在该场景中，大头是完整媒体指纹计算。注册时必须得到指纹以维持同步重复内容检查，成品检查中的不同媒体可以独立计算。

## 实现和边界

- 至少 16 个媒体条目时，按可用 CPU 数启动最多 4 个 scoped 工作线程；无法创建更多线程时仍可以继续检查。
- ZIP 读取、CRC、zstd 解析、窗口限制及累计字节预算仍在调用线程执行。只有已完整解码的小媒体内容进入哈希队列。
- 单个待哈希内容最多 64 KiB，每个工作线程最多一个待完成任务，另有一个正在读取的内容，额外哈希缓存上限为 320 KiB。线程栈和分配器的实际 RSS 另行测量。
- 超过 64 KiB 的单个媒体转为原来的流式哈希；不把大型媒体全部放入内存。
- 工作线程在发出完成通知前释放数据，结果按原媒体顺序收集；包括读取失败在内，所有工作线程都在检查返回前结束。
- 默认分配器、压缩等级、产物格式、公开 API 及指纹算法均保持原样。

## 未采用的试验

独立试验分别比较了文件缓冲/定位复用、NFC 快速路径、小媒体压缩时给出准确内容大小。它们在本机 100/1000 档完整导出中的收益很小且不稳定，没有合入。也对照过另一个 SHA-1 实现，本机结果更慢，没有引入新依赖。探索性结果全部保留，未按最佳结果筛选。

## 验证

全工作区 1001 项 Rust 测试、42 项基准工具测试通过；Clippy、格式检查、默认 API 文档测试、文档生成、嵌入合约、crate 文件清单、发布元数据和依赖策略检查通过。

新增覆盖：30 个不同大小媒体的真实 ZIP/嵌套 zstd 检查（包含 64 KiB 边界及大文件）、两种累计资源限制、最后一个媒体截断时的失败及随后重试，以及短写不会扩张哈希缓存超过固定边界。

正式确认采用三轮固定矩阵，每轮 5 种场景 × 4 种数据量，每个实现/场景 10 次计时、5 次独立 RSS 测量，两个阶段各有 3 次预热。全部导出检查原始 SQLite、模板和媒体内容，每轮每格每个实现另做一次 Anki 导入与渲染验证。当前代码未提交：测量前冻结基础 commit、源码补丁、逐文件哈希、二进制及依赖身份，三轮之间保持不变。

三轮正式确认全部通过：2520 次导出、120 次 Anki 导入/内容/渲染检查。三轮源码和二进制身份相同，无任何单元触发预先约定的 5 个百分点波动标记。
