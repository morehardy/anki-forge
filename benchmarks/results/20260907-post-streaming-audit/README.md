# 流式优化后的剩余瓶颈复查

当前最明确的后续方向是**大媒体的临时落盘与读回，以及长文本的多份存活表示**。增大媒体暂存阈值能换来速度，但明显增加 RSS；SQLite 同步、日志、延后索引三个候选没有得到值得默认采用的综合收益。本次没有修改生产实现，也没有替换 README 的正式 genanki 对照。

## 当前热点

本轮基于已采用三项流式优化的版本重新测量，正式适配器 SHA-256 为 `369dcb358f4d34d4cf40bff8814c46c32ab684cd673c54b5357419af609b43f5`。以下为独立细粒度探针的阶段中位数；括号中的端到端数字也是探针版本，不能拿这些毫秒数与其他会话相减。

| 场景 | 当前热点 | 含义 |
| --- | --- | --- |
| 10,000 条文本（590.3 ms） | SQLite 182.0 ms；归一化/转换 101.5 ms；检查 53.8 ms | 约 31%、17%、9%，耗时分散在几个线性阶段 |
| 1,000 张普通图片（244.5 ms） | 同步注册 78.1 ms；并行媒体准备 51.2 ms | 注册约占 32%；不能把后续并行流水线的提升外推到整个注册阶段 |
| 64 个 1 MiB 文件（180.2 ms） | 媒体准备 75.7 ms，其中按序接收与写 ZIP 71.7 ms、等待结果 3.2 ms | 消费端已经比继续增加准备线程更值得调查 |
| 1,000 条长 Back（171.4 ms） | SQLite 54.1 ms；暂存 manifest 17.5 ms；检查 17.9 ms | 字段字节量会影响写库、序列化和检查，不能只按笔记条数预测 |

10,000 条文本的 SQLite 阶段包含填充 128.4 ms、整理 50.7 ms；字段存储转换约 10.9 ms，note 插入（含身份 JSON 参数）约 69.9 ms、card 插入约 18.1 ms，后两者包含参数绑定和索引维护。归一化中的 lowering 约 83.4 ms；其中产品 payload 构造约 15.0 ms，产品 lowering 总计约 51.4 ms，其余约 32 ms 是后续来源路径处理。它们存在包含关系，不应相加。

普通图片注册的 SHA-1 约 37.0 ms、打开文件约 26.6 ms、读取约 6.7 ms、stat 约 3.8 ms，图片尺寸识别仅约 0.3 ms。当前 API 要求 `add()` 返回前完成内容指纹，构建时再次检查源是否变化；跳过这些工作会改变已有行为。此前更换 SHA-1 实现、Unicode 快路径、读取缓冲等失败候选不作为本轮的新优化建议。

媒体的细粒度日志还区分了生产、消费、写入和哈希线程。工作线程计时是多个线程的累计墙钟时间，包含调度等待，不能直接当成单线程 CPU 时间；例如 1 MiB 场景的 ZIP 写入约 30.5 ms，哈希提交约 3.1 ms。256 KiB 场景中哈希发送等待约 15.6 ms，但它受到单条有序 SHA-1 流的吞吐约束，不能据此推断增大队列就能消除同等耗时。

## 大媒体暂存实验：收益伴随明显内存代价

只将单个编码 payload 的内存暂存上限从 512 KiB 改为 2 MiB，任务窗口和其余代码不变。计时为每组 2 次预热、7 次采样；RSS 随后独立进行 2 次预热、5 次采样。以下时间只取第一组，内存只取第二组，没有合并或选择较快的一组。

| 场景 | 当前 ms | 候选 ms | 耗时减少 | 配对更快 / 7 | 当前 RSS MiB | 候选 RSS MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 张普通图片 | 245.359 | 247.128 | -0.72% | 4 | 40.80 | 40.70 |
| 64 × 1 MiB | 184.252 | 155.060 | 15.84% | 7 | 26.00 | 53.86 |
| 128 个大小混杂文件 | 136.943 | 123.982 | 9.46% | 7 | 26.34 | 37.83 |

这支持“大媒体 spill 是剩余瓶颈”的判断，但不支持直接提高默认阈值。四线程下最多 9 个在途 payload，编码数据的理论上限将从 4.5 MiB 增为 18 MiB；Vec 容量、分配器、编解码器和线程另占内存，实测总 RSS 增幅也明显更大。**后续应先验证以总在途内存/实际缓冲容量约束暂存与任务窗口，能否减少落盘而控制 RSS。** 该策略本轮尚未实现，不预先承诺收益。

这些大 PNG 通过合法 ancillary 块加入确定性的不可压缩字节，像素内容不变；它们用于隔离字节量与调度，不代表所有真实高分辨率图片。

## SQLite 候选筛选

每个候选只改变一个因素，并保留所有样本。同步/日志实验为 5 场景 × 3 版本 ×（2 次预热 + 7 次采样）；延后索引为 3 场景 × 2 版本 ×（2 + 7）。下表是各自会话内的端到端中位数差；正数表示更快，RSS 是这两组诊断进程随计时收集的值。

| 候选 | 10,000 条文本 | 长 Back | 其他发现 | 结论 |
| --- | ---: | ---: | --- | --- |
| 仅临时库 `synchronous=OFF` | +0.31% | +1.20% | 万条 RSS +3.81 MiB | 收益不足以支持默认修改 |
| 仅临时库 `journal_mode=MEMORY` | -0.15% | -1.54% | 万条 RSS +4.77 MiB | 不采用 |
| 7 个非唯一索引延后创建 | +1.46% | -1.44% | 长 Back 7/7 更慢、RSS +6.00 MiB；严格等价检查失败 | 不采用 |

延后索引的 schema、全部学习内容表和其他 ZIP 条目一致，且通过 Anki 导入/内容/渲染检查；但 `sqlite_stat1` 少了原有 `('cards', 'idx_cards_odid', '0 0')` 行。全表等价检查因此失败，原始失败与逐表哈希保留在证据中，未通过排除统计表来宣称检查通过。其计时只用于筛选这个已拒绝的候选。

这些结果与此前“8 MiB SQLite 缓存、构建级身份复用没有综合收益”的结论一致：阶段耗时大不等于一个参数调整就能省掉它。若继续优化文本，应先研究数据转换和生命周期；SQLite 需要更深入的插入/存储方案验证，当前这三个候选不值得直接落地。

## 长字段内存：修正上轮推断

固定 1,000 条笔记与 Front，仅改变 Back 长度。以下比较前一实现与当前正式实现，每组 2 次预热、5 次采样，使用独立进程的原生峰值 RSS。

| Back 场景 | 前一实现 RSS MiB | 当前 RSS MiB | 差值 MiB |
| --- | ---: | ---: | ---: |
| 原始短文本 | 30.78 | 30.67 | -0.11 |
| 长 Back 的 1/4 | 38.47 | 38.20 | -0.27 |
| 长 Back（4,096 字符） | 60.70 | 61.56 | +0.86 |
| 长 Back 的 4 倍 | 155.30 | 155.69 | +0.39 |

上轮长 Back 的约 +6.7 MiB **未稳定复现**，不能当成新增流水线的固定成本。独立内存诊断使用 System 分配器包装计数和阶段边界 `ps` RSS；这些进程不参与性能结论。Rust 计数不包括 SQLite/zstd 的原生分配，当前 RSS 则包括整个被测进程。

长 Back 的 Rust 存活分配峰值约 28.4 MiB，Back 放大四倍后约 90.0 MiB；同期原始字段总量约 6.6 / 26.1 MiB。峰值已在 reconcile 阶段出现，内存诊断中关闭包 SHA-1 线程后这两个峰值不变。源码与边界数据共同指向 Deck、导入后的 Project、归一化内容同时存活：四倍 Back 场景在笔记构造结束约 30.8 MiB、payload 构造结束约 86.7 MiB、reconcile 后约 89.1 MiB。它们是 Rust 分配计数，不是可直接相减预测收益的 RSS。

下一步可调查内部借用与内容所有权转移、来源路径的重复分配和大字段的存活区间；需保留 Deck 可复用、可编辑 Project、诊断来源和内容校验语义。此前持有整个构建级身份映射的候选增加了内存，本轮没有重新采用它。

## 验证与复现

共 **681 次诊断导出、15 个输入场景、18 种唯一产物**。13 种产物与前轮已独立检查并导入 Anki 的封存包逐字节相同；新增的 2 种长字段包与 3 种索引候选包完成了新的原始 SQLite/内容检查及固定版本 Anki 导入/渲染检查。索引候选的全表等价失败单独记录。其余探针与候选均保持对应输入下的产物字节一致。

粗粒度和细粒度采样分别覆盖 13 / 9 场景，每组 2 次预热、5 次采样，均与当前正式二进制交错运行。机器为 Apple M1 Pro，Rust 1.92.0 release/default features/System allocator；每次导出前后检查同一原生 Battery Power 来源。计时包含启动、JSON 解析、普通逐项注册、构建、检查和退出。探针版与对照存在计时差异，阶段数字用于定位，不能替代正式基准。没有剔除异常值、跨会话拼接绝对毫秒、为 README 选用候选数字。

198 个正式 crate/adapter 文件的 SHA-256 与启动快照一致，正式适配器已恢复并匹配构建记录。本轮不涉及生产代码测试变更；前轮完整质量检查仍见[实现报告](../20260907-streaming-followup/implementation.md)。性能覆盖仍以 Basic、临时构建和这些合成媒体为界；未新增 Cloze、自定义多模型、保留中间产物或常驻并发的性能结论。
