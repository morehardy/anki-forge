当前版本剩余性能空间 · 2026-09-07

最值得继续投入的是：让媒体检查覆盖更大的文件、重叠 ZIP 指纹计算与写入、减少万级笔记中的重复转换及 SQLite 工作。大小混杂的媒体还有调度不均的问题。媒体注册虽然耗时高，但在保留同步注册与源变更检测的前提下，容易获得的收益已经较少。

本次是对上轮优化后的当前版本做诊断。生产源码、默认配置和正式基准二进制没有变化；README 继续使用[三轮完整基准](../20260907-inspection-parallel-hash/report.md)。下面的原型结果是下一轮选题依据，不能当作已发布的性能提升。

**优先级 1：扩大媒体检查并行的适用范围**

当前只有完整解码后不超过 64 KiB 的 payload 能交给哈希线程；更大的文件退回调用线程流式计算。README 图片恰好是 64,152 字节，处在可并行的一侧。[当前实现](../../../anki_forge/src/writer_core/inspect.rs#L995)

1,000 张图片从每张 65,536 增至 65,537 字节时，媒体检查阶段由 20.76 ms 增到 46.56 ms。细分探针在后一场景记录到约 29.03 ms 的串行媒体哈希。完整路径还存在编码分块等成本变化，不能将全部端到端差值都归给检查。

单变量原型只将内部上限临时改为 256 KiB，未改变媒体内容、检查项或输出格式。下面是同一轮未插桩对照的进程耗时中位数：

| 场景 | 当前版 | 256 KiB 上限原型 | 耗时减少 |
| --- | ---: | ---: | ---: |
| 65,537 B 图片 × 1,000 | 294.83 ms | 261.54 ms | 11.29% |
| 256 KiB 图片 × 256 | 216.49 ms | 178.90 ms | 17.37% |
| 1 MiB 图片 × 64 | 233.77 ms | 232.86 ms | 0.39% |
| README 图片 × 1,000 | 256.37 ms | 256.79 ms | −0.16% |

前两项各 7 个配对样本都更快。但这个改动只是把边界移到 256 KiB，并没有解决更大文件的串行回退；额外 payload 缓冲上限也从 320 KiB 增为 1.25 MiB，不能用本次 RSS 接近来否认这个内存代价。[原型差异](hash256k.patch) · [同轮数据](candidates/summary.json)

下一步可先比较 128/256 KiB 的有限内存策略，再研究大文件解码与哈希的有界流水线。单个文件的 SHA-1 必须按原序更新；不能把各块独立哈希后拼成同一个摘要。新设计必须保留解码/ZIP 累计限额、CRC、错误回收、输出顺序和线程退出语义。整个检查阶段的时间是可优化工作的上界，不能宣称都能消除。

**优先级 2：优化 ZIP 写入与整个包的指纹计算**

细分轮的 1,000 图片场景中，媒体预处理总计 53.96 ms，消费和写入约 51.08 ms，其中 ZIP SHA-1 29.65 ms、写入 16.81 ms；等待预处理结果仅 2.39 ms。四个预处理 worker 已经存在，单纯继续加 worker 难以解决这个串行部分。[分段原始摘要](detail/summary.json) · [ZIP 写入实现](../../../anki_forge/src/writer_core/stream_zip.rs#L168)

有验证价值的方案是让按序指纹计算与实际写入通过有界队列重叠，保留同一最终字节流、发布前的全部检查和落盘保证。这里约 30 ms 的 SHA-1 是潜在关键路径，并非可以直接节省 30 ms；哈希仍然要执行，能够隐藏多少取决于与 I/O 的重叠程度及队列开销。需要单独原型验证。

1 MiB 媒体还会超过 512 KiB 编码缓冲并落到临时文件。针对这个路径，本次试了只给已落盘 payload 增加 64 KiB 读取缓冲：64 张 1 MiB 图片仅减少 1.15%，大小混杂场景减少 1.11%，各样本有正有负，故未采用。不能仅凭临时文件调用次数推定优化成立。[原型差异](spool-buffer.patch)

**优先级 3：减少万级笔记的转换和数据库成本**

1 万条短文本的粗粒度结果中，lowering 为 72.00 ms，SQLite 填充 103.05 ms、压实 45.32 ms，另有笔记添加 48.08 ms、reconcile 42.21 ms。这里的候选应该针对整段工作，继续优化某个很短的字符串函数不容易改变整体结果。

- 构建内共享已解析的身份和来源映射。`to_product_v3_payload`、`apply_note_source_paths`、`resolved_note_identities` 分别统计稳定 ID 并解析笔记身份。可让 lowering 携带这次构建的解析结果，减少重复查表、字符串和来源映射重建，保留公开借用接口、可重复构建和精确诊断路径。[重复解析位置](../../../anki_forge/src/product/project.rs#L1195)
- SQLite 继续保持单 writer，比较临时数据库的缓存预算、先插入再建立适合延后的普通索引，以及压实所需的数据重写。当前已经有事务、预编译语句、每模型字段布局和 `VACUUM INTO`，不能再把这些列为待添加优化。细分轮中 10K 的 note insert（含身份 data 参数构造）约 49.77 ms、card insert 13.21 ms、压实 41.69 ms，说明原生数据库路径仍值得试验。[数据库生成](../../../anki_forge/src/writer_core/apkg.rs#L433) · [现有索引](../../../anki_forge/src/writer_core/compat_schema.rs#L35)
- 长字段单独评估分配与字节重写。1,000 条长 Back 在细分轮的 revision 约 7.76 ms，粗粒度轮 staging 14.13 ms、SQLite 45.11 ms；它和增加 note 数量不是同一种负载。下一轮应记录分配量和峰值存活，避免只数源码里的 `clone`。

这些仍是候选，没有本轮实现后的收益数字。数据库变更必须验证原始 schema、字段和卡片、身份/修订信息、确定性以及上游 Anki 导入；不能以取消压实、减少 metadata 或放宽校验换取耗时下降。

**优先级 4：大小混杂媒体的任务分配**

当前预处理按规范排序后每隔四个任务交给同一个 worker，再按原序收取结果。本次构造每四个文件中第一个为 1 MiB、其余为 64,152 B 的输入：四个 worker 的累计工作区间约为 60.97 / 5.53 / 5.09 / 5.26 ms，消费端等待 22.11 ms，整个导出约 137.58 ms。[当前调度](../../../anki_forge/src/prepared_media.rs#L152)

这证明固定跨步分配可能受文件大小排列影响，不证明一般混合负载都会这么失衡。可以测试有界调度窗口内的任务领取或按预计字节量分配，最终仍按原序提交 ZIP 和诊断。全局无界抢任务会扩大等待重排的数据量，不能用它替代现有内存约束。规则化 README 图片负载等待很少，因此这个方向主要服务真实大小混杂的数据。

**暂时不优先的方向**

媒体注册在细分图片场景中，SHA-1 约 28.39 ms、open 19.43 ms、read 5.44 ms、文件检查 2.65 ms。即刻校验、同名内容冲突和之后的源变更检测都依赖注册时取得的真实指纹；已采用硬件支持的 SHA-1、64 KiB 读取和同句柄图片头解析。在不改变同步注册 API 的约束下，这一段较难再取得大幅收益，不能简单删掉或延后哈希。

默认运行时加载现在约 2.5 ms，旧报告中的约 31 ms 冷启动成本已经不是现状。摘要检查精简、所有权转移、预编译 SQL、流式 staging、并行媒体预处理也都已经实现。上一轮的归一化字符串快路径、归档索引缓冲、媒体编码小帧原型，以及本次的已落盘媒体读取缓冲，都没有获得足以采用的整体改善。

编译配置和分配器仍可作为独立实验，但本次没有新证据支持把它们排在上述热点之前，也不应给公共库强加宿主的构建策略。

建议下一轮先解决媒体检查的大小边界，再分别验证 ZIP 重叠流水线和万级笔记的重复解析/SQLite 路径。正式验收继续覆盖原有 20 格，同时增加 64 KiB 边界、大文件和大小混杂输入；Cloze、多模板、多自定义模型、常驻重复构建与多任务并发还没有被本次 Basic 诊断覆盖，需要补充独立负载。
