# Anki Forge 文档优化方案

核对日期：2026-09-22。范围：官网文档、根目录 README、Rust / Node / Python 使用文档，以及相关公开接口、示例和检查脚本。

本方案的审计部分记录了当时的工作区快照。随后 Python 原生 SDK 迁移及其配套说明已由对应任务完成；本次文档实施基于更新后的接口继续处理官网与使用路径。下文历史问题不代表当前状态，处理结果见文末“实施记录”。

## 1. 目标与现状

文档已有真实基础，但还没有形成完整、连贯的使用路径。首要工作是修正事实和安装指引，再按读者要完成的任务组织内容。

值得保留的基础：

- 官网目前有 6 个文档页面，其中 Rust 指南、模板指南、API 页面从仓库文件生成，已有统一来源机制。
- 快速开始引用实际 Rust 示例；官网的 Basic、Cloze、媒体和更新演示有对应的生成程序与产物检查。
- 已有站内链接、锚点、构建和下载检查；仓库也有 Rust doctest，Node 安装测试覆盖完整 README JavaScript 示例。

优化后的阅读路径应是：

**选择语言与适用版本 → 安装并生成第一副牌组 → 接入自己的工程 → 完成常见任务 → 查参数与错误 → 更新和分发牌组。**

## 2. 推广前优先修正的事实问题

这里的 P0 表示会误导安装、调用或能力判断，应在对外推广前处理。

### P0-1：Python 安装说明与当前源码入口不一致

**现状：** [Python README](../../bindings/python/README.md) 仍要求构建 `contract_tools`，通过 `PYTHONPATH` 运行，并介绍 CLI 运行时打包。官网的 [语言选择页](../../website/src/content/docs/docs/languages.mdx) 沿用了这一说法。

**源码证据：** [公共包入口](../../bindings/python/src/anki_forge/__init__.py) 已导出原生 `Project` 和 `MediaRegistry`；[构建配置](../../bindings/python/pyproject.toml) 已使用 Maturin 和 `anki_forge._native`。

**读者影响：** 只按旧说明构建 CLI，不能满足当前包对原生扩展的依赖。用户无法判断自己该使用旧版本还是迁移中的源码。

**处理：** 明确文档对应的版本或源码状态；当前源码使用经过验证的原生扩展安装流程。旧 CLI 指引归入有版本标记的迁移说明。Python 迁移尚未完成时，直接说明当前可验证的使用范围，不提前承诺完整支持。

### P0-2：Python 部分示例和行为说明已经偏离当前接口

| 文档中的用法 | 本次源码核对结果 | 应如何处理 |
| --- | --- | --- |
| `project.media.add_bytes(...)` | 当前原生 `MediaRegistry` 只有 `add_file(...)` | 随接口迁移更新；在可用前不作为当前快速开始示例 |
| `write_apkg(..., identity_lockfile=..., update_safety=...)` | 当前原生 `write_apkg` 只接收输出路径 | 为旧版用法标明版本；当前教程必须等待对应接口通过验证 |
| 修改 `project.default_deck` 后再次导出 | 当前实现是没有 setter 的只读属性 | 按实际支持的配置方式重写 |
| `add_file` 不检查文件是否存在或可读 | 当前原生路径在注册时调用 Rust 媒体注册 | 对照实际诊断时机修正迁移说明 |

来源：[Python 快速开始](../python/quick-start.md)、[诊断指南](../python/diagnostics.md)、[genanki 迁移指南](../python/genanki-migration.md)；实现：[Project](../../bindings/python/src/anki_forge/project.py)、[MediaRegistry](../../bindings/python/src/anki_forge/media.py)、[原生桥接](../../bindings/python/native/src/lib.rs)。

此外，快速开始中的 `b"png-bytes"` 是占位数据，不是真实图片；示例还依赖未提供的音频文件。完整教程应提供可用素材或生成素材的步骤，并补齐需要的字段和导出步骤。片段应明确说明依赖哪个前置示例。

### P0-3：自定义 Cloze 的字段限制描述错误

**现状：** [模板指南](../template-bundles.md) 写着“一个字段和一个模板”。

**证据：** [已有模板示例](../../contracts/fixtures/template-bundle/custom-cloze/anki-template.yaml) 和 [对应测试](../../anki_forge/tests/custom_template_entry_parity_tests.rs) 同时使用 `text` 与 `extra` 两个字段。

**修正方向：** 一个指定的 Cloze 字段和一个卡片模板，可以包含额外字段；用完整的 `Text + Extra` 示例解释。先修正仓库源文件，再由网站生成流程同步。

### P0-4：源码版本、实现状态、验证范围与发布状态需要分开

**已确认的差异：** 根目录 [英文 README](../../README.md) 和 [中文 README](../../README.zh-CN.md) 写 Python `0.1.0`，当前 [包元数据](../../bindings/python/pyproject.toml) 声明 `0.2.0`。

**已有良好做法：** [Node README](../../bindings/node/README.md) 明确区分了本机验证、候选版本、待完成的平台验证和 npm 发布。这种区分应在各入口保持一致。

**处理：** 为每个 SDK 分别列出源码声明版本、可验证的安装方式、已验证平台、已知限制和发布状态。不能由版本号推断已经上架，也不能用 Rust 功能推断绑定已经具备同等能力。

## 3. 阅读体验与覆盖问题

P1 是完成使用路径所必需的工作；P2 是后续扩展。

| 优先级 | 当前问题 | 对阅读的影响 | 优化方式 |
| --- | --- | --- | --- |
| P1 | 官网快速开始只教运行仓库示例 | 能看到结果，但不知道如何放进自己的工程 | 补“接入现有工程”，复用根 README 已有的本地依赖方式，并提供完整程序 |
| P1 | 缺少集中的核心概念说明 | 容易混淆 Note / Card、Deck / Project、字段 key / 显示名称 | 用短概念页和一个贯穿示例说明对象关系与选择依据 |
| P1 | Rust 指南将常用流程和大量路径别名、原子写入细节放在一起 | 新手很快进入与当前任务无关的长段落 | 教程保留操作步骤；详细保证移到参考页，从相关步骤链接过去 |
| P1 | 模板指南混有 fixture 校验、资源打包和维护命令 | 使用者难以判断哪些步骤必须执行 | 拆分“使用模板包”与“维护模板契约”，后者进入贡献者文档 |
| P1 | “Supported Rust API” 实际是 crate README 概述 | 找不到具体方法的参数、返回值、默认值和错误 | 先改名为“Public API overview”；逐步补公开 API 参考 |
| P1 | 媒体、自定义卡片和更新内容分散；Image Occlusion 缺少站内任务指南 | 用户需要在源码、README、博客间跳转 | 按任务建立入口，优先复用实际示例；Image Occlusion 明示可用模式及限制 |
| P1 | 模板指南中的完整示例、语义说明以纯路径出现 | 用户需要手动搜索仓库 | 改为可点击链接，并提供完整目录或可运行示例 |
| P1 | 检查范围尚未覆盖所有面向用户的教程代码 | 网站构建通过，仍可能存在不能执行的教程 | 标记完整示例和片段，前者执行验证，后者从已验证源码提取 |
| P2 | Node / Python 主要通过外链进入仓库文档 | 官网体验中断，语言能力不容易比较 | 先提供站内准确状态和安装入口，再逐步纳入各自指南 |
| P2 | 首篇博客与快速开始内容高度重合 | 同一安装流程出现多个维护点 | 文档负责当前操作步骤；博客补应用场景和设计解释，共享示例并链接到指南 |

上述内容并非全部“缺失”：不少已经存在于仓库 README、示例和长指南中。优先整理、拆分和建立入口，减少重复撰写。

## 4. 建议的文档目录

沿用现有 Astro / Starlight 和英文官网。以下是目标结构，可分阶段补齐，不要求一次创建所有页面。

```text
Start here
  Introduction                         项目用途、适用场景、从哪里开始
  Choose your language                 语言、版本、安装方式与状态
  Your first deck                      按所选语言完成第一副牌组
  Add to your application              接入自己的工程

Core concepts
  Notes, cards, and note types          字段、模板与卡片生成
  Deck and Project                     两种入口的选择
  Stable IDs and update baselines       身份、内容修订与基线

Guides
  Basic and Cloze cards
  Images and audio
  Custom note types and template bundles
  Image Occlusion
  Update and distribute a deck

Reference
  Rust API
  Node / TypeScript API
  Python API
  Compatibility and release status

Troubleshooting
  Installation and build errors
  Media, templates, and update diagnostics

Contributing                           链接到仓库开发文档
```

组织原则：

- **先按任务找内容，再选语言。** 概念说明共用；安装、异步行为、类型和错误处理按语言写，避免机械翻译 Rust 示例。
- **能力差异直接说明。** 暂未验证的语言分支显示状态和可用替代路径，不展示无法运行的标签页。
- **高级信息放到使用场景附近。** 在更新指南说明基线要求，再链接到完整写入保证；在媒体指南说明文件规则，再链接到错误参考。
- **保留已有链接。** 拆页时保留旧路由与重要锚点，提供新位置入口，避免 README 和博客链接失效。
- **贡献者资料有独立入口。** ADR、实施计划、契约打包和发布操作继续留在开发文档体系。

## 5. 每一页如何写得友好

### 任务指南采用统一结构

1. **目标与结果：** 一句话说明完成后会得到什么，例如“生成包含图片和发音的词汇牌组”。
2. **前提：** 需要的语言版本、安装状态、素材，以及命令的运行目录。
3. **可运行示例：** 给出完整文件或明确的前置示例链接；标明文件名和执行命令。
4. **验证结果：** 输出文件的位置、预期笔记和卡片数量，以及在 Anki 中应该看到什么。
5. **关键解释与常见错误：** 解释本页新增概念，给出最相关的两三个失败场景。
6. **下一步：** 一个自然延伸的任务，加一个相关 API 参考入口。

完整示例与片段的区别必须明显。需要用户提供图片、音频或上一版 APKG 时，在代码之前说明；不能将占位字节包装成可直接执行的示例。

### 信息呈现保持简单

- 每段集中说明一件事，标题描述具体任务；首次出现术语时解释，后续保持同一名称。
- 用表格比较选项、字段或语言能力；连续操作使用有序步骤。
- 提示框只用于必要的版本差异、操作限制或故障提示，避免把正文切碎。
- 折叠区承载进阶解释；安装步骤、关键限制和输出位置保持可见。
- 保留目录、搜索和代码复制。文档页优先保证可读性，无需增加装饰动效。

### API 参考与教程各有职责

API 参考至少说明：用途、签名、参数、默认值、返回值、错误、一个最小示例和相关任务链接。只覆盖承诺支持的公开接口。

Rust 优先复用源码注释与 rustdoc；Node 对照公开类型声明；Python 对照当前公共导出、类型声明和验证结果。尚未发布时提供与源码匹配的参考入口，不预设 docs.rs 或包仓库已存在对应版本。

## 6. 内容来源与持续维护

保留现有“源文件 → 网站生成”的方式，每个主题指定一个主要来源。

| 内容 | 建议的主要来源 | 官网如何使用 |
| --- | --- | --- |
| 项目介绍与首次体验 | 根 README 保持简短 | 引导到指南，共享示例来源 |
| 用户指南 | `docs/` 下按任务组织的 Markdown | 通过现有导入机制生成页面 |
| 网站导航与导读 | `website/src/content/docs/` | 仅维护网站所需的引导内容 |
| 公开 API | 源码注释、公开类型声明及必要的说明文档 | 生成参考或链接到对应版本 |
| 代码示例 | 各 SDK 的实际示例文件 | 提取代码区域，避免手工复制 |
| 实现和发布状态 | 包元数据加人工维护的验证记录 | 汇总版本与状态，不由版本号自动推断已发布 |
| 博客 | `website/src/content/blog/` | 解释场景、方法和设计，引用当前指南 |
| ADR、计划与发布操作 | 现有开发文档 | 从 Contributing 入口访问 |

具体维护要求：

- 生成的 `rust-guide.md`、`templates.md`、`api.md` 不直接编辑；修改源文件和导入配置。
- SDK 改动同时检查安装、快速开始、迁移说明和能力状态；扩展网站数据来源时同步调整工作流的触发路径。
- 关键版本从对应包配置读取；“已验证”“已发布”等状态必须有单独证据。
- 当前阶段先明确“源码文档”适用范围。支持多个实际发布版本后，再按需要引入版本切换。
- 沿用英文官网和中英文 README；先把现有语言内容校准，再扩展完整站点翻译。

## 7. 分阶段实施与验收

| 阶段 | 具体交付 | 完成标准 |
| --- | --- | --- |
| 第一阶段：纠正事实 | 修复 Cloze 字段说明；校准 Python 安装、API 和版本；统一各语言状态；调整 API 页面名称 | 文档不再把旧接口、未完成接口或候选包描述成当前可用的正式能力 |
| 第二阶段：贯通阅读路径 | 补接入自己工程、核心概念、媒体与排错入口；拆分模板维护内容；整理更新教程；建立完整示例检查 | 新读者仅按指南即可完成导出、添加媒体、查看诊断和一次有基线的更新，无需阅读内部源码 |
| 第三阶段：完善查询与多语言 | 补公开 API 参考、Node / Python 站内指南、Image Occlusion 和迁移专题；减少博客重复维护 | 各语言能力与实际版本一致，常见任务有可执行示例，API 参数与限制可以直接查到 |

Python 状态纠正可以立即做；完整原生教程以迁移任务实际验证的接口为准。这样不会因为 SDK 尚在实施，就继续保留误导性的当前使用说明。

### 验证范围

- **安装路径：** 每种被推荐的安装方式在独立目录或干净环境完成一次安装和最小导出。
- **示例：** 完整教程执行真实程序，检查输出、笔记/卡片/媒体数量；片段从这些程序提取。
- **更新：** 生成前后两个版本，检查稳定身份和比较报告；锁文件教程同时验证读写步骤。
- **网站：** 延续链接、锚点、搜索和子路径检查；新增页面与旧入口一起检查。
- **Anki 行为：** 对声明已经验证的导入、渲染、音频和更新行为，记录实际版本及验证范围；APKG 生成检查不能替代客户端行为验证。

现有 Rust doctest、Node README 示例检查和官网产物验证应继续复用。本次是文件与源码核对，没有重新执行所有 SDK 示例或 Anki 客户端测试；网站质量评分也不能证明文档内容准确、完整。
