# Anki Forge GEO 优化实施方案

日期：2026-10-25。以当前 `a2afe14`、[10 月 20 日 GEO 审计](2026-10-20-website-geo-audit.md)和[SEO 复核](2026-10-20-website-seo-audit.md)为基础，结合本轮 grilling 追问及内容、工程、测量三个子代理的交叉评审。本文是实施方案，尚未实施网站或发布变更。

**首轮应交付一条中英文都可用、三种语言都能跑通的完整采用路径：理解产品 → 判断是否适合 → 安装公开包 → 从真实数据生成 APKG → 审阅并发布更新。** AI 推荐实验和真实采用证据分别记录；首轮承诺内容与程序正确、能发布、能衡量，不承诺推荐量增长。

## 1. 已确认的决策与范围

用户已经确认以下七项：

| 决策 | 已确认选择 | 对方案的约束 |
| --- | --- | --- |
| 受众 | Rust、Python、Node.js/TypeScript 开发者同等优先 | 每种语言都有完整程序、安装说明和公开包验证，不把其中一种留到以后 |
| 目标 | 准确推荐和实际采用优先 | 访问量、star、下载量为辅助信号；不把提及、引用、复制命令当采用 |
| 投入 | 一个维护者约 2–3 周 | 按三周上限安排；主动延期外围内容和复杂自动化 |
| 内容语言 | 首轮核心页面中英文同步 | 双语内容、语言切换、对应 URL 和事实边界均需验收 |
| 性能资料 | 长期移出，官网保留最小数据 | 解除网站对大体积实验目录的依赖，保留固定历史证据 |
| 页面简洁 | 只保留有助于理解、选择和操作的信息 | 不展示未就绪功能的占位提示；提交哈希、校验值等留在来源记录和复现资料中 |
| 中文表达 | 地道、符合中文语境 | 按中文阅读习惯改写，统一术语；正文、导航、按钮和提示均需通读验收 |

决策树已经收敛为：

```text
准确推荐与真实采用
├── 三 SDK 等优先
│   └── 同一业务任务、同一输入、三个完整程序、同一结果契约
├── 核心内容中英同步
│   └── 建议 7 对核心页；已翻译页面互链，其余明确链接英文参考
├── 2–3 周
│   └── 首轮只做一个完整任务和一个选型比较，不扩第二主题
└── 性能资料长期移出
    └── 小型展示快照留在仓库，实验报告引用固定历史提交
```

建议首轮范围是 **7 对核心页面，共 14 页**。其中 5 个英文页面已经存在，只需改进；新增 2 个英文页面和 7 个中文页面。现有参考页面继续保留，不要求首轮翻译所有文档。

## 2. 子代理质疑后修正的方案

| 被质疑的建议 | 主要反对理由 | 本轮采用的处理 |
| --- | --- | --- |
| 立即补多个场景教程 | 三语言加双语会迅速增加维护成本，且示例可能只验证仓库源码 | 集中完成一个共享 JSON/媒体/更新任务，三语言都验证公开包 |
| 用稳定 ID 作为对 genanki 的主要优势 | genanki 本身支持自定义 GUID、媒体和重导入更新 | 比较可审阅发布流程、诊断与策略、运行条件和迁移成本 |
| 先做独立 benchmark 长文 | 现有测试只证明历史 Rust 工作负载；不能替代 Python/Node 采用验证 | 首轮比较页引用历史证据；新实验和独立性能页延期 |
| 安装新的统计系统 | 当前已经接入 Cloudflare Web Analytics，但没有自定义事件能力 | 验证已有统计；用独立任务验证和自愿反馈补足采用证据 |
| 尽快加全站 schema、lastmod、llms | 没有足够证据说明是当前瓶颈，且会新增维护管线 | 先保证事实、教程和索引；只做与本轮内容直接相关的小改动 |
| 三种语言各写一套中英长文 | 相同输入、限制和安装事实容易分叉 | 共享 fixture、程序和版本来源；中英文只分别维护说明文案 |

这些取舍保留了用户要求的三 SDK 和双语覆盖，减少的是第二场景、全量翻译、性能新实验和复杂监控。

## 4. 工作包 A：保留最小性能数据并恢复可发布基线

**交付。** 网站仅保留现有选定 CSV（约 8.4 KB）、来源信息和简短维护说明。建议放入 `docs/performance/20261008/`；记录原始仓库、完整提交、原路径、SHA-256、测量日期及适用范围。图表继续由同一份 CSV 生成，不手抄数值，不重新运行 benchmark。

**展示边界。** 上述提交哈希、校验值和路径用于仓库内的来源记录与复现，不直接展示在首页、性能卡片或核心教程中。性能区只呈现结论、必要的比较条件、单位，以及需要时的“测试方法”链接；链接可指向固定历史报告，链接文字不显示哈希。沿用已有报告，不为这些细节新增独立说明页。

关键设计：把本地读取位置 `dataFile` 与历史证据路径 `dataset` 或 `evidencePath` 分开。当前 [PerformanceEvidence](../../website/src/components/PerformanceEvidence.astro) 用 `evidenceCommit + dataset` 生成公开链接，直接改 `dataset` 为新本地路径会破坏历史证据地址。

## 5. 工作包 B：修正产品事实与页面角色

统一产品定义：开源 Anki APKG 生成库，Rust 核心，Rust/Python/Node.js 接口，支持媒体、模板和可审阅的更新流程。明确包名 `ankiforge`、正式域名、仓库和 MIT。三种语言的选择入口同等清楚。

| 页面或入口 | 具体工作 | 验收 |
| --- | --- | --- |
| 首页、README、GitHub About、包简介 | 使用同一组产品事实，解释用户能完成的任务；避免只称 Rust toolkit 或含糊的 Product API | 名称、类别、三语言、官网和能力边界一致 |
| 三个 quickstart | 标题明确 Anki/APKG 与开发语言；完整安装、程序、运行命令、输出及条件 | 从空目录按文档可运行；保留现有 URL |
| `/docs/api/` | 新增 `docs/api-overview.md` 作为真正三语言 API 导航，替换当前 crate README 的页面映射 | 用户能找到 API、媒体、诊断和更新，不再读到另一份安装示例 |
| `/docs/installation/` | 聚焦 Rust 项目集成、环境和依赖，链接唯一的快速入门流程 | 页面职责与 quickstart 清楚区分，保留 URL |
| Rust 入门博客 | 修复 `hola`/`es:hola` 差异和旧 source-checkout 指引 | 解释与实际代码、目标页面一致 |
| Python 页面描述及语言页 | 修复 description 承诺媒体示例但正文只有 Basic 的错位；核对已验证 Python 版本 | 最低要求、发布范围和验证范围不混淆 |
| 更新与迁移文案 | 核对残留 from source、旧版本导航等表述 | 已发布能力不被误写为源码专属；迁移边界保留 |

主要编辑入口是 [content-links.mjs](../../website/scripts/content-links.mjs)、原始 `docs/`、首页和博客 MDX。生成目录不手改。版本和安装命令继续使用 [ai-quickstart.json](../ai-quickstart.json)，不另建一套相互独立的发布版本表。

包元数据源修改应进入下次正常发版；注册表回读确认之后，才能把 npm/PyPI 的展示更新记为完成。准备好源文件不等于已改变线上包页面。

**页面信息与文案规则。** 每段新增文字都应帮助读者理解产品、判断是否适合或完成当前操作；三者都不满足就删除。此规则适用于所有核心页面，不为了 GEO 增加重复介绍、关键词堆叠或说明横幅。

- 未发布或未准备好的功能不放入口、占位卡片或禁用按钮，也不加“尚未准备好”“即将支持”等解释。
- 首页保留产品用途、主要能力、三语言入口和必要证据；完整技术解释放在对应教程或参考文档。
- 环境要求贴近安装步骤，更新条件贴近更新步骤，性能适用范围贴近比较结果；各说明一次，不在多个区块反复提醒。
- 提交哈希、校验值、内部路径、验证过程和发布流程不成为产品文案。需要核查时，通过简短的来源链接进入已有资料。
- 按钮和链接使用具体动作或目标名称，如“查看示例”“测试方法”；上下文已足够时，不再配一段解释如何点击的文字。

性能比较仍保留判断结论所必需的范围，例如“Rust 导出耗时”，避免精简后被误读为三种语言的统一性能保证。具体限制放在影响选择或操作的位置，用简短、直接的表述说明。

## 6. 工作包 C：一个三语言完整任务

建议主题：**Generate and update Anki decks from JSON**，中文为“用 JSON 数据生成并更新 Anki 牌组”。共同输入、共同限制和验证说明写一次，每种语言都有独立完整程序。

**输入与结果契约。**

- v1 JSON 含三条 Basic 笔记，每条有不可随文本变化的业务 `id`；共享一张图片、一段音频。
- v2 保持 namespace 和三个业务 ID，只修改一条答案，不增删笔记或媒体。
- 三个实现分别写到自己的输出目录，保留原始 v1 APKG，再比较和生成 v2。
- 目标预期为 3 notes、3 cards、2 media；这是实现与执行时必须验证的契约，不能在尚未运行时宣称已经通过。
- JSON 由调用方解析：Python 使用标准库，Node 使用 `JSON.parse`，Rust 明确列出 `serde`/`serde_json`。不宣传 SDK 已内置通用 JSON/CSV 转换器。

**页面提纲。** 直接说明适用任务与输出；在安装处列必要版本和环境；下载数据和素材；三语言分别给文件树、安装、完整程序、运行和检查；简要解释比较结果，在再次导入步骤说明必要条件；链接 API、媒体与更新参考。共同条件只写一次，详细原理和复现过程留在参考资料中。

三语言内容必须存在于静态 HTML，且可直接通过 `#rust`、`#python`、`#node` 进入。若用 tabs，切换不能成为读取程序的前提；Node/TypeScript 部分必须说明实际运行于 Node，提供完整 TypeScript 编译运行路径，而非仅声称有类型声明。

**源码组织建议。** 共同 JSON/媒体素材放在一个小型 recipe fixture 目录；程序分别放入现有 Rust、Node、Python examples 目录。中英文 Markdown 使用已有 source marker 引用同一份程序，新增页面加入 `content-links.mjs` 和网站导航。

**公开包验收。** 在仓库外临时应用中，三种语言分别安装 `ai-quickstart.json` 所指向的公开版本；不使用 path/git、editable、`maturin develop` 或本地 native 产物替代公开安装。核验实际解析版本和来源，Rust 测试应用使用精确版本约束或检查 Cargo.lock，避免范围约束悄悄选择更高版本。Python 使用公开 wheel（例如 `--only-binary=:all:`）；缺少对应 wheel 时记录平台发布问题，不以 sdist 本地编译静默兜底。首轮选择已支持的 Linux x64 环境完成三套验证，不把网站教程检查扩大成完整发版平台矩阵。

每套 runner 检查：安装与运行成功、持久 APKG 存在、实际内容及 note/card/media 计数、v1/v2 身份对应、答案变化、比较结果和发布策略；v1 原包没有被覆盖。要求语义一致，不要求三种语言输出的压缩包逐字节一致。CI 成功不能代替客户端行为验证，另记录指定 Anki 版本/设置下的导入检查；不把它外推为所有客户端和复习状态都被保证。

当前网站 Python CI 使用源码构建，因此需要增加小型公开消费者检查；继续保留已有源码示例检查，两者验证的对象不同。中英共用相同可执行块时无需重复运行完全相同程序；译文若改了命令、参数或代码，则须作为不同执行对象验证。

## 7. 工作包 D：一页真正能帮助选择的比较

建议新入口 `/docs/anki-forge-vs-genanki/`，与现有 migration 页互链。比较页回答是否值得选择；迁移页回答决定之后如何操作。

| 更适合考虑 Anki Forge | 更适合继续已验证的 genanki 流程 |
| --- | --- |
| 新建或重设计内容发布流程，有持久业务 ID | 现有 Python 脚本、模板与媒体流程稳定，新增能力需求不明显 |
| 需要机器可读诊断、compare、风险策略和发布前审阅 | 主要是简单生成，迁移成本大于工作流收益 |
| 需要跨语言创作模型、owned media 或程序化 Image Occlusion | 必须延续已有 GUID/数字 ID，但没有经验证的身份迁移映射 |
| 可接受原生包平台要求及保留原始发布 APKG | 当前部署环境不在 Anki Forge 验证范围，而已有流程能满足要求 |

以上是条件式选择依据，需要在发布前逐条核对对应公开 API。Basic、Cloze、媒体、离线生成等共同能力如实列为共有。genanki 支持自定义 GUID、媒体和重导入更新，不能用“它没有稳定身份”制造优势。[genanki 官方 README](https://github.com/kerrickstaley/genanki#note-guids)

结构：首段条件式结论 → 功能/环境/维护成本表 → 同一个小任务的流程对照 → 身份迁移边界 → 历史性能证据及局限 → 核对日期和来源 → 新任务指南/迁移指南。

禁止将历史 Rust benchmark 写成当前 Python/Node 同比例提速；不承诺任意旧 genanki 牌组无损迁移或自动保留全部复习记录。中英文都必须保留这些条件。

- 避免英文语序、长串名词和“赋能”“无缝体验”等空泛表述。正文、页面描述、按钮、图片说明及必要提示都要一起校对。
- 中文验收先脱离英文原文，按首次访问者的顺序通读，检查是否自然、简洁、能直接照做；再对照英文核实能力、安装和更新条件，防止改写扩大承诺。浏览器中检查换行、按钮长度和移动端布局。

**局部国际化需要先验证路由行为。** 当前 Starlight 0.42.2 在启用多个 locale 后会为缺失译文生成 fallback 页面。只新增少数中文内容，不能直接推断只产生这几个中文 URL。首个技术切片限半天，验证现有英文 URL、显式中文页面、语言属性、sitemap 和语言切换。[Starlight 官方国际化说明](https://starlight.astro.build/guides/i18n/)

实施边界定为：保留现有英文 Starlight 路由，不开启全站 locale fallback；一个 7 项配对清单驱动中文首页和 6 个显式中文文档路由。优先评估官方 [StarlightPage](https://starlight.astro.build/guides/pages/) 和 [route middleware](https://starlight.astro.build/guides/route-data/) 的组合。本地版本仅传内容 `lang` 属性不足以保证 HTML 根语言正确，须检查实际产物。middleware 不能用来取消已经生成的静态路由。

如果这个小样本需要内部 API 或大范围组件覆盖，半天内收敛到现有 `SiteLayout` 加一个 `CoreGuide` 薄包装，显式渲染六篇中文 Markdown，继续使用现有 Astro、Markdown、Pagefind 和样式。中文内容使用不参与 Starlight 自动 docs 路由的集合，避免先生成英文镜像再批量加 noindex。

具体接入点：`SiteLayout.astro` 增加 locale 与页面配对信息；Header/Footer 使用真实存在的对应链接；`content-links.mjs`、`prepare-site.mjs` 处理有限的中文来源；`content.config.ts` 注册显式中文内容；新增 `website/src/pages/zh-cn/index.astro` 和一个仅生成六个文档路径的路由；`check-site.mjs` 检查实际页面集合与元数据。核心翻译不会要求迁移原有英文文档目录。

双语发布门槛：

1. 14 页有真实正文，title、H1、description、导航与主要交互文案符合页面语言。
2. 每页 canonical 指向自身；`hreflang` 为真实对应页面建立双向、自引用映射，不指向未翻译 fallback。
3. 语言切换进入同一主题；原英文 URL 和已有关键锚点可用。
4. 中文前缀仅发布 7 个已翻译核心页面；未翻译的中文文档路径返回 404，不因默认 fallback 额外暴露英文正文镜像。
5. 两种语言安装命令、代码、适用版本、媒体素材和更新限制一致；比较页做独立语义复核。
6. 两个布局继续各只有一个统计 beacon；不能因包装布局重复注入。
7. 核心页面没有未就绪功能占位、提交哈希或重复说明；必要条件位于相应操作或比较处。
8. 中文完成独立通读和语义核对，术语、导航与按钮自然一致，没有翻译腔或因文案过长造成的布局问题。

首页只做产品定义、导航、必要文案国际化和内容精简，中文按阅读习惯改写，不做视觉重设计。现有 AI prompt 已有中英文数据，可复用，但中文仍按上述标准通读；不因为文本占比就假定它产生搜索惩罚。

## 9. 工作包 F：推荐与采用分别衡量

### 9.1 已有流量统计

Cloudflare Web Analytics 可观察 Path、Referer、Visits/PV；不支持自定义事件，也不记录 query strings/UTM。Visits 也不等同独立用户。因此本轮不声称能用现有 beacon 测安装复制、下载点击、出站点击、用户漏斗或本地 APKG 生成。[官方 FAQ](https://developers.cloudflare.com/web-analytics/faq/)、[维度](https://developers.cloudflare.com/web-analytics/data-metrics/dimensions/)、[指标定义](https://developers.cloudflare.com/web-analytics/data-metrics/high-level-metrics/)

验证首页与一个文档页的真实上报和后台记录，然后固定过滤条件每周记一次页面/来源快照。“已识别 AI 来源访问”只是可识别的部分，其他访问保持未知，不全部归为 AI。Search Console/Bing 账号若已可用，记录核心 URL 的索引、canonical 选择和 AI 展示/引用；账号等待不阻止内容准备。

### 9.2 固定的中英文推荐样本

首轮建议使用两个已有访问条件、支持联网检索的平台；在基线前固定平台、模式、设置和自然语言。若只有一个可用平台，记录这个限制，不将另一个模拟出来；采样计划相应缩为每窗口 16 次、基线加后测共 32 次。

三 SDK 各两个相同意图，共 6 个非品牌问题；各有中英文版本：

| SDK | 新建意图 | 更新意图 |
| --- | --- | --- |
| Python | 用 Python 从 JSON 数据生成带图片的 Anki APKG，推荐哪些库？请说明限制。 | 我需要用 Python 持续生成和更新 Anki 牌组，避免重复卡片，应该如何选库？ |
| Node/TypeScript | 同上，将语言替换为 Node.js/TypeScript | 同上，将语言替换为 Node.js/TypeScript |
| Rust | 同上，将语言替换为 Rust | 同上，将语言替换为 Rust |

英文模板：`Which libraries would you recommend for generating Anki APKG decks with images from JSON in <language>? Explain their limitations.` 以及 `How should I choose a <language> library for repeatedly generating and updating Anki decks while avoiding duplicates?`。

另外两道品牌诊断题：`Anki Forge 是什么？支持哪些编程语言？`、`请给出 Anki Forge 的官网，以及 Rust、Python、Node.js 的安装方法。`，配对应英文版本。问题不给官网提示，观察同名混淆；评分依据在每个窗口冻结的公开版本和事实清单。

每窗口：6 非品牌意图 × 2 自然语言 × 2 平台 = 24 个回答；2 品牌题 × 2 语言 × 2 平台 = 8 个回答，合计 32。发布前与发布后各一窗口，共 64 次，首轮不再增加重复次数。这优先保证覆盖，代价是每条件只有一次观察，不能估计稳定概率、显著提升或因果效果。

| 指标 | 严格定义 |
| --- | --- |
| 提及 | 指向正确项目，包括中性提及；同名其他产品不计 |
| 有效推荐 | 明确建议用于题中任务，理由符合实际，且适配性、能力边界、安装/迁移条件无实质错误；否定推荐不计 |
| 官网引用 | 包含支持相关结论的 `ankiforge.dev` 链接；GitHub/包页另列 |
| 事实错误 | 包名、语言、运行环境、功能、性能或更新边界存在可证伪错误 |

按平台 × 自然语言四格分别展示无品牌结果；六题都完成时展示 `x/6`，有技术失败时展示 `x/有效回答数`，同时列出计划 6、完成数和失败数。按 SDK 展示具体回答，不把品牌题混入自然发现分母。事实错误率的分母是包含可核查产品事实的回答；零分母记 N/A，缺席不算事实正确。品牌题各预登记四项必要事实，每格八个事实项分别记正确/错误/遗漏/无法核实；技术失败另记，不将未获得的回答伪装成满分或零分。

使用新会话、固定题目和设置，保留完整回答、引用、日期及模型变化。技术失败记录计划数、完成数、失败数，按预定规则最多重试一次，原始记录保留。不能通过追问暗示项目来制造推荐。

### 9.3 使用验证与真实采用

六条入口路径（中文/英文 × 三 SDK）分别检查是否能找到正确安装、版本、限制、程序和更新说明；三套程序按同一契约执行生成和更新。入口检查与端到端执行分别报告，不能把三套程序通过写成六次独立成功。

给定文档的 agent/内部使用验证说明教程是否可用，不代表自然推荐或真实用户采用。实际采用采用轻量证据台账：独立使用者或下游项目、公开包版本、任务、首次成功或持续复用、可核实证据和日期。没有总体分母时不计算虚假的采用率。

建议在教程验收后准备一个试用说明和反馈模板，争取三 SDK 各有一个独立试用反馈；招募和回复时间不作为两三周交付承诺。没有真实案例时，先公开明确标注为维护者示例的成果。对外帖子和联系另以具体稿件与对象为准，本方案不等同于已发送授权。

## 10. 工作包 G：发布与维护

正式部署增加小范围参数护栏：部署到主站的构建必须使用正式 origin、根 base、正确 CNAME；本地/预览继续保留自己的配置能力。[当前配置](../../website/site.config.mjs)、[部署流程](../../.github/workflows/website.yml)

现有 `check:site` 使用相同配置生成期望值，配置与产物一起错误时可能自洽。因此部署后独立抽查首页、Starlight 文档页、中文核心页、robots 和 sitemap 的最终 URL、canonical 与内容。检查失败应阻止继续宣传错误发布，并按正常发布流程修复。

对本轮实质修改的文章/教程维护作者、适用版本和复核日期；只有帮助读者判断内容时效的信息才简洁展示，版本要求优先放在安装处，不在每页堆叠来源与验证说明。提交哈希等留在仓库来源记录中。不要给所有页面自动写构建时间。首轮不建全站 lastmod 依赖图；若日期可准确维护，后续再将小范围日期接入 sitemap。

验证顺序：先小型数据/文档检查，再新增三语言公开包消费者，再完整网站检查与构建，最后部署后抽样。保留既有 `check:ai`、`check:docs`、`check:examples`、`npm test`、`check`、`build` 和 `check:site` 中适用的要求；不要为同一文案增加机械测试。

## 11. 三周实施顺序与工作量

以下是熟悉仓库的一个维护者的估算，包含写作、实现和核对；外部账号、发布等待及真实用户招募另计。双语和三语言要求使完整范围更接近三周，不能同时承诺两周内完成全部工作并取得推荐增长。

| 时间窗口 | 主要交付 | 退出条件 |
| --- | --- | --- |
| 第 1–2 个工作日 | 冻结指标与题目；采基线；保留最小性能数据；验证中文路由方案；修最明确事实冲突 | 数据依赖可读取；内容检查恢复；中文路由没有意外 fallback 扩散 |
| 第 3–7 个工作日 | 共同 JSON/媒体/v1/v2 fixture；三 SDK 完整实现；公开包消费者；文档源同步 | 三 SDK 都能从干净应用生成和更新，实际结果满足契约 |
| 第 8–11 个工作日 | 完成选型页；补齐 7 对页面；精简重复文案；中文改写与术语核对；对应导航/语言映射 | 14 页与三 SDK 输入输出、限制一致，核心路径全部可用 |
| 第 12–13 个工作日 | 全站构建、链接/语言/证据检查；中文独立通读与移动端文案检查；指定客户端导入验证；生产参数护栏与发布检查 | 无已知事实冲突、缺失数据或语言路由错误；公开消费者全部通过；页面简洁与中文表达验收通过 |
| 第 14–15 个工作日 | 修复缓冲；上线后复查；统计快照；收集试用证据；完成后测并标注旧内容/索引状态 | 交付及观测记录完整；若后测必须延后，明确记录未完成及实际采样数，不能以索引状态记录代替问答采样 |

估算构成：最小性能数据与构建依赖 0.5–1 人日；三语言实现、公开消费者及英文核心内容 3–5 人日；局部双语路由、导航和产物检查 1–1.5 人日；中文写作和事实校对 2–3 人日；部署护栏与上线检查 0.5–1 人日。以上约 7–11.5 人日，人工评估和使用验证另留 1–2 人日，再保留修复缓冲，按 15 个工作日排期。测量协议与 64 次问答标注预计 6–9 小时，属于人工评估预算，不重复相加。工期估计依赖现有示例可复用，不包含新 SDK 能力或新的性能实验。

若半天的局部国际化验证暴露超出预期的框架限制，或性能资料迁移牵涉整个实验 CI，不牺牲三 SDK/中英正确性来赶工：先公开具体增加的工作量，再调整排期或缩减外围内容。第 4–6 周可以作后续观察窗口，不属于首轮开发工期，也不自动创建监控任务。

## 12. 发布门槛与后续决策

**发布必须满足：** 三套公开包消费者通过；14 个核心页面及配对正确；页面无多余提示和内部复现细节；中文自然、术语统一且经独立通读；已知正文漂移清除；新性能快照可追溯且无超范围声称；没有坏掉的必需构建依赖；基础测量记录存在；真实案例与维护者示例明确区分。文案精简和中文通读纳入现有写作、校对及发布检查预算，不另增页面或工作阶段。

**推荐增长不作为发布门槛。** 首轮样本只能暴露遗漏和错误。如果后测改善，需要保留原始回答，不直接归因为某个标签或标题；如果没有改善，按症状处理：

| 观察 | 下一步 |
| --- | --- |
| 核心页未索引或仍使用旧内容 | 先诊断抓取、canonical、发现与平台更新，不急于再写文章 |
| 项目被提及但能力被说错 | 修正冲突来源、定义和条件，复测相关事实 |
| 文档已被引用却不适合题目 | 检查问题与真实定位是否匹配，不强行追求被推荐 |
| 推荐准确但首次使用失败 | 优先修安装、运行环境或教程，暂停扩宣传 |
| 可运行但没有独立采用证据 | 与愿意试用的目标开发者核实需求和阻力，不以 star/下载代替采用 |
| 一个语言/地区样本明显不同 | 保留分层结果，增加该组样本后再决策，不改变用户的三 SDK 同等支持要求 |

首轮延期：全量参考文档翻译、第二个 CSV/IO 教程主题、全站 schema、自动 lastmod 依赖图、llms-full、IndexNow 自动化、新分析服务、自动模型监控、首页视觉重设计、新性能实验和独立 benchmark 长文。Google 官方没有特殊 AI schema 门槛，llms.txt 不影响其搜索排名；这些事项应由后续具体需求推动。[Google 官方指南](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)

计划实施过程中的 PR/提交建议按“数据依赖 → 事实修正 → recipe 与公开消费者 → 双语核心内容 → 选型与发布验收”拆分。每个切片保持可审阅和可验证；不要把 1,893 个性能资料删除、所有文案、i18n 和测量代码混成一个难以判断的变更。
