# Anki Forge 新增语言的市场依据

决策日期：2026-10-27，America/Los_Angeles。适用对象：Anki Forge 官网及 Rust、Python、Node.js 开发者文档；现有英文和简体中文不计入新增名额。

建议新增 **西班牙语 `es`、巴西葡萄牙语 `pt-BR`、日语 `ja`、德语 `de`、法语 `fr`、俄语 `ru`**。实施顺序为 `es / pt-BR` → `ja / de` → `fr / ru`。这是在缺少本站语言需求数据时的投资优先级；公开数据不能证明它们就是本站实际新增流量最大的六种语言。印尼语 `id` 是最强候补，尤其应与第六席俄语比较。

Anki Forge 的目标用户是将数据编程转换为 APKG 的开发者和内容生产者。语言学习人数、某语言牌组下载量、Anki 用户总数，都不能直接替代这一用户群的搜索需求。[项目定位](../../../../README.md)

## 六种语言的选择和优先级

| 顺序 | 语言和范围 | 选择依据及产品推断 | 证据强度与需要验证的问题 |
| --- | --- | --- | --- |
| 1 | 西班牙语 `es`，首版使用跨地区易懂的用语 | 网站语言生态大；多个相关经济体的开发者市场可共用一个语言版本。推断：一份高质量技术文档有较广的潜在触达范围 | 市场规模代理较强；本站技术查询量、地区用词和英语版本替代程度未知 |
| 2 | 巴西葡萄牙语 `pt-BR` | 巴西有明显的开发者市场规模；先集中一个地域变体，便于统一审校。选择 `pt-BR` 的依据来自巴西市场，不能由 W3Techs 的整个葡语比例单独推出 | 市场代理较强；需验证巴西来源的相关查询和安装意向 |
| 3 | 日语 `ja` | 日本 GitHub 账号规模与日语网站生态都较大；可形成独立的本地技术内容入口 | 市场代理较强；“很多人在用 Anki 学日语”不能证明日本开发者需求大，仍需查询证据 |
| 4 | 德语 `de` | 德语网站生态及德国开发者市场均有规模，适合完整翻译指南、迁移和参考文档 | 市场代理较强；新增访问是否只是从既有英语页面迁移，必须测量 |
| 5 | 法语 `fr` | 法语网站生态大，法国本身已有较大开发者市场；首版使用通用法语，不立即拆分法国、加拿大和其他地区版本 | 市场代理中等偏强；其他法语地区的可达规模及产品需求尚未量化 |
| 6 | 俄语 `ru` | 俄语网站生态与俄罗斯开发者市场均支持入围；当前作为较成熟内容生态的第六席 | 入围合理但与印尼语的先后置信度较低；需要用本站查询和实际激活比较 |

顺序是综合上述两个代理与翻译投入方式的判断，不是加权公式得出的精确市场排名。暂不使用缺乏观测输入的“潜力分数”，也不承诺某语言能带来固定百分比增长。

Anki 官方手册列出了西语、巴西葡语、日语、德语、法语、俄语的志愿译本，也列出印尼语、意大利语、阿拉伯语等；官方同时提醒译本可能不是最新。这能支持术语调研和潜在社区审校渠道的存在，不能用于证明本轮六种语言比其他语言的 Anki 用户更多。[Anki 手册翻译列表](https://docs.ankiweb.net/manual/intro#translations)

## 候补语言及未入选原因

| 候补 | 本轮判断 | 改变优先级所需证据 |
| --- | --- | --- |
| 印尼语 `id` | 最强候补。其地域开发者代理已超过德国、俄罗斯和法国；内容语言生态较小并不等于需求小，不能只凭 W3Techs 排除 | 如果印尼相关的高意图查询、安装命令复制和示例使用信号优于俄语，应优先安排印尼语 |
| 韩语 `ko` | 有规模的开发者市场，但当前两个代理尚不足以挤进首选六种；不能由韩国国家规模直接推出韩语增量 | 韩语技术查询、现有韩国来源流量和可持续母语审校资源 |
| 意大利语 `it` | 网站生态不小，作为下一轮成熟市场候选；本轮六席更优先覆盖选定的开发者市场 | 意语相关 Anki 自动化需求、迁移词和落地页表现 |
| 印地语 `hi` | 印度账号数量很大，但印度多语言环境使“印度市场＝印地语市场”无效；现有英文版的覆盖与新增印地语需求必须拆开 | 实际印地语技术查询、语言偏好及相对于英语入口的提升 |
| 阿拉伯语 `ar` | 多个相关市场有潜力；首轮需同时处理从右到左界面和夹杂代码、路径、数字的双向排版，投入不同于此次六种从左到右语言 | 明确的阿语需求，以及足以支持完整 RTL 验收和持续审校的资源 |

## 用本站数据验证新增流量

首轮发布前，导出最近 90 天 Search Console 查询、页面、国家、设备、点击、展现、CTR 和平均排名，并保留最近 28 天作为近期窗口。Search Console 的标准维度没有“用户语言”；页面路径可以确定内容语言，查询语言只能经过分类推断，国家也不能直接等同于语言。[Google Search Console 指标和维度](https://support.google.com/webmasters/answer/7576553)

验证单位是“某种语言的具体任务”，如生成 APKG、JSON 转 Anki、Python 生成牌组、genanki 迁移、Image Occlusion 和安全更新。品牌名称、代码符号和 `Anki Python` 等跨语言词保持单独分组，避免强行归到某一种自然语言。

建议在每批发布后查看第 28、56、84 天的完整窗口。这些是操作节奏，不是搜索引擎收录或排名提升的承诺。至少观察：

- 新语言页面的非品牌自然搜索点击、有效收录页面及进入指南的访问。
- 相同市场和任务在全部语言页面上的总点击，区分纯粹从英语页面迁移与全站增长。
- 本地化内容进入安装、示例和下载的行为；“复制安装命令”是安装意向，不等于已经安装或成功生成 APKG。
- 对照同期英语趋势、发布活动和季节性；分批上线只能改善解释能力，不能自动形成因果实验。
- 每种语言的审校耗时、过期页面比例和搜索无结果率，判断持续新增内容的投入。

优先级调整应依据相关查询、真实使用行为和持续维护成本共同进行。数据量小或查询被匿名化时，应保留“尚不足以判断”，不能把零观测直接解释为零需求。实际新增流量仍需后续观测，本次研究未访问本站私有分析后台。
