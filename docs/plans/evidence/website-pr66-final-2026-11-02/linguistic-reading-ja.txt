1: # ビルドと出力の保証
2:
3: `Project::build` は操作が成功した場合にのみ `BuildOutput` を返し、APKG 成果物の存在を保証します。失敗した操作は、構造化された kind/code、観測結果、原因、実際の公開状況を持つ `BuildError` を返します。
4:
5: <!-- section: temporary-and-persistent-artifacts -->
6: ## 一時成果物と永続成果物
7:
8: 所有権のモデルを明示的に選びます。
9:
10: | 要求 | 所有権 |
11: | --- | --- |
12: | `BuildOptions::to(path)` | 永続的な保存先。ハンドルの解放後も残る |
13: | `BuildOptions::temporary()` | 一時ファイル。最後の成果物所有者とともに削除される |
14: | `artifact.persist_to(path)` | 新たな永続所有者。元の所有者も引き続き使用できる |
15:
16: 一時パスを読んでいる間は、`BuildOutput` または成果物のクローンを保持してください。レポートや JSON スナップショットはファイルの生存期間を延ばしません。Rust は通常の仕組みで所有者をドロップします。Node には決まったタイミングで解放するための `artifact.close()` があります。パスをアプリケーションの状態にコピーするだけでは、所有者は作成されません。
17:
18: Rust の成果物ハンドルは、ビルドや `persist_to` で相対パスを指定した場合でも絶対パスを保持します。その後にプロセスの作業ディレクトリが変わっても、既存ハンドルが読み取りやコピーに使う元ファイルは変わりません。新しい `persist_to` の保存先は、呼び出し時のディレクトリを基準に解決されます。
19:
20: `BuildReport::snapshot()` は観測結果だけを含みます。`BuildOutput::snapshot()` と `BuildError::snapshot()` は、さらに実際の成功・失敗を示します。成功したスナップショットにも警告が含まれる場合があります。診断の重大度、パスの存在、レポートに比較結果があるかどうかから、成功・失敗を推測しないでください。
21:
22: <!-- section: baselines-and-publication -->
23: ## 基準パッケージと公開
24:
25: 更新時には、前回配布時のオリジナル APKG を不変の基準パッケージとして保存し、出力先には別のパスを選びます。基準の証拠と候補の内容は公開前に検査されます。ポリシーが拒否した場合は出力を置き換えません。証拠の欠落・破損や検査上限の超過は、許可できない失敗です。
26:
27: 公開には APKG のアトミックな置き換えを使います。保証はファイル単位です。アプリケーションの別の JSON レポートを書き出す処理は、別の操作です。通常のビルドは識別情報の別ファイルを出力しません。バージョン付きの完全な証拠は配布パッケージに埋め込まれます。
28:
29: 永続化の確認中など、公開後の遅い段階でエラーが発生することがあります。そのため、エラーのスナップショットは `PublicationSnapshot` の事実を記録します。対象は `path`、`stage`（`not_published` または `published`）、`temporary`、耐久性（`confirmed` または `unconfirmed`）です。再試行したり、ファイルが書き出されていないと通知したりする前に、これらを確認してください。`PersistError` も公開状況と実際の I/O エラー原因を保持します。アトミックな置き換えだけで、クラッシュ後の耐久性まで確立されるわけではありません。
30:
31: スナップショットのシリアライズはファイルシステムにアクセスせず、ネイティブのパスを保持します。Unicode パスは JSON 文字列になります。UTF-8 でない Unix パスは `{"encoding":"unix_bytes","bytes":[...]}`、対になっていない UTF-16 サロゲートを持つ Windows パスは `{"encoding":"windows_wide","units":[...]}` を使います。配列には正確なネイティブのバイト列またはコード単位が入ります。成功時の成果物パス、失敗時の公開パス、バインディングのエラーパス詳細はすべてこの表現を使います。これらの値はパスを記述するだけで、成果物の所有権は保持しません。特定のネイティブパスをファイルシステムが拒否しても、公開に失敗した事実はシリアライズできます。
32:
33: <!-- section: inspection-limits -->
34: ## 検査の上限
35:
36: アーカイブ、エントリー数、展開、デコード後のコレクション・メディア、zstd ウィンドウには有限の上限があり、基準パッケージと候補に独立して適用されます。`InspectLimits::default()` から始め、必要な上限だけを意図的に増やしてください。0は無制限を意味しません。これらのカウンターは、プロセス全体のメモリや CPU のサンドボックスではありません。メディアのインポートには、それより前の段階で適用する別のアセット単位の上限があります。
37:
38: <!-- section: concurrent-work -->
39: ## 並行処理
40:
41: Rust のビルドは不変のプロジェクト状態を借用します。データを所有するモデルとメディアは、プロジェクト間で共有できます。Node バインディングは build または compare の呼び出し時にプロジェクトのスナップショットを取得するため、後からノートを追加してもその要求は変わりません。すべての読み取り側が終わるまで成果物の所有者を保持してください。別の利用側がまだパスを必要としている間に最後の一時所有者を閉じることは、アプリケーション側の生存期間管理の誤りです。
42:
43: パッケージの検査だけでは、クライアント側のすべての動作を確認できません。対象の Anki バージョンと設定で、描画、再生、更新のインポートをテストしてください。復習スケジュールとスキーマ変更の制約は[更新](/docs/updates/)を参照してください。
44:
45: <!-- section: prepared-publication-from-source -->
46: ## 候補ファイルを準備し、確認後に保存する
47:
48: 候補を事前に生成し、確認後に保存する機能は、公開 `0.3.1` パッケージに含まれています。
49:
50: `prepare_publication` は1つの非公開の候補をビルド・検査・比較します。`publish` は同じファイルを使います。オプションと相対保存先は準備時に確定します。プロジェクトを編集しても候補は変わりません。準備だけで保存先が置き換わることはありません。未公開の所有者をドロップまたは閉じると候補が削除されます。
51:
52: 公開の試行は、ポリシー拒否や I/O 失敗を含めて、必ず所有者を消費します。再試行したり、ポリシーや保存先を変えたりするには、再び準備してください。レポートは引き続き読めますが、ファイルは所有しません。Node と Python は冪等な `close()` と、理由が `closed` または `consumed` の利用不可エラーを提供します。公開開始後に閉じてもキャンセルはしません。所要時間にはレビュー待ち時間を含みません。置き換え成功後に耐久性の確認が失敗する場合があるため、実際の公開状況を確認してください。
53:
54: [完全な例](/docs/updates/#build-once-review-then-publish)と各言語の API リファレンスで、型付きエラーとワーカーの動作を確認できます。

68: 型付きの `image()` と `sound()` の値は、エクスポートまで依存関係を保持します。手書きの HTML・CSS・スクリプトで参照する場合は、`builder.asset(media)` または `project.add_asset(media)` が必要です。ライブラリは任意の文字列からファイルの内容を推測しません。明示的なアセットは、静的に検出可能な参照がなくても含まれます。
69:
70: `with_export_name` には実際のファイル名をそのまま渡してください。型付き音声参照は描画時に HTML エンティティをエスケープするため、`tone&copy;.mp3` のような名前も、その名前のアセットを正確に参照します。ファイル名を事前にエスケープしないでください。音声ファイル名のパーセント記号やフラグメント記号は文字どおり扱い、URL パスとは解釈しません。
71:
72: <!-- section: names-mime-and-budgets -->
73: ## 名前、MIME、上限
74:
75: 既定のエクスポート名は内容から導かれ、元のパスには依存しません。固定のファイル名が必要なら、参照を作成する前に `with_export_name` を使います。クローンの名前を変えても、それ以前のクローンやコンテンツノードの名前は変わりません。
76:
77: 名前にパス、制御文字、移植性のない予約名を含めることはできません。競合検査は Unicode NFC と大文字・小文字の正規化を使います。そのため、大文字・小文字または正規化形式だけが異なる名前も競合します。名前と内容が完全に一致する組み合わせの登録は冪等です。同じ名前で異なる内容を登録すると、部分的に登録せず失敗します。
78:
79: 拡張子を含めたエクスポート名全体の上限は UTF-8 で255バイトです。プロジェクトとテンプレートバンドルの JSON Schema は、ファイル名の構文と文字数を検査します。ローダーはバイト数も検査します。たとえば `é` を128回繰り返すとスキーマの文字数上限は通りますが、256バイトになるため、読み込み時に `MEDIA.EXPORT_NAME_INVALID` を返します。ビルド前に `tools::load_project` または `NoteType::from_bundle` で入力全体を検証してください。 `tools::load_project` は `internal-tools` feature が必要なリポジトリ内部向けの API であり、利用側アプリケーション向けのサポート対象 API には含まれません。
80:
81: MIME の構文と、判別可能な内容は一致する必要があります。ネイティブのバイト列には64 KiBのインライン上限はありません。インポートの既定上限はアセットごとに256 MiBです。`file_with_limits` と `bytes_with_limits` は、読み取り前に `MediaLimits { max_bytes }` を受け取ります。大きなスナップショットは一時ストレージに退避される場合があり、最後の所有者が解放されると削除されます。スナップショットを所有していても、インポート中に同時変更される元ファイルについて、ファイルシステムのアトミックな読み取り像を保証するものではありません。
82:
83: プロジェクト JSON では、インラインの `bytes` 配列をデコードするときにも同じ既定のアセット単位の上限を適用します。最初の超過バイトで停止し、配列の残りは収集しません。エラーには上限と観測バイト数を持つ `MediaError` が保持されます。拒否時のバイト数は下限であり、未読部分を含む配列全体のサイズではありません。
84:
85: 有効なメディアパッケージであっても、すべての Anki クライアントでコーデックが再生できるとは限りません。対象クライアントで画像、音声、フォントをテストしてください。[トラブルシューティング](/docs/troubleshooting/#media-and-templates)を参照してください。
86:
87: <!-- section: typed-image-and-sound-usage -->
88: ### 型付きの画像・音声としての使用
89:
90: コンストラクター自体は引き続き失敗しません。`Project::add` はインポート時に保持した MIME を検査します。画像には `image/*`、音声参照には `audio/*` と `video/*` を受け付けます。`application/octet-stream`、テキスト、フォント、PDF の型付き使用は `NOTE.MEDIA_USAGE_INVALID` になります。直接記述した HTML・CSS 用の明示的アセットとして登録してください。正しい形式で明示した未知の画像・動画 MIME は種類の検査を通りますが、デコーダーやプレーヤーがそのバイト列に対応することを保証するものではありません。改名によって保持済みの MIME が変わることはありません。ビルドでは配置済みのバイト列を判別し、エクスポート拡張子を独立して検証します。`wrong.mp3` という名前の PNG は画像としての追加に成功しても、ビルドで `MEDIA.DECLARED_MIME_MISMATCH` になることがあります。

96:
97: これらのメソッドは公開 `0.3.1` パッケージに含まれています。
98:
99: 同時実行数を制限して複数のファイルをインポートし、入力順を保ちながら、後のエクスポートに使うメディアスナップショットを所有します。

108: <!-- section: batch-behavior-and-budgets -->
109: ### 一括処理の動作と上限
110:
111: Rust では `Media::files(paths)`、Node では `await Media.files(paths)`、Python では `Media.files(paths)` を使います。呼び出しごとに最大4ワーカーで、入力順にファイルをインポートします。16ファイル未満のバッチは逐次実行します。Rust には `files_with_limits` もあります。Node と Python は `file` と同じ上限指定を受け付けます。上限はアセットごとに適用します。インポートに失敗すると、開始済みの処理を待ってからバッチのスナップショットを破棄し、入力順で最初のエラーを返します。既存のメディア所有者は引き続き有効です。Python はインポート中に GIL を解放し、Node はイベントループの外で処理します。単一ファイルのインポートは、従来どおりその場でデータを所有するスナップショットを取得します。同時実行を使うには、一括メソッドを明示的に選んでください。
112:
113: 生存中のスナップショットは、プロセス全体で **64 MiB** のメモリ枠を共有します。1 MiBを超える個々のアセットは、引き続き一時ファイルへストリーミングします。エンコード済みメディアは、準備処理ごとに遅延確保する **16 MiB** のバッファープールを共有し、いっぱいになると一時ストレージへ退避します。これらの上限は他の作業用メモリを含まず、RSS の上限ではありません。同時ビルドはそれぞれ独自のエンコード用プールを所有できます。

45: ## メディアと画像穴埋め
46:
47: `await Media.file(path, limits?)` と `await Media.bytes(Uint8Array, mime, limits?)` は、データを所有するスナップショットを返します。await が成功した後は元ファイルを変更・削除できます。`withExportName(name)` は、それ以前のクローンやコンテンツを変更せず、改名した値を返します。`filename`、`mediaType`、`byteLength` はプロパティとして読み取ります。
48:
49: `media.image()` と `.sound()` は、プロジェクトへのアセット追加を自動で行う型付き Content を返します。直接記述した HTML・CSS・スクリプトの参照には、明示的な `project.addAsset` とモデルの `builder.asset` を使います。メディア上限は `{ maxBytes }` を受け付けます。既定値は256 MiBで、ネイティブバイト列に64 KiBのインライン上限はありません。
50:
60:

64: ## ビルド、比較、出力
65:
66: | API | 結果 |
67: | --- | --- |
68: | `await project.build(BuildOptions.to(path))` | 永続成果物を所有する BuildOutput |
69: | `await project.build(BuildOptions.temporary())` | 一時成果物を所有する BuildOutput |
70: | `await project.compare(CompareOptions.against(path))` | ポリシーによる公開拒否も含む、完了した ComparisonReport |
71: | `options.updateFrom(path)` | 配布時のオリジナルパッケージの完全な証拠を使った更新を設定 |
72: | `options.inspectLimits(limits)` | 独立した検査カウンターを上書き |
73: | `options.updatePolicy(policy)` | 更新・比較のリスクポリシーを設定 |
74:
75: 成功した出力は `.artifact`、`.report`、`.snapshot()` を公開します。`BuildReport` は `.counts`、`.baselineCounts`、`.durationMs`、`.diagnostics`、`.comparison`、`.snapshot()` を公開します。成功・失敗の結果やファイルの所有権は持ちません。`.comparison` は `ComparisonReport` または `null` で、`project.compare()` と同じクラスを使います。比較は `.findings`、`.highestRisk`、`.policy`、`.diagnostics`、`.snapshot()` を公開します。スナップショットのフィールド名は、`allows_publication` や `schema_version` を含めて Rust の JSON と一致します。ネイティブレポートを camelCase にしたコピーではありません。`null` でないことを確認した後、比較オブジェクトでは `report.comparison.highestRisk`、JSON スナップショットでは `report.snapshot().comparison.highest_risk` を使います。
76:
77: `new UpdatePolicy()` は High/Critical を拒否します。`.failOn('medium')` はしきい値を変更します。`.allow('RISK.NOTE_REMOVED')` は証拠と重大度を保持したまま、その分類全体を明示的に許可します。不明なコードとハードエラーは許可できません。新規作成だけのビルドにポリシーを指定するとエラーになります。比較とビルドの公開判断を一致させるには、同じポリシーと上限を使ってください。
78:
79: 検査オプションには `maxArchiveBytes`、`maxEntries`、`maxCentralDirectoryBytes`、`maxZipEntryBytes`、`maxZipTotalBytes`、`maxMetaBytes`、`maxMediaMapBytes`、`maxIdentityBytes`、`maxCollectionBytes`、`maxMediaBytes`、`maxDecodedTotalBytes`、`maxZstdWindowBytes` があります。値は非負の安全な整数、または u64 の最大値までの `bigint` です。0は実際に上限0を意味します。カウンターは基準パッケージと候補に独立して適用します。不明なオプションはエラーになります。

81: <!-- section: artifact-lifetime-and-concurrency -->
82: ## 成果物の生存期間と並行処理
83:
84: JSON スナップショットのパスは、エクスポートされた `PathSnapshot` 型を使います。Unicode パスは文字列です。Unicode でないネイティブパスは `{ encoding: "unix_bytes", bytes: number[] }` または `{ encoding: "windows_wide", units: number[] }` になります。配列は正確な Unix のバイト列または Windows の UTF-16 コード単位を保持します。ビルドスナップショットの成果物パス、失敗時の公開パス、構造化エラーのパス詳細が対象です。エンコード済みのパスは元のプラットフォームでのみデコードしてください。Unix では `Buffer.from(value.bytes)` が、Node のファイルシステム関数で使えるバイト列のパスを保持します。Node の作成メソッドは引き続き文字列のパスを受け付けます。
85:
86: 相対的なメディア・バンドルのパスは読み取りの呼び出し時に、ビルド先と基準パッケージはオプション作成時に基準ディレクトリが確定します。POSIX では、シンボリックリンクの後の `..` はファイルシステムでのパス走査の意味を保持します。`persistTo` は、クローン済み・永続化済みハンドルも含め、元のビルドが記録した作業ディレクトリを相対保存先の基準にします。後から作業ディレクトリを変えても、これらのパスは変わりません。
87:
88: `.path` を利用している間は成果物の所有者を保持します。`.clone()` は独立した所有者を作り、`await .close()` はその所有者を解放します。最後の一時所有者が解放されるとファイルが削除されます。`await .persistTo(path)` は永続成果物を返し、失敗しても元の成果物は使用できます。所有者を保持していれば、標準の Node ファイルストリームで成果物を読み取れます。
89:
90: スナップショットは凍結済みの JSON データで、ネイティブファイルを保持しません。永続ファイルは所有者の解放後も残ります。`BuildOutput` は呼び出し側で構築できず、成功したビルドによってのみ作成されます。
91:
92: ビルドと比較は、呼び出し時に取得した所有付きのプロジェクトスナップショット上で非同期実行します。後の編集でその要求が変わることはありません。メディアの読み取りとバンドルの読み込みもワーカーで実行します。Node の ESM と CJS は同じネイティブモジュールとクラス識別子を共有します。
93:
94: <!-- section: errors -->
95: ## エラー
96:
97: `SchemaError`、`AddError`、`MediaError`、`TemplateBundleError`、`ImageOcclusionError`、`PolicyError`、`ConfigurationError`、`CompareError`、`BuildError`、`PersistError` は `ForgeError` を継承します。`kind`、`code`、`domain`、ネイティブ原因チェーンのテキスト `causes`、認識可能な I/O・スキーマ・メディア・上限の原因を構造化した `sourceDetails`、操作の `details` を公開します。元のネイティブ例外は JS の `cause` に保持されます。
98:
99: `BuildError.snapshot()` は失敗と公開状況を保持します。`BuildError.report` と `CompareError.report` は `BuildOutput.report` と同じ BuildReport を返します。これらのレポートでは `.baselineCounts` と `.comparison` を使い、snake_case の JSON フィールドには `.snapshot()` を使います。失敗した比較では、一部の観測結果と `null` の比較が含まれる場合があります。`PersistError.publication` は、保存先がすでに公開されたか、耐久性が確認されたかを記録します。メディア・検査エラーは上限の詳細を保持します。エラーメッセージの解析ではなく、これらの機械処理用フィールドを使ってください。`ArtifactClosedError` は閉じた所有者の使用、`NativeLoadError` はネイティブパッケージの欠落・非互換・古いバージョンを報告します。

101: <!-- section: addition-context -->
102: ## 追加時のコンテキスト
103:
104: 追加に失敗してもプロジェクトは変わりません。構造化コンテキストには元のノート・モデルのキーと対象を記録し、必要に応じて競合やメディア使用の詳細を付けます。Rust では `AddError::context()` / `detail()` を通じて `note::{AddContext, AddTarget, AddDetail}` を取得できます。SDK では `AddError.details` が型付きの context/detail を提供します。Node のフィールドは camelCase で深く凍結されています。Python は snake_case の TypedDict を使います。タグは挿入時のインデックスを保持します。フィールドの位置は、元のシーケンスインデックス（フィールド自体は null/None、ルートは []）と任意の UTF-8 バイト範囲を保持します。ビルド時の既定デッキのエラーはノート・モデルのキーを持たず、原因チェーンから確認できます。
105:
106: 型付き画像を追加する際は image/* MIME が必要です。音声参照には audio/* または video/* を受け付けます。他の種類は `NOTE.MEDIA_USAGE_INVALID` になります。コンストラクター自体は失敗せず、明示的アセットと直接記述した HTML には影響しません。検査はインポート時に保持した MIME を使い、再生を保証しません。ビルド時の独立した MIME・拡張子検証も引き続き適用されます。対象と詳細の完全な対応表は[設計文書](https://github.com/morehardy/anki-forge/blob/main/docs/plans/2026-09-28-rust-api-validation-and-errors-design.md)を参照してください。

116: ### 準備、確認、公開
117:
141:
142: `publish()` はネイティブの所有者を即座に取得し、1つのワーカータスクを実行します。ポリシーや I/O による拒否を含め、すべての試行で所有者を消費します。再呼び出しは `PreparedPublicationStateError` で拒否され、コードは `BUILD.PREPARED_UNAVAILABLE`、`reason` は `consumed` または `closed` です。公開開始後に閉じてもキャンセルされません。閉じた後もレポートは読めます。オプションは準備の呼び出し時に確定します。ポリシーや保存先を変えるには、再び準備する必要があります。所要時間には確認待ち時間を含みません。レポートや JSON を所有者へ戻すことはできません。
143:
144: ビルド、比較、準備、クローンは、不変のネイティブ Project のバージョンを共有します。作成時の変更は引き続き同期的で、互いに独立しています。別のスナップショットが生存している間の最初の変更では、Project がコピーされる場合があります。その後に排他的に行う変更ではコピーしません。これによりコピー処理は Promise の送信時から移りますが、最初の編集の高速化、最悪タイマー遅延の改善、RSS の削減を保証するものではありません。JavaScript のバイト列入力は、引き続きワーカー送信前にコピーします。これらのラッパーにはプロトコル6のバイナリーを使ってください。

23: ## モデルとテンプレート
24:
25: `NoteType.builder(key)` は不変のビルダーを返します。`.name`、`.field`、`.template`、`.css`、`.cloze_field`、`.asset` の各メソッドは、変更を反映した新しいビルダーを返します。`.build()` は定義全体を検証し、不変の NoteType を返します。`model.note()` は、そのモデルを所有するノートを作成します。`NoteType.from_bundle(path, limits=MediaLimits())` は、現在のバンドル形式から同じモデルと関連ファイルを読み込みます。任意の上限指定は、各ファイルを読み込む前に個別に適用されます。

30: ## メディアと画像穴埋め
31:
32: | API | 動作 |
33: | --- | --- |
34: | `Media.file(path, *, limits=MediaLimits())` | 直ちにファイルを読み込み、内容のスナップショットを所有します |
35: | `Media.bytes(data, media_type, *, limits=MediaLimits())` | 明示した MIME タイプとともにバイト列を所有します |
36: | `media.with_export_name(name)` | 同じスナップショットを共有する、別のファイル名の値を返します。以前の参照の名前は変わりません |

44: <!-- section: operations-and-results -->
45: ## 操作と結果
46:
47: | API | 結果 |
48: | --- | --- |
49: | `project.build(BuildOptions.to(path))` | 永続ファイルが保証された BuildOutput を返します |
50: | `project.build(BuildOptions.temporary())` | 所有権付きの一時ファイルを持つ BuildOutput を返します |
51: | `options.update_from(path)` | 完全な基準パッケージの識別情報を使って更新するオプションを返します |
52: | `project.compare(CompareOptions.against(path))` | 完了した ComparisonReport を返します。公開ポリシーによる判断は検出事項とは別に含まれます |
53: | `options.update_policy(policy)` | Update／Compare に明示的なリスクポリシーを適用します。Create に指定すると設定エラーになります |
54: | `options.inspect_limits(limits)` | 基準パッケージと候補に、それぞれ有限の上限を適用します |
55:
56: BuildOutput は `.artifact`、`.report`、`.snapshot()` を持ちます。BuildReport は `.counts`（ノート数・カード数・メディア数を持つ BuildCounts）、`.diagnostics`、`.comparison`、`.snapshot()` を公開します。レポート自体は成功・失敗という処理結果やファイルの所有者を持ちません。ComparisonReport は `.findings`、`.policy`、`.allows_publication`、`.snapshot()` を公開します。スナップショットは JSON にシリアライズできる通常の辞書であり、成果物の所有権は含みません。
57:
58: ApkgArtifact は `.path`、`.persist_to(path)`、`.close()` を公開します。`copy.copy` でコピーすると所有者が1つ増えます。コンテキストマネージャーは終了時にその所有権を解放します。一時ファイルは最後の所有者が解放されると消えます。永続パスのファイルは、ハンドルを破棄しても残ります。永続化に失敗しても、元のハンドルは引き続き利用できます。
59:
60: `UpdatePolicy()` は High と Critical の検出事項をブロックします。`.fail_on(RiskLevel.MEDIUM)` はしきい値を変更します。`.allow('RISK.NOTE_REMOVED')` は、根拠を保持したまま、登録済みカテゴリ全体を明示的に許容します。不明なコードは即座に拒否されます。`InspectLimits` は `max_identity_bytes` を含む、すべての有限のバイト数／件数上限を公開します。必須の検査を無効にすることはできません。
61:
62: <!-- section: errors-and-concurrency -->
63: ## エラーと並行処理
64:
65: 失敗時には SchemaError、AddError、MediaError、ImageOcclusionError、TemplateBundleError、CompareError、PolicyError、BuildError、PersistError のいずれかが送出されます。それぞれ `kind`、`code`、`details`、`source_details` 内の構造化された検査結果、`causes` 内の原因チェーンのテキストを公開し、ネイティブ例外を `__cause__` として保持します。取得可能な場合は、I/O の原因も連鎖した OSError として保持されます。BuildError は `.report` と `.snapshot()`、CompareError は部分的な `.report` を持ち、PersistError の details には実際に起きた公開処理の情報が含まれます。
66:
67: ネイティブの Project 操作は GIL を解放し、同じオブジェクトの同時利用を `BINDING.PROJECT_BUSY` で拒否します。独立したプロジェクトは並行して実行できます。プロセスを fork した後は、すべてのネイティブ値とハンドルを作り直してください。引き継がれたハンドルは `BINDING.FORKED_OBJECT` で操作を拒否し、クリーンアップでも親プロセス所有のファイルを削除しません。子プロセスで作った値は通常どおり動作し、クリーンアップされます。[診断](/docs/python-diagnostics/)も参照してください。

69: <!-- section: addition-context -->
70: ## ノート追加時のコンテキスト
71:
72: 追加に失敗した場合、プロジェクトは変更されません。構造化されたコンテキストには、元のノート／モデルキーと対象が記録され、必要に応じて衝突やメディアの使用箇所の詳細も含まれます。Rust は `note::{AddContext, AddTarget, AddDetail}` を `AddError::context()`／`detail()` で公開し、SDK は型付きのコンテキストと詳細を `AddError.details` で公開します。Node のフィールドは camelCase で、入れ子も含めて不変です。Python は snake_case の TypedDict を使います。タグは挿入時のインデックスを保持します。フィールドの位置は元のシーケンスのインデックス（フィールド自体には `null`／`None`、ルートには `[]`）と、任意の UTF-8 バイト範囲を保持します。ビルド時のデフォルトデッキのエラーにはノート／モデルキーがなく、原因チェーンから確認できます。
73:
74: 型付き画像を追加する場合は image/* MIME が必要です。音声参照には audio/* または video/* を使えます。それ以外のカテゴリでは `NOTE.MEDIA_USAGE_INVALID` が発生します。コンストラクターは引き続き失敗せず、明示的なファイル追加と生の HTML には影響しません。この検査はインポート時に保持した MIME を使うもので、再生できることを保証しません。ビルド時の独立した MIME／拡張子検証も引き続き適用されます。対象と詳細の全項目は[設計文書](https://github.com/morehardy/anki-forge/blob/main/docs/plans/2026-09-28-rust-api-validation-and-errors-design.md)を参照してください。

82: ### 準備、確認、公開
83:
103:
104: 公開を一度試みると、ポリシー違反や I/O エラーで失敗した場合も含めて所有者を消費します。その後の呼び出しは `PreparedPublicationStateError` となり、コードは `BUILD.PREPARED_UNAVAILABLE`、理由は `closed` または `consumed` です。close は、すでに実行中の公開処理を取り消しません。相対パスは準備の呼び出し時に確定し、後から Project を変更しても確認対象の APKG は変わりません。レポートは close 後も利用でき、ファイルは保持しません。オプションの変更や再試行には、もう一度準備を行ってください。所要時間には確認待ちの時間は含まれません。遅い段階のエラーでは、置換に成功していても永続性が未確認の場合があります。対応を決める前に、公開処理の実際の結果を確認してください。ネイティブ binding protocol 1 と contract bundle 2.1.0 が必要です。同じバージョン番号でも古いバイナリは拒否されます。

1: # Python API の刷新
2:
3: `python -m pip install ankiforge` と `from ankiforge import ...` を使います。以前の配布名 `anki-forge` とインポート名 `anki_forge` は、互換エイリアスではありません。ソースをチェックアウトして使う場合、名前を変更した後は Maturin でネイティブ拡張を再ビルドしてください。[セットアップガイド](https://github.com/morehardy/anki-forge/blob/main/bindings/python/README.md)を参照してください。
4:
5: 旧 API の互換レイヤーは残していません。従来の Deck・レジストリ・ランタイムの API を、データを所有する公開モデルに置き換えます。
6:
7: | 従来の手順 | 現在の手順 |
8: | --- | --- |
9: | 安定 ID が任意の Deck または Project | `Project(namespace, default_deck=...)` |
10: | `add_note(note)` と内容由来の識別情報 | `add(stable_key, note)` |
11: | 変更可能な NoteType と add_notetype | `NoteType.builder(key)...build()` の後に `model.note()` |
12: | 文字列によるモデル参照 | ノートが検証済みモデルを所有 |
13: | プロジェクトのメディアレジストリ | 独立した `Media.file` / `Media.bytes` スナップショット |
14: | インラインで描画したメディアとフィールド専用 setter | `Content.sequence`、`media.image()`、`media.sound()`、`Note.field` |
15: | 暗黙の HTML | 文字列は Text。HTML には `Content.html` を使う |
16: | 安定した識別情報のないマスク | `Mask.rect(key, x, y, width, height)` |
17: | 成果物がない場合もある戻り値と ensure_success | 成果物が保証された `BuildOutput`。失敗時は構造化エラーを送出 |
18: | 診断からレポートの成功・失敗を推測 | Output/Error のスナップショットが実際の結果を示す。Report は観測結果のみ |
19: | Diff、lockfile、更新安全性の切り替え | `compare(CompareOptions.against(...))`、`BuildOptions.update_from(...)` |
20: | 実行時のサブプロセス用パッケージ | デフォルト Rust API へのプロセス内 PyO3 バインディング |
21:
22: 更新の基準に使えるのは、現在の識別情報の証拠を持つ完全な配布時のオリジナル APKG だけです。旧バンドルや古い APKG の証拠を自動復元することはありません。新しい手順は README と実行可能なサンプルを参照してください。

1: # Rust API
2:
3: よく使う値は crate のルートにあります。`Project`、`Note`、`NoteType`、`Field`、`Template`、`Content`、`Media`、`BuildOptions`、`BuildOutput` です。公開されている機能別モジュールは `note`、`schema`、`media`、`build`、`update`、`diagnostics` です。リポジトリのツール群は、feature で有効にする別の API 群です。利用側のアプリケーションに必要ありません。
4:
5: <!-- section: authoring -->
6: ## コンテンツの作成
7:
8: | API | 役割 |
9: | --- | --- |
10: | `Project::new(namespace)` | 配布物の安定した名前空間を検証する |
11: | `project.default_deck(name)` | 既定の配置先を設定する |
12: | `project.add(key, note)` | ノート、モデル、メディアをアトミックに収集する |
13: | `project.add_asset(media)` | 直接記述した HTML・CSS・スクリプトの明示的アセットを追加する |
14: | `Note::basic(front, back)` / `Note::cloze(text)` | 組み込みモデルを保持するノートを作る |
15: | `model.note().field(key, content)` | 不変モデルを保持する独自のノートを作る |
16: | `note.deck(name).tag(tag)` / `.tags(iterable)` | 追加前にノートを設定する |
17: | `NoteType::builder(key)...build()` | 不変モデルを検証して完成させる |
18: | `NoteType::from_bundle(path)` | bundle-v2 からモデルと、データを所有するアセットを読み込む |
19:
20: `Field::new(key).name(display)` と `Template::new(key).name(display)` は、識別情報と表示を分けます。テンプレートは、フィルター、条件セクション、ブラウザーテンプレートを含めてフィールドキーを参照します。`Field::required()` は内容が空でないことを検査し、`Field::sort()` は並べ替え用フィールドを選択します。`schema::GenerationRule::all` と `any` はフィールドキーを受け取ります。`builder.cloze_field(key)` は Cloze モデルを宣言します。
21:
22: `schema::FieldKey` と `TemplateKey` は別の型です。文字列リテラル、所有する文字列、借用する文字列、`Cow<str>`、借用・所有するキーを組み合わせて使えます。変換は元の値を保持し、キーの検証はスキーマ完成時に行います。テンプレートキーをフィールドキーとして暗黙に受け付けることはありません。
23:
24: <!-- section: content-and-media -->
25: ## コンテンツとメディア
26:
27: 通常の文字列はすべて `Content::text` になります。HTML には `Content::html` が必要です。`Content::sequence` は意味を持つ値を組み合わせ、ビルド時に描画します。`Media::file(path)` と `Media::bytes(bytes, mime)` はスナップショットを所有します。`with_limits` 版は読み取り前に `media::MediaLimits { max_bytes }` の上限を適用します。既定値はアセットごとに256 MiBです。`with_export_name(name)` は、同じスナップショットを共有する改名済みの値を返します。既存のクローンは名前を保持します。
28:
29: `media.image()` と `media.sound()` はリソースの依存関係を保持します。固定ファイル名は移植可能で、衝突しない名前である必要があります。明示的アセットは、静的に見える参照がなくても同梱されます。[メディア](/docs/media/)を参照してください。
30:
31: `Note::image_occlusion(media)` は `note::ImageOcclusionBuilder` を返します。`.mask(Mask::rect(key, x, y, width, height)).mode(mode).build()` は、デコード後の画像サイズ、矩形、一意の安定キーを検証します。`HideAllGuessOne` と `HideOneGuessOne` の両方に対応しています。[画像穴埋め](/docs/image-occlusion/)を参照してください。
32:
33: <!-- section: build-options -->
34: ## ビルドのオプション
35:
36: `project.build(BuildOptions::to(path))` は永続 APKG を公開します。`BuildOptions::temporary()` は所有権で寿命を管理する一時出力を返します。どちらも `.update_from(previous_apkg)`、`.inspect_limits(limits)`、`.update_policy(policy)` を受け付けます。基準パッケージなしでポリシーを指定すると設定エラーになります。setter の順番はこの規則に影響しません。
37:
38: `build::InspectLimits::default()` は有限の上限を設定します。公開フィールドは変更可能です。値はすべて `u64` で、0は無制限ではなく0を意味します。
39:
40: | フィールド | 既定値 |
41: | --- | --- |
42: | `max_archive_bytes` | 2 GiB |
43: | `max_entries` | 100,000 |
44: | `max_central_directory_bytes` | 16 MiB |
45: | `max_zip_entry_bytes` / `max_zip_total_bytes` | 1 GiB / 4 GiB |
46: | `max_meta_bytes` / `max_media_map_bytes` | 64 KiB / 16 MiB |
47: | `max_identity_bytes` | 64 MiB |
48: | `max_collection_bytes` / `max_media_bytes` | 512 MiB / 256 MiB |
49: | `max_decoded_total_bytes` / `max_zstd_window_bytes` | 4 GiB / 64 MiB |
50:
51: 上限は基準パッケージと候補の検査に独立して適用されます。検査に失敗すると、リソース、上限、観測量、取得可能な場合は関連エントリーを報告します。上限を増やすには、呼び出し側で明示的に指定します。メディアのインポートには、それより前の段階で別の上限を適用します。
52:
53: <!-- section: build-compare-and-output -->
54: ## ビルド、比較、出力
55:
56: `BuildOutput::artifact()` は、データを所有する `build::ApkgArtifact` への参照を返します。`BuildOutput::report()` は観測結果を返します。成果物のクローンは一時ファイルの生存期間を共有します。`persist_to` は永続所有者を返すか、公開状況と元の I/O エラーを持つ `build::PersistError` を返します。
57:
58: `project.compare(update::CompareOptions::against(path))` は、高リスクの検出事項によりポリシーが公開を阻止しても、完了した `ComparisonReport` を返します。`findings()`、`highest_risk()`、`policy()`、`diagnostics()`、`snapshot()` で内容を参照できます。`UpdatePolicy::default()` は High/Critical を拒否します。`.fail_on(level)` はしきい値を変更し、`.allow(RiskCode)` は登録済みのリスク分類全体を許可します。識別情報の証拠の欠落・破損などのハードエラーは許可できません。
59:
60: <!-- section: reports-and-errors -->
61: ## レポートとエラー
62:
63: `BuildReport::snapshot()` は `build::json::ReportSnapshot` を返します。これは成功・失敗やファイルの所有権を持たない観測結果です。`BuildOutput::snapshot()` と `BuildError::snapshot()` は、実際の結果とレポートを含む `build::json::BuildSnapshot` を返します。`update::json::ComparisonSnapshot` は、元の検出事項とポリシー評価を分離します。すべてのスナップショット DTO は `serde::Serialize` を実装し、ファイルを所有しません。拡張トレイトは不要です。
64:
65: スナップショットのパスフィールドは、Rust ではネイティブの `PathBuf` 値を保持します。JSON では、有効な Unicode なら文字列、それ以外は損失のないネイティブ表現です。UTF-8 でない Unix 名は `{"encoding":"unix_bytes","bytes":[...]}`、対になっていない UTF-16 サロゲートを含む Windows 名は `{"encoding":"windows_wide","units":[...]}` になります。成功時の成果物パスと失敗時の公開パスの両方に適用されます。元のプラットフォームで JSON のパスを復元するには、`build::json::PathSnapshot` としてデシリアライズし、`into_path_buf()` を呼び出します。別のプラットフォームのエンコード済みパスは拒否されます。エラーのネイティブパスを自分でシリアライズする際は、`PathSnapshot::new(path)` が同じ表現を提供します。
66:
67: エラーは操作と同じモジュールにあります。スキーマ・バンドルのエラーは `schema`、ノート追加・画像穴埋めのエラーは `note`、メディアのエラーは `media`、ビルド・永続化のエラーは `build`、比較・ポリシーのエラーは `update` です。各エラーは `kind()` と `code()` を提供し、`std::error::Error + Send + Sync + 'static` を実装して、実際の原因エラーを保持します。
68:
69: <!-- section: addition-context -->
70: ## 追加時のコンテキスト
71:
72: 追加に失敗してもプロジェクトは変わりません。構造化コンテキストには元のノート・モデルのキーと対象を記録し、必要に応じて競合やメディア使用の詳細を付けます。Rust では `AddError::context()` / `detail()` を通じて `note::{AddContext, AddTarget, AddDetail}` を取得できます。SDK では `AddError.details` が型付きの context/detail を提供します。Node のフィールドは camelCase で、深く凍結されています。Python は snake_case の TypedDict を使います。タグは挿入時のインデックスを保持します。フィールドの位置は、元のシーケンスインデックス（フィールド自体は null/None、ルートは []）と任意の UTF-8 バイト範囲を保持します。ビルド時の既定デッキのエラーはノート・モデルのキーを持たず、原因チェーンから確認できます。
73:
74: 型付き画像を追加する際は image/* MIME が必要です。音声参照には audio/* または video/* を受け付けます。他の種類は `NOTE.MEDIA_USAGE_INVALID` になります。コンストラクター自体は失敗せず、明示的アセットと直接記述した HTML には影響しません。検査はインポート時に保持した MIME を使い、再生の可否は保証しません。ビルド時の独立した MIME・拡張子検証も引き続き適用されます。対象と詳細の完全な対応表は[設計文書](https://github.com/morehardy/anki-forge/blob/main/docs/plans/2026-09-28-rust-api-validation-and-errors-design.md)を参照してください。
75:
76: <!-- section: review-once-publish-once -->
77: ## 一度確認した候補をそのまま公開する
78:
79: 候補の事前生成と保存を行う API は、公開 `0.3.1` パッケージに含まれています。
80:
103:
104: 準備処理では、上限付きの完全な検査と比較を実行します。`publish` までは保存先に公開しません。`publish` は同じ非公開候補を使い、基準パッケージとのパスの別名関係を再検査します。相対パスは準備呼び出し時に確定します。プロジェクトを編集しても候補は変わりません。レポートの所要時間には確認に費やした時間を含みません。未公開の所有者をドロップすると候補が削除されます。公開された一時出力は、通常どおり最後の成果物所有者の解放時に削除されます。JSON からの復元や、消費済み所有者での再試行はできません。ネイティブビルドは使用しないステージング用マニフェストを省略しますが、埋め込みの識別情報の証拠とメディア検証は保持します。内部のステージングツールには、引き続き完全なマニフェストとフィンガープリントを渡します。

47: 文字列 `es:hola` は、名前空間 `spanish` 内の明示的な安定ノートキーです。解答の言い方とは独立して、どのノートかを示します。後で “hello” を “hello; hi” に広げても、同じ ID を使えます。
48:
49: 論理的なノートごとに別の ID を使ってください。ソースに語彙項目の ID など永続的なキーがあるなら、そのキーを出発点にできます。編集予定の本文だけから識別情報を作ることは避けてください。
50:
51: 配布済みデッキの更新には、リリース履歴も必要です。前回配布時のオリジナルパッケージを保持し、<a href={sitePath('/ja/docs/updates/')}>文書化された更新手順</a>に従ってください。
52:
53: <span id="grow-from-one-note" data-section-alias="grow-from-one-note"></span>
54:
55: {/* section: grow-from-one-note */}
56: ## 1件のノートから広げる
57:
58: 別の挨拶には、新しい Basic ノートを作り、新しいキーで追加します。文中の単語を穴埋めにするなら、<a href={sitePath('/ja/examples/#cloze')}>Cloze ノート</a>を使います。さらに表現豊かなカードには、プロジェクト API でフィールドとテンプレートを定義し、画像や音声をノートと一緒に同梱できます。
