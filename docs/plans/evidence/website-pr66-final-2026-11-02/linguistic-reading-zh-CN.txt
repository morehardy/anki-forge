1: # Anki Forge 与 genanki
2:
3: 如果正在设计可重复的发布流程，需要拥有所有权的媒体、结构化诊断，以及发布更新前的比较与策略检查，可以考虑 Anki Forge。如果已有 genanki 的 Python 脚本、模板和媒体满足需求，迁移成本高于收益，则应保留经过验证的流程。
4:
5: | 决策点 | Anki Forge | genanki |
6: | --- | --- | --- |
7: | 编写语言 | Rust 核心；Rust、Python 和 Node / TypeScript 接口 | Python |
8: | 共同基础能力 | Basic、Cloze、自定义模板、媒体与离线 APKG 生成 | Basic、Cloze、自定义模板、媒体与离线 APKG 生成 |
9: | 身份 | 显式命名空间和笔记键；更新需保留原始 APKG | 可配置 GUID 和数字模型/牌组 ID；支持重新导入更新 |
10: | 发布前 | 比较发现项、风险策略和已检查的预备候选包 | 由自己的脚本和测试定义发布检查 |
11: | 媒体所有权 | 图片和音频对象持有不可变数据快照，克隆共享存储 | 脚本提供包媒体文件和引用 |
12: | 编程式图片遮挡 | 通过公开 API 使用带键矩形遮罩 | 按流程评估合适模型或扩展 |
13: | 运行成本 | 需要原生依赖；使用受支持平台和解释器 | 保留现有 Python 部署可能成本更低 |
14: | 迁移成本 | 显式验证旧身份映射、模板和导入 | 已正常工作的 genanki 流程无需迁移成本 |
15:
16: ## 同一个小任务
17:
18: 将三个 JSON 问题生成带图片和声音的牌组时，两种库都由 Python 解析 JSON 并编写笔记。genanki 需要选择模型和牌组 ID、设置字段值与 GUID 规则、将媒体文件加入包，再写出 APKG。Anki Forge 需要选择命名空间和持久业务键，将拥有所有权的媒体组合进笔记，构建 v1，再基于原始 v1 APKG 比较和预备 v2，最后发布。[完整 JSON 示例](../json-to-anki.md)提供 Rust、Python 和 TypeScript 实现及运行命令。
19:
20: ## 已有 genanki 牌组
21:
22: [genanki 支持自定义 GUID](https://github.com/kerrickstaley/genanki#note-guids)、媒体和重新导入更新。不能将稳定身份视为 Anki Forge 独有能力。默认 GUID 规则可能依赖字段；字段会变化时，应有意选择 GUID 规则。
23:
24: Anki Forge 不会自动恢复任意 genanki 数字 ID 或 GUID。没有单独验证的映射时，应将首次 Anki Forge 分发视为身份边界。此比较及成功 APKG 构建均不承诺无损迁移或保留全部复习历史。迁移已有牌组前阅读[迁移指南](../python/genanki-migration.md)。
25:
26: ## 历史性能证据
27:
28: 2026-10-08 的比较在 Apple M1 Pro 上测量 Rust Project API 与 genanki 0.13.1。每组 1,000 条 Basic 笔记时，五个实测 Rust 工作负载的导出耗时低 45.7–53.9%；部分媒体场景的峰值内存更高。[方法、原始结果与限制](https://github.com/morehardy/anki-forge/blob/bef4aeb653fc875f216614e73d8a617be039b9cf/benchmarks/results/20261008-latest-commit-genanki/report.md)。该实验未测量当前 Python 或 Node 宿主性能，也不保证这些 SDK 或其他工作负载获得相同加速。
29:
30: Anki Forge 维护者 · 2026-10-25 根据公开 Anki Forge 0.3.1 API、[genanki 文档](https://github.com/kerrickstaley/genanki)和归档测量复核。开始新任务前，查看[运行环境兼容性](../compatibility.md)并[选择开发语言](https://ankiforge.dev/docs/languages/)。

1: # 构建与输出保证
2:
3: `Project::build` 只在操作成功后返回 `BuildOutput`，并保证其中有 APKG 产物。失败时返回 `BuildError`，包含结构化 kind/code、观察结果、底层原因和实际发布事实。
4:
5: ## 临时与持久产物
6:
7: 显式选择所有权模型：
8:
9: | 请求 | 所有权 |
10: | --- | --- |
11: | `BuildOptions::to(path)` | 持久目标；句柄清理后仍保留 |
12: | `BuildOptions::temporary()` | 临时文件；随最后一个产物所有者删除 |
13: | `artifact.persist_to(path)` | 新的持久所有者；原所有者仍可使用 |
14:
15: 读取临时路径时，保持 `BuildOutput` 或克隆的产物存活。报告或 JSON 快照不会延长文件寿命。Rust 正常释放所有者；Node 提供 `artifact.close()` 以确定性释放。把路径复制到应用状态中不会创建所有者。
16:
17: Rust 产物句柄保留绝对路径，即使构建或 `persist_to` 使用相对目标。之后改变进程工作目录不会重定向从已有句柄进行的读取或复制。每个新 `persist_to` 目标均相对于调用时的目录解析。
18:
19: `BuildReport::snapshot()` 只有观察结果。`BuildOutput::snapshot()` 和 `BuildError::snapshot()` 还说明真实结果。成功快照中也可能有警告。不要从诊断严重程度、路径是否存在或报告是否包含比较发现项来推断结果。
20:
21: ## 基线与发布
22:
23: 更新时保留之前的原始分发 APKG 作为不可变基线，并选择独立输出目标。发布前检查基线证据和候选内容。策略拒绝不会替换输出。缺失或损坏的证据、检查预算耗尽均为硬失败。
24:
25: 发布通过原子替换 APKG 完成。这是单文件保证；写入应用自己的独立 JSON 报告属于另一次操作。普通构建不写额外身份文件：完整的带版本证据嵌入分发包。
26:
27: 发布后仍可能发生晚期错误，例如确认持久性时出错。因此错误快照记录 `PublicationSnapshot` 事实：`path`、`stage`（`not_published` 或 `published`）、`temporary`，以及持久性（`confirmed` 或 `unconfirmed`）。重试或声称没有写入文件前，应检查这些事实。`PersistError` 同样保留发布事实和实际 I/O 源。仅原子替换并不能证明崩溃后的持久性。
28:
29: 快照序列化保留原生路径，不访问文件系统。Unicode 路径仍为 JSON 字符串。非 UTF-8 Unix 路径使用 `{"encoding":"unix_bytes","bytes":[...]}`；含未配对 UTF-16 代理项的 Windows 路径使用 `{"encoding":"windows_wide","units":[...]}`。数组保存精确的原生字节或代码单元。成功产物路径、失败发布路径和绑定错误路径详情均使用此表示。它们描述路径，但不保留产物所有权。文件系统可能拒绝特定原生路径，但其发布失败事实仍可序列化。
30:
31: ## 检查限制
32:
33: 有限的归档大小、条目数量、展开大小、解码集合或媒体及 zstd 窗口预算，分别独立应用于基线与候选包。从 `InspectLimits::default()` 开始，确有需要时再有意提高相关限制。零不是无限制。这些计数器并非进程级内存或 CPU 沙箱；媒体导入另有更早执行的单资源预算。
34:
35: ## 并发工作
36:
37: Rust 构建借用不可变项目状态。拥有所有权的模型和媒体可跨项目共享。Node 绑定在调用 build 或 compare 时捕获项目快照，之后的添加不会改变该请求。保持产物所有者存活，直到全部读取者结束；另一个消费者仍需路径时关闭最后一个临时所有者，是应用的生命周期错误。
38:
39: 包检查不能证明所有客户端行为。请使用目标 Anki 版本和设置测试渲染、播放与更新导入。调度与 schema 更改限制见[更新](../updates.md)。
40:
41: <!-- section: prepared-publication-from-source -->
42: ## 准备候选包并在审阅后写入目标文件
43:
44: 预备发布已包含在公开 `0.3.1` 包中。
45:
46: `prepare_publication` 构建、检查并比较一个私有候选包；`publish` 使用同一文件。选项和相对目标在预备阶段绑定。项目编辑不会改变候选包。仅预备不会替换目标；释放或关闭未发布的所有者会移除候选包。
47:
48: 每次发布尝试都会消耗所有者，包括策略或 I/O 失败。重试或改变策略、目标需要重新预备。报告仍可读取，但不拥有文件。Node/Python 提供幂等 `close()`，以及原因是 `closed` 或 `consumed` 的不可用错误；发布开始后关闭不会取消它。耗时不包含等待审阅的时间。成功替换后仍可能发生晚期持久性失败，因此要检查实际发布事实。
49:
50: 完整操作见[示例](../updates.md#build-once-review-then-publish-from-source)，类型化错误和工作线程行为见各语言 API 参考。

1: # 核心概念
2:
3: ## Project 与笔记
4:
5: 一个 `Project` 表示一次具有稳定命名空间的发布。它可以把笔记放入多个 Anki 牌组：`default_deck` 提供默认目标，`Note::deck` 覆盖该目标。牌组是输出的去处，并非另一层内容编写、媒体或构建容器。
6:
7: `Note` 携带其模型和内容。`project.add(key, note)` 分配必填的稳定源记录键，并原子地收集依赖。重复键、未知字段、模型或媒体冲突会使操作失败，不会留下部分添加的状态。项目命名空间和记录键必须在编辑及源数据重新排序后保持不变。显示名称和文本不是身份键。
8:
9: ## 模型、字段与模板
10:
11: `NoteType::builder(key)` 收集声明；`.build()` 校验后返回可共享的不可变模型。`model.note()` 创建持有该模型的笔记。内置 Basic、Cloze 和图片遮挡笔记自带模型。
12:
13: 字段和模板有稳定键与可选的显示名称。编写模板时使用字段键，例如 `{{front}}`，即使 Anki 显示名称为 `正面`。模型完成时会校验并编译引用，包括条件区块、过滤器、Cloze 和浏览器模板。赋值也使用键，不会猜测键或回退到显示名称。
14:
15: ## 文本与 HTML
16:
17: 在 Basic、Cloze 和自定义笔记中，普通字符串始终表示 Text。Text 会转义 HTML；`Content::html` 用于有意加入标记。`{{c1::answer}}` 等 Cloze 语法在 Text 中保留，但这不会使嵌入 HTML 自动成为可信标记。`Content::sequence` 把文本、HTML、图片和声音组合成一个字段。
18:
19: 类型化的图片与声音内容会保留媒体依赖直至导出。添加内容前不要把媒体渲染成字符串，除非也为手写的 HTML、CSS 或脚本显式声明了该资源。
20:
21: ## 媒体所有权
22:
23: `Media` 持有媒体数据的不可变快照，并管理其生命周期；导出文件名由内容确定。只有在预算范围内完成读取与校验后，导入才会成功；之后源文件可以改变或消失。克隆共享存储，可用于多个项目。`with_export_name` 选择固定且可移植的文件名，不会改变已有克隆或内容节点。
24:
25: 类型化引用自动收集媒体。模型或项目上显式声明的资源，即使静态分析无法识别用途，也会被包含。库不会从任意 HTML 或脚本中自动发现文件内容。
26:
27: ## 构建与更新
28:
29: 成功构建返回保证包含 APKG 的输出对象。报告只包含观察结果；快照是 JSON 数据，不拥有文件。临时产物只有在至少一个产物所有者仍存在时才保持有效。
30:
31: 更新使用上一次原始分发 APKG 内嵌的完整证据。独立比较将发现项与发布策略分开。高风险发现项默认阻止更新；硬错误不能被放行。Anki 导入设置、本地编辑和卡片调度仍需客户端验证。参见[更新](../updates.md)和[构建保证](../build-guarantees.md)。

1: # 从 genanki 的概念迁移
2:
3: 还在选库？阅读 [Anki Forge 与 genanki](../anki-forge-vs-genanki.md)。
4:
5: AnkiForge 使用稳定数据键、已校验的不可变模型、拥有所有权的媒体快照以及显式构建和更新操作。这是一套新的内容编写模型，不模拟 genanki 对象，也不模拟已移除的 AnkiForge Deck/lockfile 接口。
6:
7: | genanki 概念 | AnkiForge 对应方式 |
8: | --- | --- |
9: | 带数字 ID 的 Model | `NoteType.builder(stable_key)...build()` |
10: | 字段名用作标识符 | 稳定 Field 键与独立显示名称 |
11: | 携带字段字符串的 Note | 持有模型的 `model.note().field(key, content)` |
12: | Deck 作为笔记容器 | 带默认牌组的 Project；可选笔记级 `.deck(name)` |
13: | Package 的媒体文件路径 | 拥有所有权的 `Media.file(path)` 值，经类型化内容自动收集 |
14: | 写入 Package | `project.build(BuildOptions.to(path))` |
15: | 从字段派生的默认 GUID，或自定义 GUID 规则 | 显式稳定命名空间和笔记键 |
16:
29:
30: 从持久业务标识符选择键。重命名显示名称或更改定义文本，不应改变这些键。除非导入器明确要求按内容寻址身份，否则不要散列当前字段内容。没有键的源数据，应在 SDK 外分配并持久保存键。
31:
32: 模板表达式使用 Field 键。显示名称可以独立翻译，库将键引用编译为 Anki 字段名。模型完成时就会拒绝缺失或冲突声明，之后才可添加笔记。添加笔记自动收集模型依赖，并拒绝同一模型键下的冲突定义。
33:
34: 字符串是纯文本；有意加入 HTML 时使用 `Content.html(...)`。通过 `media.image()`、`media.sound()` 和 `Content.sequence(...)` 组合内容。原路径被移除或编辑后，文件快照仍有效。原始 HTML、CSS 或脚本引用的依赖，必须在模型构建器上用 `.asset(media)` 或通过 `project.add_asset(media)` 显式声明。
35:

70: ## 名称、MIME 与预算
71:
72: 默认导出名称由内容决定，与源路径无关。需要固定文件名时，应在创建引用前使用 `with_export_name`。重命名某个克隆不会改变之前的克隆或内容节点。
73:

75:

77:
78: MIME 语法必须与可识别的内容一致。原生字节没有 64 KiB 的内联限制。默认导入预算为每个资源 256 MiB；`file_with_limits` 和 `bytes_with_limits` 在读取前接收 `MediaLimits { max_bytes }`。大快照可能写入临时存储，并在最后一个所有者消失后清理。快照所有权不保证在源文件同时被修改的导入过程中获得原子的文件系统视图。

103: ### 批量行为与预算
104:
105: Rust 使用 `Media::files(paths)`，Node 使用 `await Media.files(paths)`，Python 使用 `Media.files(paths)`，按输入顺序导入文件，每次调用最多四个工作线程。少于 16 个文件时串行运行。Rust 还提供 `files_with_limits`；Node 和 Python 接受与 `file` 相同的限制。限制按每个资源计算。若某项导入失败，调用会等待已启动的工作完成、释放此批次的快照，并返回输入顺序中的第一个错误。已有媒体所有者继续有效。Python 在导入期间释放 GIL；Node 在事件循环之外执行工作。单文件导入仍立即返回持有媒体数据快照的对象；调用方必须选择批量方法才能获得导入并发。

78:
79: JSON 快照路径使用导出的 `PathSnapshot` 类型。Unicode 路径为字符串；非 Unicode 原生路径使用 `{ encoding: "unix_bytes", bytes: number[] }` 或 `{ encoding: "windows_wide", units: number[] }`。数组保留精确的 Unix 字节或 Windows UTF-16 代码单元，适用于构建快照中的产物路径、失败发布路径及结构化错误路径详情。只在原平台解码路径；Unix 中 `Buffer.from(value.bytes)` 为 Node 文件系统函数保留字节路径。Node 内容编写方法仍接受字符串路径。

81: 相对媒体和模板包路径在调用读取时锚定；构建目标和基线在构建选项时锚定。POSIX 中，符号链接后接 `..` 保留文件系统遍历语义。`persistTo` 将相对目标锚定到原构建捕获的工作目录，包括克隆和持久化句柄。之后的工作目录变化不会重定向这些路径。

90:

46: | `max_decoded_total_bytes` / `max_zstd_window_bytes` | 4 GiB / 64 MiB |

48: 限制独立应用于基线和候选包检查。失败检查报告资源、限制、观察量以及可用的相关条目。提高限制是调用方的显式操作；媒体导入有自己的更早预算。

50: ## 构建、比较与输出
51:
52: `BuildOutput::artifact()` 返回拥有所有权的 `build::ApkgArtifact` 引用。`BuildOutput::report()` 返回观察结果。产物克隆共享临时文件寿命；`persist_to` 返回持久所有者，或返回带发布事实与底层 I/O 来源的 `build::PersistError`。
53:
54: `project.compare(update::CompareOptions::against(path))` 返回完成的 `ComparisonReport`，即使高风险发现项阻止其策略。它提供 `findings()`、`highest_risk()`、`policy()`、`diagnostics()` 和 `snapshot()`。`UpdatePolicy::default()` 阻止 High/Critical；`.fail_on(level)` 改变阈值，`.allow(RiskCode)` 接受整个已注册风险类别。它不能接受标识映射与修订信息缺失或损坏等硬错误。
55:
56: ## 报告与错误
57:
58: `BuildReport::snapshot()` 返回 `build::json::ReportSnapshot`，只有观察结果，没有成功/失败或文件所有权。`BuildOutput::snapshot()` 与 `BuildError::snapshot()` 返回 `build::json::BuildSnapshot`，包含实际结果和报告。`update::json::ComparisonSnapshot` 将原始发现项与策略评估分开。所有快照 DTO 实现 `serde::Serialize`，且不拥有文件。不需要扩展 trait。
59:
60: Rust 中的快照路径字段保留原生 `PathBuf` 值。JSON 对有效 Unicode 使用字符串，否则使用无损原生编码：非 UTF-8 Unix 名称为 `{"encoding":"unix_bytes","bytes":[...]}`，含未配对 UTF-16 代理项的 Windows 名称为 `{"encoding":"windows_wide","units":[...]}`。成功产物路径和失败发布路径均适用。在原平台恢复 JSON 路径时，反序列化为 `build::json::PathSnapshot`，再调用 `into_path_buf()`；来自不同平台的编码路径会被拒绝。自行序列化错误中的原生路径时，`PathSnapshot::new(path)` 提供相同表示。
61:
62: 错误与所属操作放在一起：schema 和模板包错误在 `schema`，添加/IO 错误在 `note`，媒体错误在 `media`，构建/持久化错误在 `build`，比较/策略错误在 `update`。它们均提供 `kind()` 和 `code()`，实现 `std::error::Error + Send + Sync + 'static`，并保留真实来源错误。
63:
64: ## 添加上下文
65:
66: 添加失败不会改变项目。结构化上下文记录原始笔记或模型键和目标，并可附带冲突或媒体用法详情。Rust 通过 `AddError::context()` / `detail()` 提供 `note::{AddContext, AddTarget, AddDetail}`；SDK 通过 `AddError.details` 提供类型化 context/detail。Node 字段使用 camelCase 且深度冻结；Python 使用 snake_case TypedDict。标签保留插入下标；字段位置保留原始序列下标（null/None 指字段，[] 指其根）以及可选 UTF-8 字节范围。构建产生的默认牌组错误不带笔记或模型键，仍可从来源链读取。
67:
68: 添加时，类型化图片要求 image/* MIME，声音引用接受 audio/* 或 video/*。其他类别产生 `NOTE.MEDIA_USAGE_INVALID`。构造函数保持不会失败；显式资源和原始 HTML 不受影响。检查使用导入时保留的 MIME，不认证播放能力。构建的独立 MIME/扩展名校验仍然适用。完整 target/detail 表见[设计](../plans/2026-09-28-rust-api-validation-and-errors-design.md)。

70: ## 审阅一次，发布一次
71:
72: 预备发布 API 已包含在公开 `0.3.1` 包中。
73:
74:
97:
98: 预备阶段执行完整的受限检查与比较。直到 `publish` 才发布目标；它使用同一私有候选包并复查基线别名。相对路径在预备调用时绑定。项目编辑不能改变候选包。报告耗时不含审阅等待。释放未发布所有者会清理它；已发布临时输出遵循通常的最后产物所有者清理规则。不能从 JSON 恢复所有者，也不能对已消耗所有者重试。原生构建省略未使用的暂存 manifest，但仍内嵌标识映射与修订信息，并保留媒体验证。内部暂存工具仍接收完整 manifest 和指纹。

69: 缺失或损坏的证据、命名空间不匹配、无效候选数据和检查限制都是硬错误，不是可放行的风险类别。分析无法完成时，比较返回错误及已完成的观察结果。对没有 `update_from` 的新建请求显式设置策略属于配置错误，与 setter 调用顺序无关。
70:
71: ## 证据与身份
72:
73: 包内包含 `ankiforge-identity.json`，格式为 `ankiforge-identity-v1`。它将模型或配置 ID、笔记 GUID、历史字段或模板槽位、卡片或遮罩序号、修订和媒体绑定到实际集合与载荷。Anki 重新导出不保留该证据，不能作为更新基线。缺失证据绝不会被静默重建。
74:
75: 显示名称和内容编辑保留身份键。内容未变时保留基线修订；内容改变时推进修订。字段或模板重排保留历史映射。退役身份继续保留，恢复相同键时可复用。笔记键不能移到另一模型，模型键也不能在普通与 Cloze 类型间改变。
76:
77: ## 客户端导入行为与发布检查
78:
79: APKG 是分发包，不是删除同步。省略笔记、字段、模板或遮罩，不会删除学习者已有数据。字段或模板 schema 和排序字段变化属于高风险，因为 Anki 合并与导入设置会影响行为。Schema 变化可能复制模型，或在笔记内容比较前更新目标笔记的时间戳。
80:
81: 在支持的客户端测试首次导入以及导入已有集合的更新。使用目标合并与笔记更新设置，检查字段、GUID、卡片集合、本地编辑和已有调度。仅稳定身份不保证较新本地编辑被覆盖，也不保证已删除的历史被恢复。
82:
83: 将候选包写到与归档基线不同的路径。审阅后分发被接受的包，并将它保留为下一次发布的证据。所有权和发布事实见[构建保证](../build-guarantees.md)。
84:
85: <a id="build-once-review-then-publish-from-source"></a>
86:
87: ## 构建一次，审阅后发布
88:
89: 此 API 已包含在公开 `0.3.1` 包中。
90:
91: 构建一次，检查报告，然后发布同一个候选文件。审阅后再运行一次普通构建会创建另一个候选包；预备发布使实际 APKG 始终与已审阅报告对应。
