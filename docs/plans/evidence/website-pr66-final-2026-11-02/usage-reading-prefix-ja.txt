「出力を確認してインポートする」のセクション

選んだプログラムは output/<language>/v2.apkg のパスを表示します。v1.apkg も一緒に保管してください。回答だけを変えた今回の編集では、comparison.json と review.json に RISK.NOTE_CHANGED が記録され、追加・削除されたノートはなく、policy.allows_publication: true になります。プログラムは公開前に、準備済み候補についてもポリシーを確認します。どちらかの版が出力先ディレクトリに存在する場合、そのディレクトリは再利用しません。

安定したノート ID で Anki デッキを更新する

すでに配布した Anki デッキに訂正や新しいカードを届けます。ノートの ID を安定させると、Anki Forge と Anki は既存のノートを新規ノートとして扱わずに識別できます。ただし、実際に何が更新されるかには、Anki のインポート設定や、それより新しいローカルでの編集も影響します。

プロジェクトの名前空間と、ノート・モデル・フィールド・テンプレートのキーは変更しないでください。新しいリリースは、完全なバージョン付き識別情報を含む、前回の配布時のオリジナル APKGを基準に作成します。そのパッケージを対応するソースのリビジョンと一緒に保管してください。

ポリシーと検査の上限
「ポリシーと検査の上限」のセクション

次の完全なプログラムでは、より厳しいしきい値を選び、比較と更新に同じ設定を使います。

[Rendered code/command: captured and separately bound in browser-tour.json]

デフォルトのポリシーは High と Critical の検出事項がある場合に公開を止めます。特定のカテゴリを確認したうえで、呼び出し側が意図的に UpdatePolicy::default().allow(RiskCode::NoteRemoved) を選ぶこともできます。この指定は、元のレベルと根拠を保持したまま、そのカテゴリの検出事項をすべて許容します。特定のノートだけを個別に承認する指定ではありません。該当する検出事項のない許容指定には警告が出ます。不明なリスクコードは拒否されます。比較で返されたコードをすべて自動的に許容しないでください。

識別情報の欠落や破損、名前空間の不一致、不正な候補データ、検査上限への抵触はエラーであり、許容指定できるリスクカテゴリではありません。分析を完了できない場合、比較はそれまでに得られた検査結果を含むエラーを返します。update_from のない新規作成に明示的なポリシーを指定すると、setter の呼び出し順にかかわらず設定エラーになります。

識別情報とその根拠
「識別情報とその根拠」のセクション

パッケージには ankiforge-identity-v1 形式の ankiforge-identity.json が含まれます。モデル／設定の ID、ノートの GUID、過去のフィールド／テンプレートのスロット、カード／マスクの通し番号、リビジョン、メディアを、実際のコレクションと格納データに結び付けます。Anki からの再エクスポートではこの情報が保持されないため、更新の基準には使えません。欠落した情報が暗黙に再構築されることもありません。

表示名や内容を編集しても、識別用のキーは保持されます。内容が変わらない場合は基準パッケージのリビジョンを維持し、変更した場合はリビジョンを進めます。フィールドやテンプレートを並べ替えても、過去の対応関係は保持されます。使われなくなった識別子も予約されたままなので、同じキーを復元すると再利用できます。ノートキーを別のモデルへ移すことはできず、モデルキーの種類を通常型と Cloze 型の間で変更することもできません。

クライアントのインポート動作と公開前の確認
「クライアントのインポート動作と公開前の確認」のセクション

APKG は配布用パッケージであり、削除を同期する仕組みではありません。ノート、フィールド、テンプレート、マスクを省いても、学習者の既存データは削除されません。フィールド／テンプレートのスキーマ変更と並べ替えフィールドの変更は、Anki のマージやインポートの設定が動作に影響するため、高リスクです。スキーマ変更によって、ノート内容の比較より先にモデルが複製されたり、対象ノートのタイムスタンプが更新されたりする場合があります。

サポートするクライアントで、初回インポートと既存コレクションへの更新をテストしてください。予定しているマージ設定とノート更新設定を使い、フィールド、GUID、カードの集合、ローカルでの編集、既存の学習スケジュールを確認します。識別情報が安定しているだけでは、新しいローカル編集の上書きや、削除された履歴の復元は保証されません。

候補は、保存済みの基準パッケージとは別のパスに書き出してください。確認を終えたら承認したパッケージを配布し、次回のリリースの根拠として保管します。ファイルの所有権と公開時の保証についてはビルドの保証を参照してください。

トラブルシューティング

失敗した操作の構造化された kind と code、原因チェーン、観測結果を使います。表示テキストは人向けであり、変わる可能性があります。操作そのものの失敗と、比較は完了したもののポリシーが公開を阻止した場合は、異なる結果です。

インストール
「インストール」のセクション
症状	確認すること
Rust がツールチェーンを拒否する	rustc --version を実行し、Rust 1.92 以降を使用します。cargo tree -i ankiforge でインストール済みのバージョンを確認します
Node がネイティブパッケージを読み込めない	node -p "process.platform + '/' + process.arch" と npm ls ankiforge を実行し、npm install --include=optional ankiforge@0.3.1 で再インストールします
Node がネイティブ側とラッパーの不一致を報告する	バージョンを揃えます。同じレジストリ版から再インストールするか、同じチェックアウトから両方を再ビルドします
Python が拡張を読み込めない	python -m pip show ankiforge と python -m pip debug --verbose を実行し、インタープリターと wheel の OS/CPU タグを確認します
Python がソース配布物を選択する	対応する wheel・インタープリターを選ぶか、コンパイラーを用意してソースからのビルドに従います

検証済みの環境、Node のセットアップ、Python のセットアップを参照してください。

「モデルとノート」のセクション
症状	修正方法
無効または空のキー	安定キーを明示的に指定します。表示名は別です
NOTE.KEY_DUPLICATE	論理的なソースレコードごとに一意のキーを1つ割り当てます
NOTE.FIELD_UNKNOWN	表示名ではなくフィールドキーで代入します
NOTE.FIELD_REQUIRED	追加前に required() を指定したフィールドを埋めます

HTML が文字として表示される	意図したマークアップに限って Content::html を使います
Cloze カードが生成されない	対応範囲1〜500の番号で {{c1::answer}} 構文を指定します

追加の失敗はアトミックです。ノート・モデルを修正して再試行してください。部分的に登録されたモデルやメディアを取り消す必要はありません。モデルビルダーは .build() で完成させてから独自のノートを作成します。

メディアとテンプレート
「メディアとテンプレート」のセクション
症状	修正方法
ファイルのインポートに失敗する	Media::file の時点で元ファイルを確認します。成功後の元ファイル削除は可能です
MIME と内容が一致しない	バイト列のコンストラクターに実際の MIME タイプを渡します
エクスポート名が競合する	一意で移植可能な名前を選びます。大文字小文字・Unicode 正規化だけの違いも競合します
直接記述した HTML・CSS・スクリプトのリソースが見つからない	モデルの asset またはプロジェクトの add_asset で宣言します
メディアのインポートが上限を超える	インポート前に MediaLimits.max_bytes を明示的に増やします
ビルド時の検査が上限を超える	その操作の該当する InspectLimits カウンターを調整します
バンドルの読み込みに失敗する	bundle-v2、明示的なキー、キーを参照するテンプレート、バンドル内のパスを使います
画像穴埋めの矩形が失敗する	デコード後の表示サイズ、有限の座標、一意のマスクキーを確認します

すべてのノートタイプで文字列の既定の扱いは同じです。メディアノードは依存関係を収集しますが、ファイル名を手書きしただけではバイト列はインポートされません。有効なパッケージでも、使用するコーデック・フォントについてクライアントでの再生確認が必要です。

更新と出力
「更新と出力」のセクション

完全な識別情報の証拠を含む、配布時のオリジナル APKG を基準に使います。Anki から再エクスポートしたパッケージにはその証拠が残りません。名前空間の不一致や証拠の破損は、更新ポリシーで許可できません。

完了した比較で allows_publication == false となる場合があります。特定のリスク分類を明示的に許可する前に、元の検出事項と証拠を確認してください。すべての結果を一括で許可しないでください。同じ判断を適用するには、実際の更新ビルドにも同じポリシーを渡します。新規作成だけの要求にポリシーを指定するとエラーになります。

一時パスが消えた場合は、すべての読み取り側が終わるまで出力・成果物の所有者を保持してください。レポートと JSON スナップショットは所有者ではありません。永続化に失敗した場合は、エラーの公開段階と耐久性を確認してください。保存先に公開した後でエラーが返ることがあります。出力の保証を参照してください。
