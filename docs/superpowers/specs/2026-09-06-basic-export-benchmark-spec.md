# Spec: Reproducible Basic export benchmarks for anki-forge and genanki

Date: 2026-09-06
Status: Implemented; reviewed revision 3
Reviewed: 2026-09-06 (data, measurement/acceptance, presentation)
Phase: Basic notes at 200, 500, 1,000, and 10,000 notes
Design baseline: anki-forge commit a5f8f10f45807b29698dbd0063a2ce27095ffcc3

## Problem Statement

Maintainers want evidence for the performance claims shown on the project README. Readers need to know how long a useful Anki export takes, how much memory the exporting application uses, and how large the resulting APKG is. Currently the repository has public API capability tests and APKG inspection/roundtrip oracles, but no reproducible comparative benchmark suite.

The first comparison is the anki-forge native Rust Supported Consumer Interface against genanki's Python API. It must cover Basic decks containing exactly 200, 500, 1,000, and 10,000 notes, with one card per note. Small decks make process startup and runtime initialization material to the result. Anki-forge's default checks, modern APKG format, and compression also make a narrow writer-only comparison insufficient to describe the default user experience.

There are no measured results supporting a speed or memory advantage yet. The suite must make favorable, unfavorable, noisy, and failed results visible without changing the benchmark to manufacture a win.

## Solution

Create an independently executable benchmark suite in the existing repository. Use a shared deterministic workload and thin subprocess adapters, with one external runner responsible for scheduling, timing, memory sampling, verification, and raw result collection. Initially enable only anki-forge Rust and genanki Python. Future Node and Python binding adapters reuse this protocol without changing the workload or measurement definitions.

The main measured boundary is a fresh adapter process reading a prepared workload, constructing notes through the library's public API, exporting a real APKG with default behavior, and exiting successfully. Artifact verification is outside that boundary. Full reports show all four sizes, fresh-process wall-time distributions, OS-reported single-process peak RSS, APKG sizes, correctness outcomes, and reproducibility metadata.

The suite provides separate smoke, full measurement, and offline report-generation entry points. README material is generated from eligible recorded results and contains a full four-size comparison, a clearly labeled 10,000-note summary, and a link to the complete methodology and raw data.

## User Stories

1. As a maintainer, I want to compare exactly 200, 500, 1,000, and 10,000 Basic notes, so that the initial scope reflects the deck sizes selected for this phase.
2. As a Rust consumer, I want the benchmark to use the Supported Consumer Interface, so that the result represents an application I could write with the Public Crate.
3. As a genanki user, I want the comparator to use normal public APIs and a reused Basic model, so that unnecessary adapter work does not misrepresent genanki.
4. As a maintainer, I want both implementations to read the same prepared data, so that input differences cannot determine the winner.
5. As a contributor, I want a fixed seed and a versioned workload recipe, so that I can reproduce the exact inputs independently.
6. As a reader, I want notes and cards counted separately, so that equal workload sizes correspond to equal useful output.
7. As a user of multilingual content, I want a characterized mix of Unicode and literal HTML-sensitive characters included, so that correct text handling remains part of the workload.
8. As a user exporting a small deck, I want startup, imports, parsing, and shutdown included in the main time, so that the number describes a complete invocation.
9. As a maintainer, I want default validation, identity derivation, and packaging behavior retained, so that performance claims apply to the documented default API.
10. As a reader, I want the output format and compression differences disclosed, so that I can interpret speed and size together.
11. As a user with limited memory, I want the memory metric and process scope stated explicitly, so that a process peak is not mistaken for a future binding's entire process tree.
12. As a benchmark author, I want memory collection separate from headline timing, so that monitoring does not distort small-task timing.
13. As a maintainer, I want repeated runs in a recorded balanced order, so that cache state and machine drift do not systematically favor one implementation.
14. As a reader, I want the median, dispersion, sample counts, and evidence limits, so that a small descriptive sample is not presented as proof of a stable advantage.
15. As a maintainer, I want every measured successful APKG checked against the expected workload, so that a fast but incomplete artifact cannot improve a score.
16. As an Anki user, I want representative outputs imported by a pinned Anki oracle before README claims are generated, so that package readability is independently evidenced.
17. As a contributor, I want failures, timeouts, interruptions, and missing measurements retained, so that unsuccessful attempts are not silently excluded.
18. As a maintainer, I want a short smoke command for CI, so that adapter and verification regressions are caught without running a performance competition on shared runners.
19. As a contributor, I want compilation and dependency setup outside measured runs, so that setup costs are not accidentally attributed to export.
20. As a release maintainer, I want benchmark dependencies and fixtures excluded from the Rust Distribution, so that this development tool does not change the Package Payload or consumer dependency graph.
21. As a contributor, I want temporary outputs and environments isolated and cleaned safely, so that repeated measurements do not pollute my checkout or reuse previous artifacts.
22. As a maintainer, I want raw records tied to source, dependency, executable, and fixture identities, so that a displayed number can be traced to its actual inputs.
23. As a contributor, I want dirty-checkout measurements marked as exploratory, so that an uncommitted change is not presented as a reproducible release result.
24. As a documentation author, I want reports and charts generated from recorded data without rerunning benchmarks, so that presentation cannot drift away from the evidence.
25. As a reader, I want every selected scale shown, including scales where anki-forge is slower, so that the README does not select only favorable cases.
26. As a maintainer, I want the 10,000-note summary selected before measurements, so that the showcase case is not chosen after observing the winner.
27. As a future binding contributor, I want to add an adapter using the same subprocess contract, so that Node and Python comparisons do not require a second harness.
28. As a maintainer, I want missing Anki-oracle evidence to produce a clearly marked draft report, so that local exploration can continue without publishing unverified claims.
29. As a reviewer, I want tests to exercise observable runner and artifact behavior, so that internal refactoring does not invalidate the benchmark contract.
30. As a maintainer, I want the baseline to be useful even when no advantage is found, so that it guides later optimization without conflating measurement with implementation changes.

## Implementation Decisions

1. **Repository and distribution boundary.** Keep the suite in a dedicated top-level benchmarks directory in this repository. It is a development tool, not a new published product. The Rust adapter is a private binary crate with publication disabled, an explicit independent Cargo workspace, a committed lockfile, and a local dependency on the Public Crate. Use the repository's Supported Rust Baseline and only default production features. Do not add the adapter to the root workspace's ordinary members or default members. Benchmark dependencies, environments, generated inputs, APKGs, and upstream oracle sources remain outside the Rust Distribution and Package Payload.

2. **Responsibilities and extensibility.** Separate the workload generator, adapter registry, external runner, artifact verifier, and offline reporter. The only execution contract the runner requires is a versioned adapter command accepting an input document and output destination and producing one APKG. Adapters also expose preparation-time identity/capability metadata. Version 1 supports only the Basic scenario; additional adapter entries can declare the same capability later. Avoid dispatching measurement or validation rules on implementation names. No plugin service, RPC server, or general benchmark framework is required.

3. **Initial comparison matrix.** Enable exactly the following eight cells. Keep numeric note counts in raw data and use consistent display labels.

   | Case | Notes | Cards | Populated decks | Used note types | Fields per note | Packaged media |
   | --- | ---: | ---: | ---: | ---: | ---: | ---: |
   | Basic 200 | 200 | 200 | 1 | 1 | 2 | 0 |
   | Basic 500 | 500 | 500 | 1 | 1 | 2 | 0 |
   | Basic 1K | 1,000 | 1,000 | 1 | 1 | 2 | 0 |
   | Basic 10K | 10,000 | 10,000 | 1 | 1 | 2 | 0 |

   Run each case with `anki-forge/rust` and `genanki/python`. Here Python identifies genanki's implementation language; it does not mean the anki-forge Python binding is included.

4. **Shared workload contract and freezing.** Define a benchmark-owned input schema/version independent of production contracts. Inputs contain the case identity, seed, deck name, numeric note count, and ordered records with a fixture identifier and plain-text Front/Back. Fixture identifiers are not supplied as stable IDs or GUIDs. The expected manifest contains exact counts, content digests, input byte sizes, and expected standard Basic question/answer template text. Both adapters read the same byte-identical UTF-8 document, without prebuilt IR, rows, cached GUIDs, or privately pre-escaped inputs. Freeze the generator recipe, phrase pools, serialization, and four fixture digests before timed measurements. Verify their identity before and after the run. Changing content after inspecting performance creates a separately versioned experiment, not a replacement baseline.

5. **Explicitly synthetic data profile.** Name the profile `basic-mixed-text-v1`: it is one synthetic corpus, not an observed distribution of real decks. Use seed 20260906 to generate 10,000 records and take ordered prefixes for the smaller cases. Each Front begins with a unique record marker. Freeze project-owned phrase pools and a deterministic selection algorithm, with golden fixture digests across supported generator hosts; avoid unordered iteration and implicit PRNG changes. Normalize source pools to NFC before freezing, use LF and UTF-8 without BOM, and prohibit NUL, the Anki field separator, and other control characters in fields. Artifact verification must not add Unicode normalization or trim text to hide changes.

   Preserve the chosen Front length target of 40–100 code points and Back target of 120–300, including the marker. Each block of 20 records contains 10 English, 8 mixed Chinese/English, and 2 mixed records with literal HTML-sensitive characters. Include both tag-shaped text intended to display literally and entity-shaped text to test decoding exactly once. Fields are nonempty; no tags, media, active HTML, cloze markers, custom templates, or scheduling history are included.

   Report actual per-case field code-point/UTF-8 byte distributions, language/escaping counts, pool provenance, and a compressed-input/raw-input ratio using a fixed, recorded compressor/version/level as a repetition diagnostic. This diagnostic is not a score and does not modify inputs. Text length and repetition affect memory/compression; any result applies to this named corpus. Real datasets, different lengths, and additional seeds remain future profiles, keeping phase one at eight cells.

6. **Rust adapter.** Use the documented Deck facade and Basic note builder, followed by the default APKG export and successful BuildReport check. The Deck facade accepts HTML field strings; escape the shared plain-text fields in the timed Rust adapter through a pinned HTML escaping library, just as the genanki adapter does. Preserve default identity derivation, inspection, resource budgets, and report construction. Preparation confirmed that assuming automatic escaping by the Deck facade changes the visible text and is incorrect. Do not call normalization or writer internals, enable the Internal Tools Interface, disable checks, or change SQLite/compression settings in the measured adapter. The facade's own conversions and copying remain part of the cost. Resolve and build the release executable before the run, then invoke that executable directly. Do not invoke Cargo inside a measured sample.

7. **Genanki adapter.** Initially pin the published genanki 0.13.1 release and all of its transitive dependencies in an isolated CPython environment. Use its public Deck, Note, reusable built-in Basic model, Package, and file-export APIs. Construct one deck and reuse one model for all notes. The required deterministic deck identifier is a recorded constant in the workload configuration. Keep default GUID derivation and packaging behavior. Escape the shared plain-text fields through normal Python HTML escaping inside the measured invocation. Do not prebuild model requirements, cards, GUIDs, or database content in a parent process, patch genanki, or alter its compression behavior. Record the installed package version and source/artifact identity instead of using a floating branch.

8. **Default-output comparison.** The benchmark compares default public-API workflows that produce the same Basic learning content. It does not claim byte-identical output, identical styling, or an isolated comparison of programming-language execution speed. Both stock models use the same Basic front/back template behavior, but default CSS, model display names, field presentation metadata, internal identifiers, timestamps, scheduling defaults, and anki-forge identity metadata can differ. Record observed package versions, canonical collection entry names, and compression policies. Size reductions must be described as a default-output result with these differences disclosed. Do not convert or recompress one implementation's package to influence the primary comparison.

9. **Fresh-process time boundary.** Name the metric "fresh-process export wall time, including startup and input parsing." Start a monotonic high-resolution clock immediately before direct adapter launch and stop at adapter exit. The protocol requires the adapter to wait for its work and descendants before returning; check containment outside the timer and invalidate attempts that leave work running. Do not quantize short timings by extending them to a periodic process-discovery tick. Include startup, Python imports, input reading/parsing, object/model construction, default identity/checks, serialization, compression, writes, library cleanup, and shutdown. Exclude external preparation, verification, import, reporting, and cleanup. Use no shell, Cargo, or dependency-resolving launcher inside an attempt. Drain bounded diagnostics consistently; neither adapter dumps the full fixture or BuildReport to stdout.

   Record clock resolution and test wait/launch behavior with small helpers. Do not subtract Python startup, an empty-loop estimate, or unrelated overhead. Closed outputs are required, without a special fsync guarantee. BuildReport duration is a different metric. Startup-dominated results are valid under this explicit label and must not be advertised as isolated writer throughput.

10. **Phases and balanced schedule.** The order is preparation/preflight, timing warmups, the complete timing pass, memory warmups, the memory pass, then deferred raw/semantic and Anki verification. Preflight verifies a small real export from both implementations before any measurement warmups. Each pass has three warmups per cell, retained in raw data and excluded from reported metrics.

   Timing has ten rounds. Each round contains one adjacent two-implementation block for each of the four sizes, with shuffled size order. Precompute five Rust-first and five genanki-first blocks per size and shuffle their round assignments with a recorded schedule seed. This gives ten attempts per cell without running all repeats for one implementation/size consecutively. Memory uses five similarly interleaved rounds, with order balanced as closely as possible. Only one adapter runs at a time.

   Between measured attempts permit only lightweight exit/output-presence checks and raw-record bookkeeping. Do not decode, hash, inspect, import, or bulk-delete artifacts between samples: even untimed work can affect the next sample's caches and temperature. Defer those operations until both passes finish. Describe the regime as fresh processes after warmups with warmed, uncontrolled filesystem caches, not cold-storage or guaranteed-hot-cache performance. Keep AC/power mode consistent where applicable, avoid known concurrent heavy work, and record pre/post host state and interruptions. Do not disable default GC, clear OS caches, discard outliers, selectively retry, or extend only favorable cells.

11. **OS memory peak and future scopes.** Run five separate memory attempts per cell; their durations do not enter headline timing. Review and test the two initial adapters as single-process exporters, with native threads allowed. Their primary metric is OS-reported high-water RSS for the specific completed adapter process, identified as `single_process_peak_rss_os_v1`. Obtain per-attempt resource usage from the platform wait/resource-usage facility with one owner reaping each process. Do not use cumulative child usage, the wrapper's own RSS, Python-only tracing, or 5 ms polling as the primary peak. Normalize Linux KiB versus macOS bytes explicitly and record collector/platform identity.

   The collector must avoid attributing a large generator/supervisor's inherited pre-exec memory to the exporter. Use a minimal native collector or validated direct-spawn method as needed. Check large-parent/small-child and large-child-followed-by-small-child counterexamples. Unsupported or unreliable collection is unavailable, never zero. Record raw peak, units, metric ID, process scope, launch/collection method, and attempt identity. These are OS resident-memory peaks, not exact allocation counts or cross-OS equivalent values.

   A future subprocess-based binding cannot reuse this metric as a whole-tree peak. Adding it requires a separately versioned validated whole-tree collector and a fresh common baseline for every compared adapter. A sampled tree series can be a labeled diagnostic, but cannot be silently mixed with OS process peaks or support an exact memory-saving claim. Retain this collector extension point without implementing bindings or tree collection now.

12. **Retention and failure lifecycle.** Give every attempt private output/work/temporary directories on the same recorded filesystem, without earlier artifacts or staging. Keep all successful artifacts and dependency-created temporary files through deferred verification; do not bulk-clean between measurements. Preparation estimates storage from both implementations' preflight outputs, includes headroom, and records a budget. Insufficient storage stops with a partial result rather than asymmetric cleanup.

   Reserve timed attempt 1 from every cell for Anki validation. After both measurement passes, hash and verify all artifacts, import these selected exact bytes, persist evidence, then clean successful outputs and leaked temporary SQLite files. If Anki is unavailable, retain the selected artifacts within the documented budget for later verification. Explicit expiry/cleanup marks missing evidence; regenerating an APKG cannot retroactively verify an old timed artifact. Keep raw records and diagnostics even after cleanup.

   Apply a recorded 120-second timeout equally. On timeout/interruption terminate the whole process group/tree, mark the affected pass incomplete, and mark remaining attempts not-run instead of retrying until success. Continue unaffected cells; explicit user cancellation stops the remaining schedule. Timing requires all ten attempts and their checks to pass. Memory completeness is separate. Adapter failures or invalid artifacts in any pass prevent positive claims for that cell; a collector-only failure suppresses only memory. Required timing/artifact failures return a nonzero full-run result with durable partial evidence. Oracle absence and collector unavailability have explicit separate statuses.

13. **Physical and semantic verification.** After measurement, verify every successful artifact, including warmups, through two views of the same APKG boundary: benchmark-local read-only checks of the unmodified canonical SQLite rows, and semantic APKG inspection. Use the existing repository inspector for modern schemas. Its legacy path currently requires a modern `decks` table, so use a benchmark-local, read-only schema-11 semantic reader for legacy packages, checking original model/deck JSON, full fields, templates, and associations without upgrading or repackaging the measured artifact. Record which reader was used and the repository-inspector limitation; test both paths and retain the independent upstream Anki requirement. Reuse bounded decoding where available without adding a production public API. Read physical rows before any importer, normalization, or schema-upgrade process can repair/drop them. Exclude the modern archive's legacy compatibility placeholder from the actual collection. Reader incompatibility is a verifier error/unavailable state, not proof of an invalid competitor output.

   Raw checks require database integrity; exact note/card row counts; unique nonempty GUIDs and fixture Fronts; valid note-type/deck references; no orphan cards; one card per raw note primary key; ordinal zero; and exactly two stored field segments, retaining empty segments when counting. A GUID/ordinal map or inner join cannot prove physical counts because it can hide duplicates/orphans. Whitespace-only genanki tag storage is logically empty; normalize that representation rather than demanding identical serialized arrays. Require zero real packaged media and account for all archive payloads.

   Semantic checks require one populated benchmark deck, one used normal note type with ordered Front/Back fields, frozen standard Basic question/answer templates, exact expected field contents, and empty logical tags. Identify Basic by these semantics, not a forge-only stock marker or model name. Detect active markup in raw field HTML before decoding entities exactly once. Correctly escaped tag-shaped text must display literally; do not strip markup, repeatedly unescape, trim, or normalize observed Unicode to make output match. Preserve record multiplicity. Ignore only documented style/metadata differences and empty default decks. Save physical counts, semantic digest, bytes, artifact hash, and both check outcomes. BuildReport and projected inspection counts alone are insufficient.

14. **Independent Anki evidence.** After raw/semantic verification, import each retained timed-attempt-1 artifact into its own fresh collection with a pinned upstream Anki revision/version. Do not select by speed or replace a failed first sample. All other artifacts in the cell must pass raw checks and match expected semantic content. Reuse isolated roundtrip-oracle infrastructure, but add a benchmark-specific single-artifact mode; the existing two-import template scenario alone is insufficient. Identify the oracle executable, revision, and dependencies before measurement and keep its build/setup outside timing.

   Independently query every imported note/card and compare complete field content, counts, ordinal-zero cards, deck assignment, and media absence. Require no skipped/conflicting notes. Count imported/used entities rather than built-in catalogs. Render deterministic English, mixed-Unicode, and escaping records through Anki and verify literal question/answer content; an import exit code or correct counts alone does not pass. Record the exact artifact hash, oracle identity, import status, logical digest, and rendering evidence.

   Missing oracle prerequisites or selected artifacts is an explicit unverified state. Verified evidence remains valid after those exact artifacts are cleaned, but later regenerated bytes cannot substantiate the earlier run. Upstream Anki remains outside the Public Crate and normal CI.

15. **Descriptive statistics and advantage wording.** For a complete timing cell report the median, Q1/Q3 under a named linear-interpolation convention, min/max, and attempted/successful counts. Report the median/range of five successful OS RSS peaks separately. APKG size summaries use the ten timed artifacts only; other attempt sizes remain raw evidence. Retain integer nanoseconds/bytes and convert only for display.

   For a complete comparable pair, report the observed ratio of genanki median to Rust median and the millisecond difference calculated as genanki median minus Rust median. Positive differences mean time saved by Rust; negative differences mean additional time. Time reduction is that difference divided by the genanki median: a 1.25 ratio means 20% less time, not 25% less time. A ratio below one means the observed Rust median was slower. These are descriptive measurements of the named synthetic corpus, runtime versions, host, and invocation boundary. Phase one emits no bootstrap confidence interval, p-value, significance verdict, or p95 from this small single-session sample. IQR shows sample spread, not confidence, and its overlap is not a significance test. Do not average across scales, select best repeats, or summarize only the survivors of incomplete cells.

   One eligible run can produce a descriptive table. Optional generated speed-advantage wording is restricted to the preselected 10K case and requires one predeclared full confirmation run with identical source/input/runtime/host/settings and the same eight-cell matrix. Retain both runs separately. Both must show at least 5% time reduction and at least 1 ms absolute reduction; these are editorial materiality thresholds, not statistical significance. If confirmation disagrees/fails, retain both reports and omit the headline. Do not retry until confirmation is favorable or substitute another size as the headline.

16. **Immutable evidence manifest.** Version results independently from production contracts. Before timing persist spec revision, run/experiment identity, source commit/dirty state, Crate Version and Bundle Version, adapter/collector/verifier/reporter identities, executable hashes, fixture/profile and golden digests, input distributions, dependency locks, interpreter/genanki versions, compiler/toolchain/target/flags, and observable SQLite/compression versions. Record OS/kernel/architecture, CPU/cores, RAM, filesystem/storage, AC/power mode and available pre/post load/thermal indicators, UTC/monotonic times, clock resolution, both warmup sets and schedules/seeds, timeout/storage budgets, metric IDs/scopes/units, and Anki artifact/evidence identities.

   Required comparison identities cannot silently be unavailable; optional host indicators are explicitly unknown. Recheck source, executables, and fixture digests after verification to reject mid-run changes. A version string alone does not establish which binary ran. Capture a reproducibility allowlist, not arbitrary environment variables or credentials.

   Every attempt has an immutable ID and role (preflight, timing warmup, timing, memory warmup, memory, verification), scheduled order, actual timestamps, exit/outcome, metric availability, artifact hash, and verification state. Cells track measurement, physical/semantic validation, Anki evidence, and metric eligibility separately. Dirty/inconsistent provenance produces a retained exploratory draft. The reporter cannot upgrade missing evidence based on a later tool or regenerated artifact.

17. **Execution, CI, and full acceptance.** Provide preparation, smoke, full-run, independent-oracle completion, and offline-report operations. Preparation locks/resolves dependencies, builds release/verification tools, checks frozen inputs, and performs resource/host preflight. No measured attempt prepares dependencies. Ordinary smoke runs one 200-note export per implementation plus physical/semantic checks, with no performance thresholds. Behavioral tests verify generator/manifests for all four sizes, so a fixed-200 implementation cannot masquerade as complete support.

   Full implementation acceptance additionally exercises all eight real cells and the required evidence lifecycle; a 200-note smoke alone is insufficient. Each cell either validates completely or produces the specified tested failure state. A descriptive README baseline needs clean provenance and Anki evidence for each displayed numeric cell; winning is never an acceptance condition.

   Dedicated CI runs smoke and harness behavior without Anki or shared-runner speed assertions, preserving existing Release Gates. Full measurement remains manual on a fixed host. Initial tooling supports Linux x86_64 and macOS ARM64 without changing Rust Distribution Tier 1 commitments. CPython 3.11 remains the explicitly named initial comparator profile, matching repository tooling, with its exact patch and genanki dependencies pinned. This is not claimed as genanki's newest-runtime or best-possible performance. A newer interpreter defines a separate comparison profile.

18. **Presentation with explicit limits.** Generate Markdown, accessible SVG, and machine-readable summaries only from recorded evidence. The README's primary comparison is a four-row table with both implementations' absolute fresh-process times/IQR, observed median ratio, absolute difference, and status. Add the preselected 10K time/RSS/APKG summary with metric scopes and sample counts. Put runtime versions, the synthetic profile, startup/input-parsing inclusion, default checks, and output compression/format differences next to the numbers rather than only behind a link.

   Full reports may include grouped point plots with median/IQR on a linear time axis. A labeled logarithmic view may supplement this, but cannot be the only view or imply measured behavior between four scales. Do not require a double-log line chart, use truncated bars to amplify differences, interpolate failed cells, or round finite values to zero. Label IQR as spread and use shape/text as well as color.

   All four cases remain visible. Failed/incomplete/unverified cells show a reason and raw-evidence link, never zero/infinity or a missing row. Eligible cells can show verified descriptive numbers while unrelated failures remain visible. A ratio requires a complete comparable pair; RSS availability is independent of valid time/size. Globally dirty/incompatible experiments remain drafts. Do not merge different hosts, profiles, versions, binaries, or metric conventions. Descriptive tables and promotional wording have separate evidence requirements.

19. **Publication and storage boundary.** Ignore generated corpora, APKGs, environments, tools, and transient measurements by default. Commit selected compact manifests, raw records, fixture recipe/golden-hash evidence, physical/semantic/Anki summaries, and generated reports/charts. A confirmation retains and links both runs, including unfavorable results. Cleanup cannot precede the relevant verification, and selected artifacts remain until Anki evidence or explicit expiry. Reproducing an export is different from proving which historical bytes were verified.

   Snapshots are immutable in meaning; corrections receive a new revision and explanation. Offline rendering reproduces values without rerunning data generation or measurements. Report generation does not automatically edit/publish README. Normal review selects descriptive snapshots or eligible headlines. No production API/contract version change is introduced; core optimizations remain separate work.

20. **Evidence states.** Use separate per-cell/per-metric states, not one all-or-nothing publication flag.

   | Condition | Full report | README descriptive result | Advantage wording |
   | --- | --- | --- | --- |
   | Complete timing, clean provenance, physical/semantic checks and Anki import/render pass | All values and summaries | Verified time/size; RSS only if the complete matching metric is available | Only after the predeclared 10K confirmation rule |
   | Timeout, nonzero exit, missing output, interruption, incomplete timing | Attempts/reason; no survivor-only median | Keep the cell/status and all other eligible cells | None for that cell; no ratio against it |
   | Proven physical/content/template corruption | Invalid-artifact diagnostics | Invalid-artifact status, no score | None for that cell |
   | Incompatible verifier or missing Anki evidence | Unverified/unsupported draft with provisional values | Unverified status, not an invalid-competitor claim | None for that cell |
   | Collector-only failure or unmatched RSS scope/metric | Memory unavailable with reason | Eligible time/size remain; RSS unavailable, not zero | No memory-saving wording |
   | Dirty source, changed input/binary, incompatible provenance | Whole-run draft with reasons | Draft/status view, not validated comparative values | None |
   | Missing, inconsistent, or failed confirmation | Retain available run(s) | Eligible descriptive table remains useful | No promotional headline |

   Valid slower Rust results remain publishable descriptive evidence. No branch may discard a row because it is unfavorable.

## Testing Decisions

Good tests assert observable subprocess behavior, immutable evidence, raw/semantic APKG content, failure handling, and displayed claims. Do not assert private lowering steps, exact timings/RSS, SQL call counts, or expected speed ratios. The public adapter-process-to-APKG seam remains primary. Helper processes cover lifecycle/collector cases; real adapters and artifacts establish acceptance.

1. **Data:** Check four golden hashes, prefixes/counts, unique Fronts, frozen language/escaping distribution, code-point/byte statistics, and prohibited control/separator characters across supported generator hosts. Use hand-authored expectations for literal tags/entities and Unicode. Mutating input/binary identity mid-run must invalidate provenance.
2. **Adapters:** Exercise both real adapters at 200, 500, 1K, and 10K, beyond smoke. Check exact output, release/default-feature identity, locked comparator, model reuse in adapter design, and private-working-directory behavior. The Rust adapter uses only the Supported Consumer Interface and embedded defaults.
3. **Schedule/time:** Verify ten rounds, four adjacent case pairs each round, and five of each order per case. Check both warmup sets and the separate five-round memory schedule. Use phase events to prove no decode/hash/inspect/import/bulk cleanup runs during measurement passes or between samples. Post-exit containment is outside timing; leftover work invalidates an attempt. Test bounded diagnostic draining without tight timing assertions.
4. **Failure/retention:** Cover exits, missing output, timeout, cancellation, descendants, stale artifacts, storage exhaustion, and partial schedules. Selected first timed artifacts remain until Anki verification/expiry. Missing artifacts cannot be replaced to attach evidence retrospectively. Cleanup only removes run-owned files after their required verification. Collector absence and adapter failure are distinct; user cancellation stops further scheduling.
5. **OS RSS:** Verify platform unit conversion, per-attempt reaping, process scope, unavailable values, and rejection of unmatched metrics. A large child followed by a small one must not return cumulative maxima. A large parent spawning a small exporter must not inflate the latter through inherited pre-exec accounting. A tree-producing helper cannot pass as a comparable single-process peak. Use coarse behavioral checks rather than exact RSS values.
6. **Physical counterexamples:** Starting from valid packages, add a duplicate same-note/ordinal card, orphan card, dangling deck reference, third stored field segment, duplicate GUID/content, wrong template, or malformed canonical database. Raw checks must fail even if projected inspection looks correct. Whitespace-only genanki tags must remain valid. Do not change production behavior merely to make checker tests pass.
7. **Semantic checks:** Compare every record and association to expected values. Cover missing/extra data, modern compatibility placeholders, exactly-once escaping, literal entity text, active markup, and allowed metadata/CSS/model-name differences. Unsupported readers produce verification errors, not competitor-invalid verdicts.
8. **Anki evidence:** Use fresh pinned collections for selected attempt-1 artifacts; verify all imported fields/counts/assignments, no skipped/conflicting notes, and deterministic rendering of three text categories. Exit/count-only evidence cannot pass. Hashes must match retained bytes. Existing two-import template scenarios do not satisfy this contract without a benchmark mode.
9. **Statistics/display:** Use hand-computed records for medians, percentile convention, ranges, ratio direction, absolute differences, timing-only size aggregation, and missing values. Show IQR as spread with no confidence/significance claim. Exercise every evidence-state row, including one failed cell alongside seven eligible ones, unavailable RSS, and valid slower performance. Preserve all four sizes. Promotional text needs the predeclared confirmation and both materiality checks; failed confirmation cannot be swapped for another sample.
10. **Acceptance/isolation:** Run the actual eight-cell acceptance and verify offline regeneration. Existing Package Payload and packaged-consumer checks must pass without benchmark dependencies entering the Rust Distribution. Ordinary workspace tests do not execute full benchmarks. CI smoke requires neither Anki nor performance thresholds.
11. **Prior art:** Reuse public API smoke/capability tests, bounded decoding, semantic inspection, packaged-consumer isolation, and isolated upstream oracle infrastructure. Add benchmark-local physical checks for their known observational limits; a normalized observation is not a lossless database dump.

Acceptance requires the public eight-cell matrix to execute, correct physical/semantic verification, deterministic phase/schedule records, separate timing/OS-RSS passes, honest retention/failure states, tested report eligibility, and distribution isolation. A descriptive README baseline needs clean provenance and Anki evidence for each numeric cell. Confirmation is needed only for optional generated advantage wording. Failure to outperform genanki is not an implementation-test failure.

## Out of Scope

- Measuring the anki-forge Python binding, Node binding, low-level contract CLI, or alternate Rust public API routes in phase one.
- Cloze, reversed cards, custom note types/templates, image occlusion, tags as a workload dimension, media, multiple populated decks, update-safe rebuilds, comparison baselines, and identity lockfiles.
- 100,000-note or million-note workloads, limits/stress competitions, and changing the four selected sizes after observing results.
- Core writer optimization, production instrumentation, disabling default checks, changing compression, or modifying genanki to improve a score.
- Writer-only microbenchmarks, separate in-process steady-state timing, internal phase profiling, import performance, and durable-storage/fsync benchmarks.
- Claiming equivalent byte layout, CSS presentation, internal identity, historical scheduling order, or cross-language runtime-independent speed.
- Automatic desktop UI control, making upstream Anki part of the Public Crate, or requiring it for normal repository CI.
- Automated performance regression gates on shared CI, recurring benchmark scheduling, independent benchmark hosting, and a separate repository.
- Exact allocation/heap profiling, implementing future whole-tree memory collection now, and cross-platform RSS equivalence claims.
- Building future binding adapters now, launching a generic plugin framework, automatically publishing README changes, or promising that anki-forge will win.

## Further Notes

- The user approved an in-repository independent suite and the external adapter/verification boundary in the preceding discussion. This spec narrows the initial workload to the explicitly requested 200, 500, 1K, and 10K Basic cases and excludes anki-forge bindings from initial measurements.
- Domain vocabulary follows the repository's Rust Distribution context, especially Public Crate, Supported Consumer Interface, Internal Tools Interface, Self-Contained Distribution, Crate Version, Bundle Version, and Package Payload.

- The first practical vertical slice is frozen synthetic Basic inputs, the two public adapters, and physical/semantic smoke; then the full eight-cell schedule, OS RSS, deferred artifact/oracle evidence, and offline presentation. These are implementation steps within one spec, not separate user-facing phases or additional issue requests.
