# 媒体导出明显快于 genanki：目标、原型证据与实施方案

日期：2026-09-07。状态：完成隔离原型验证，生产源码未修改。

建议把“明显低于 genanki”具体化为：五个场景 × 100、200、500、1000 条的每个组合，端到端耗时中位数均不超过同轮 genanki 的 70%。这是待验收目标，不是当前已经实现的保证。无需增加 10K 档位。

本轮最终原型的 20 个组合中位数全部低于 genanki，其中 15 个达到上述目标。1000 条媒体场景仅降低约 14%–25%，500 条独立图片降低约 13%，仍需继续优化。同时，1000 条图片的原型峰值 RSS 达到约 167 MiB，明显高于 genanki 的 38 MiB。因此，应将已验证的结构优化改造成有内存上限的正式实现，不能直接交付当前原型。

## 2. 原型已经证明的优化方向

上一轮已证明逐媒体 CAS/staging 同步是主要退化原因，但仅省略临时文件的两处同步，1000 条独立图片仍约 2.4 秒，远高于 genanki。原方案见[媒体性能诊断](2026-09-07-media-performance-optimization-plan.md)。

这轮原型组合了以下改动：

1. 默认临时导出以构建拥有的不可变媒体快照代替输入副本、磁盘 CAS 和 staging 的物理媒体副本，保留逻辑清单。
2. 对这些不可变快照复用已验证的内容元数据；把来源变化检查合并进实际入库读取，避免重复打开、复制、哈希。
3. 四个工作线程批量注册媒体，并行准备快照、压缩媒体；复用压缩上下文，按原始顺序写 ZIP。最终结果使用新增的诊断批量注册入口，不能把它的收益归给现有逐项 `.add()` 循环。
4. 候选包完成检查后同步一次，并在同一文件系统内重命名到目标，消除最终 APKG 的额外复制。
5. 预生成内容固定的旧版 `collection.anki2` 升级提示数据库，避免每次导出重新建库、填充和 VACUUM。原实现与负载无关，20 个原始 APKG 中此条目相同；它不是用户笔记数据库，也不是缓存基准答案。
6. 私有诊断辅助库使用 macOS CommonCrypto 计算相同 SHA-1，已通过已知向量和分块输入测试。单独替换只带来约一成的媒体收益，不是主要解法；试用 ring 的另一组实验没有改善，已放弃。

原型仍保留独立 APKG inspection、最终发布同步及相同媒体/卡片内容。当前字节相等证明这些成功用例的输出兼容，不代表来源变化、错误处理、并发安全等生产语义已全部验证。

## 3. 下一步核心方案：一次构建读取、有界缓存、顺序打包

### 3.1 建立 `PreparedMedia` 内部边界

将“媒体是什么、如何验证”与“媒体暂存在哪里”分开。正式实现可用内部 `PreparedMedia` 表示构建已验证的内容：媒体绑定与导出文件名、原始大小、SHA-1/BLAKE3、类型信息，以及编码后内容的位置。位置可以是受控内存或一个顺序暂存文件中的偏移和长度。

注册入口继续保留当前的即时验证语义。新增批量注册 API 时，在计时范围内做相同检查，并保留输入顺序和每个 binding 的错误信息。注册后来源仍可能变化，因此构建时还需要验证实际读取的来源；不能宣称媒体从注册到导出总共只读一次。

构建阶段将来源读取、注册指纹核对、大小/双哈希计算、必要的类型探测、zstd 编码合并到一次流式处理。只有检查成功才产生 `PreparedMedia`。后续只复用本次构建拥有的不可变结果，外部可修改文件或调用者提供的 CAS 不能仅凭历史哈希跳过验证。多个名称绑定到同内容时保留各自的导出名称和诊断。

默认临时导出使用该路径；显式 `artifacts_dir` 或 `media_store_dir` 的持久存储、可检查目录及同步行为继续遵循原有契约。省略 staging 物理媒体副本涉及现有 staging-first 约定，应明确更新内部契约，并保留显式产物目录的行为。

### 3.2 用一个顺序暂存文件控制内存

当前原型预先保留全部原始媒体，再叠加整包指纹读取及编码缓冲区，导致图片 RSS 过高。其所谓 64 MiB 阈值在预加载后才检查，不能作为有效内存上限。

正式流水线使用按字节计费的预算及背压：分配/读取前申请预算，覆盖原始块、压缩输出、等待写入的结果和乱序缓存；2–4 个工作线程，队列满则暂停生产。建议先测 16/32 MiB 两个媒体缓冲预算；它们不等于整个进程 RSS 上限。

无法立即写入 ZIP 的编码结果追加到同一个顺序暂存文件，并保留偏移索引，避免重新产生上千个小文件。原始数据处理完即可释放。单个超大媒体也必须按块处理，不能绕过预算。保持稳定写入顺序，错误时丢弃候选结果、清理本次构建资源。

此设计同时减少文件系统操作和全量媒体常驻内存。它尚未实现和测量，暂存文件的读写也有成本，需以正式基准确认净收益。

### 3.3 消除整包读取和发布复制

当前 [APKG 包指纹](../../../anki_forge/src/writer_core/apkg.rs) 把整个文件读入 Vec 后再算 SHA-1。先改成固定缓冲区流式哈希，可以保持 APKG 字节/指纹不变，并降低峰值内存；这一步仍需重新读一遍包，不能保证单靠它就缩短耗时。

进一步使 ZIP 写入成为最终字节的顺序输出，写入时同步计算包指纹，才能真正消除这一遍读。现有 ZIP writer 有 seek/回填头部行为，直接给 Write 包装哈希会得到错误结果。需要使用已知长度/CRC 的预编码条目，或经过 Anki 兼容验证的数据描述符方案。该阶段可能改变 ZIP 容器字节及包指纹；必须明确更新对应期望值，并保持解码后的卡片/媒体身份和内容、稳定输出及 Anki 兼容性。

候选文件应创建在目标旁边，检查通过后保留最终同步并原子替换，避免 [发布函数](../../../anki_forge/src/build/artifact.rs) 的额外全包复制。不能假设任意工作目录与目标同盘；无目标路径的构建、跨卷情况、替换失败和旧文件保留均需明确处理。

### 3.4 降低固定成本，选择有效的并行粒度

将固定兼容数据库变为随包发布、可重复生成且与 schema/bundle 版本绑定的资源；生成测试要证明它包含正确的升级提示。继续保留随用户笔记变化的实际数据库生成。

批量注册和媒体编码复用有限工作线程与编码上下文。文字场景不创建空媒体线程池；共享媒体场景按真实文件数/字节量选择串行或并行，不能单凭笔记数开线程。不同机器的阈值需要实测。

原型中的 macOS SHA-1 后端只是可行性验证。正式选型保持哈希算法不变，测试分块、边界长度和支持的平台，不将 macOS 实测收益外推到所有架构，也不把本次 FFI 诊断代码直接作为库默认实现。

## 4. 差距与实施顺序

以最终同轮 genanki 为基准，尚未达标的单元仍需降低以下耗时，才达到 70% 比例线。这是差距计算，不是对下一步收益的承诺。

| 场景 | 条数 | 尚需减少约 ms |
| --- | ---: | ---: |
| 独立图片 | 500 | 38.0 |
| 独立图片 | 1000 | 59.4 |
| 独立音频 | 1000 | 31.6 |
| 混合独立媒体 | 1000 | 38.4 |
| 混合复用媒体 | 1000 | 7.6 |

图片仍有较大的包指纹与媒体准备成本，因此优先推进上述读取合并和顺序 writer。共享媒体只剩较小的绝对差距，固定数据库、模板/字段处理中的重复准备更值得测量。独立 inspection 是输出验证边界，不能为了达标直接删除。插桩父子阶段计时存在嵌套，工作线程累计时间也不是墙钟时间，不能将它们相加来预测收益。

建议按以下顺序提交正式改动，每步均有可回退边界：

1. 恢复并冻结五场景、四档媒体 benchmark/adapter；记录构建、依赖、输入和二进制身份。当前检出的 runner 已回到旧文字入口，不能直接用它宣称覆盖了媒体。
2. 实现临时/持久存储所有权策略、流式包指纹及固定兼容资源，保持现有 API 行为。
3. 引入内部 `PreparedMedia` 和有界顺序暂存文件，合并构建读取；保留显式 CAS/staging 路径及错误语义。
4. 增加批量注册入口和有限工作线程；分别报告逐项与批量入口，确保已有调用方式也获得基础流水线优化。
5. 改造最终字节顺序写入/指纹计算与候选包发布，补齐失败注入和兼容验证。
6. 跑完整矩阵，按未达标单元的剩余热点继续优化，不能用平均提速掩盖某个档位未达标。

## 5. 正式验收与证据边界

正式性能验收固定五场景 × 四档，每个适配器每单元 10 次计时、另做 5 次 RSS。同机、同输入、同构建配置，交错运行，保留中位数、IQR、包体积、真实媒体数及字节量。把进程启动、JSON 解析、媒体注册、构建、检查、发布和退出全部计入；不将媒体哈希/压缩等预处理挪到计时外。不将 RSS 采样耗时混入正常计时，也不使用进程内跨轮缓存。

性能主目标是每个单元 Rust 中位数 ≤ genanki 的 70%；边界或高波动单元需要复测，不能以三次样本推断稳定优势。内存建议以 1000 条图片峰值 RSS ≤ 64 MiB 作为首个工程目标，结合 16/32 MiB 媒体预算实测调整；这是尚未验证的目标，不能把当前 167 MiB 版本直接设为默认。

语义验收覆盖：注册后来源变化/消失/变空、每个 binding 的错误、同名冲突与同内容不同名、损坏外部 CAS、软硬链接别名、并发构建隔离、工作线程错误传播、预算和超大单文件、暂存写入失败、最终同步/替换失败后旧输出保留。内存预算测试必须观察真实流式行为，不能只测试一个配置数字。对异常路径使用可控 I/O 边界，不通过 sleep 制造竞态。

对保持编码方式的阶段要求完整 APKG 字节与包指纹一致；对调整 ZIP 编码的阶段验证确定性、实际字节指纹、独立包检查和固定版本 Anki 导入/字段/媒体/渲染。所有安全检查针对实际使用的字节执行。

本轮在 macOS arm64 上使用 release、system allocator、冻结媒体输入与 genanki 0.13.1。原型使用四个工作线程，会消耗更多并行 CPU；相较 genanki 的时间收益不意味着 CPU 总工作量同比减少。媒体是本地合成素材、缓存没有控制为冷缓存；三次重复用于筛选架构，尚不是正式发布性能结论。

本轮只修改隔离副本，原型含诊断用全局状态、macOS FFI、简化错误处理与暂存假设，不能直接合入。当前生产库与原基准记录的 192 个 crate/根 Cargo 文件一致，冻结媒体二进制身份也一致。完整紧凑证据、输入/源码身份与最终原型差异保存于本地 `benchmarks/results/20260907-faster-than-genanki-prototype/README.md`。
