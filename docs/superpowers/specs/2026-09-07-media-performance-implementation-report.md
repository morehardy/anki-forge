日期：2026-09-07。状态：实现、回归及本机基准已完成。

默认临时导出已采用有界媒体流水线。纯文字、图片、音频、混合独立媒体、混合复用媒体统一使用 **100、200、500、1000** 四档，主动执行和图表均不再包含 10K；历史记录保留。

最终同一版 release/system-allocator 二进制在两套素材的各 20 个组合中，中位数都比 genanki 低至少 30%。这是本机样本结果；图片接近阈值，不能把它写成任意机器、负载或每次调用的 30% 保证。该成绩使用新增的 `Deck::media().add_many()`，原逐项 `.add()` 的结果单列在下文。

## 最终结果

主表使用可从仓库源码重新生成的 v2 PNG/WAV 素材。每格每实现 10 个独立计时进程；RSS 另做 5 次，表内 RSS 为其中最高峰值。每个测量阶段前各做 3 次预热。

| 场景（1000 条） | Rust 中位数 ms | genanki 中位数 ms | 耗时降低 | Rust RSS 最高 MiB |
| --- | ---: | ---: | ---: | ---: |
| 纯文字 | 56.15 | 100.41 | 44.08% | 30.48 |
| 独立图片 | 198.13 | 285.01 | 30.48% | 40.34 |
| 独立音频 | 146.67 | 251.67 | 41.72% | 40.28 |
| 混合独立媒体 | 141.65 | 220.90 | 35.87% | 39.17 |
| 混合复用媒体 | 67.27 | 108.90 | 38.23% | 35.56 |

v2 全矩阵降低 30.48%–71.95%；原冻结 v1 素材降低 31.40%–70.85%。两套各 20/20 个组合通过预设门槛。1000 条图片最高 RSS 分别为 40.59 / 40.34 MiB，低于 64 MiB 工程目标；仍略高于 genanki 的约 35 MiB。

完整四档数据、IQR、原始样本、构建及源码身份分别见 [v1 报告](../../../benchmarks/results/20260907-media-export-pr/historical/v1/report.md)、[v2 报告](../../../benchmarks/results/20260907-media-export-pr/historical/v2/report.md)及对应的 `summary.json`、`manifest.json`、`verified.jsonl`。两套素材配方不同，不合并计算平均提速。

图片另做预先固定的 20 次交错复测，未挑选最好样本：

| 素材（1000 图片） | Rust ms | genanki ms | 耗时降低 | Rust IQR ms | genanki IQR ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| basic-image-unique-v1 | 202.89 | 290.32 | 30.11% | 37.96 | 34.03 |
| basic-image-unique-v2 | 203.05 | 298.00 | 31.86% | 27.56 | 57.57 |

复测同样达到门槛，但 v1 仅有约 0.11 个百分点余量，且波动较大。当前结论是图片耗时约降低三成，尚没有稳定超过该阈值的充分余量。前一版出现 29.94% 的复测，随后增加检查器解码上下文复用；前一版数据保存在证据目录的 `before-decoder-reuse/`，不混入最终统计。

## 已落地的改动

1. `PreparedMedia` 在构建时一次流式读取来源，合并注册指纹核对、SHA-1/BLAKE3、类型探测及 zstd 编码。注册阶段仍立即校验文件，因此不是从注册到导出总共只读一次。最多 4 个工作线程，通过容量为 1 的队列按确定顺序交给 ZIP。每个编码结果超过 512 KiB 即溢写，避免全量媒体常驻内存。输入模型、inline 数据、编码上下文和分配器容量不属于这项缓冲上限。
2. 内部顺序 ZIP writer 使用已知大小/CRC 写最终头部，支持 ZIP64，并在写入时计算真实包指纹。预编码媒体直接进入私有候选包，省去中间副本和整包重读。
3. 固定的 schema11 升级提示数据库作为随包资源复用，并用生成测试验证其字节。实际笔记数据库仍逐次生成。
4. 已检查的、构建独占的候选包在最终同步后重命名发布，跨文件系统保留复制后替换路径。`persist_to` 仍保留复制语义。
5. SHA-1 升级到 RustCrypto 0.11，保持算法和身份语义，使用运行时硬件选择与可移植回退。检查器复用 zstd 解码工作区，每帧重置 session，继续检查精确窗口及累计解码预算。
6. 增加原子批量注册 `deck.media().add_many(sources)`：最多 4 个线程、结果保持输入顺序，任何注册或名称冲突失败均不修改注册表。

临时构建保留逻辑 staging 清单及最终独立 inspection。显式 `artifacts_dir`、`media_store_dir`、`base_dir` 和 self-contained 模式保留原物理 CAS/staging 路径，本报告没有为这些持久化模式声明同样的性能收益。默认媒体包的 ZIP 条目顺序改变，因而包哈希可能改变；解码后的条目内容、Anki 身份与学习内容保持一致，同模式重复构建仍确定。设计依据见 [ADR 0018](../../adr/0018-build-owned-media-streaming.md)。

## 原调用方式与批量入口

下面是最终版在原 v1 素材上做的额外交错对照：每项 5 次计时、另做 3 次 RSS。批量与逐项 Rust 输出的 SHA-256 在每组对照中完全相同。所有解析、注册和文件读取均在计时范围内。

| 场景（1000 条） | 批量 Rust ms | 逐项 Rust ms | genanki ms | 逐项耗时降低 |
| --- | ---: | ---: | ---: | ---: |
| 纯文字 | 57.26 | 62.32 | 99.31 | 37.25% |
| 独立图片 | 201.55 | 248.06 | 298.81 | 16.98% |
| 独立音频 | 155.10 | 182.58 | 247.44 | 26.21% |
| 混合独立媒体 | 142.39 | 169.68 | 219.44 | 22.68% |
| 混合复用媒体 | 70.03 | 71.78 | 115.07 | 37.62% |

逐项注册已获得基础流水线优化，但独立图片、音频和混合独立媒体尚未达到 30% 目标。要获得主矩阵结果，应采用批量入口；不能把这部分并行收益归给原 `.add()` 循环。纯文字两种分支没有媒体工作，其小差异属于本次采样波动。

```rust
let references = deck.media().add_many(
    paths.into_iter().map(MediaSource::from_file),
)?;
```

## 验证与复现

- 完整工作区运行：996 项通过、25 项按仓库设置忽略。最终检查器改动后另跑 112 项库测试、14 项 APKG 资源限制测试、20 项检查器测试及 4 项媒体优化回归，全部通过。
- Python benchmark 行为测试 35 项通过；Clippy `-D warnings`、格式及空白检查、契约治理、包文件白名单检查通过。`cargo package --no-verify` 成功，未宣称跨平台发布包编译/CI 已完成。
- 两套最终矩阵各 840 次导出（含预热）全部通过原始 SQLite 行/模板、媒体文件名/数量/内容哈希及字段引用检查；共 80 份产物通过固定上游 Anki 的实际导入、全部字段/媒体字节及代表性渲染检查。逐项补测 135 次、图片复测 88 次（含 8 次预热）也全部通过原始产物校验。没有检查 GUI 显示或音频实际播放。
- 来源变更/消失/空文件、别名、同内容不同名、损坏 CAS、并发隔离、大文件溢写、来源失败后旧输出保留及重试、ZIP 写入错误和 ZIP64 均有回归覆盖。
- 本机 macOS arm64、Rust 1.92、release/system allocator、CPython 3.11/genanki 0.13.1；所有最终测量源码/可执行文件/依赖的前后身份一致。一次只运行一个导出器，停止编译后测量。文件缓存未控制为冷缓存；多线程提高墙钟速度不等于等比例减少 CPU 工作量。

```sh
python3 benchmarks/bench.py prepare --python python3.11 --with-anki
benchmarks/.venv/bin/python -m unittest discover -s benchmarks/tests -v
benchmarks/.venv/bin/python benchmarks/media_bench.py --name your-new-run
```

默认运行会生成经 golden hash 校验的 v2 PNG/WAV 素材。v1 复现需保留原素材并使用 `--inputs`；证据归档只包含其 JSON 与内容指纹，没有重新生成或替换旧素材。命令、适用平台和 oracle 准备方法见 [benchmark README](../../../benchmarks/README.md)。
