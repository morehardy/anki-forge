# 媒体导出性能诊断与优化方案

日期：2026-09-07。状态：根因已通过隔离实验确认；生产实现尚未修改。

针对后续“明显快于 genanki”的目标，新增[进一步优化方案与原型验证](2026-09-07-faster-than-genanki-plan.md)。本文保留最初的同步瓶颈诊断及其原始数据。

## 结论

主要瓶颈是每个媒体文件在 CAS 入库及 staging 复制后执行的两次串行 `sync_all()`。默认 `Deck::write_apkg()` 为本次构建创建临时工作区，CAS 与 staging 默认都位于其中，构建结束后删除，却承担逐文件同步等待。

1000 个独立媒体对应 1000 次 CAS 同步及 1000 次 staging 同步；混合复用场景只有 70 个注册文件，对应 140 次同步。它解释了原基准几乎按独立文件数量增长、图片与音频字节量相差约两倍而耗时接近的现象。

在本次插桩构建中，1000 张独立图片的两处同步各累计约 4.3 秒，合计约 8.6 秒；逐次同步占总耗时的比例中位数为 67.6%。独立音频对应 69.2%。省略这两处同步后，独立图片、独立音频和混合独立媒体耗时下降约 81%–85%，复用媒体下降约 74%，完整 APKG 字节保持一致。同步计时与净收益并不等价：净收益还受文件系统后续行为和运行波动影响，不能用两个不同统计量精确相减。

## 复现与证据

先使用原基准保留的 Rust 二进制复现三次 100 张负载：纯文字约 33 ms，独立图片/音频约 1.2 秒；后两者的用户态加内核态 CPU 时间仅约 0.3 秒，说明墙钟时间包含大量等待。

当前检出为 `3de0ed0`。当前基准 adapter/workload 源码已是旧文字版本，当前未包含上一轮完整媒体入口；但原媒体二进制的 SHA-256 与原始 manifest 完全一致，192 个生产库文件及根 Cargo 配置/lock 也与原基准记录完全一致。因此复现先使用冻结二进制，插桩在隔离复制的库中进行，未修改当前生产源码。正式优化前后跑分前，需要恢复并冻结五场景媒体 runner/adapter 和四档配置。

诊断构建保持 release、默认 system allocator、相同依赖版本和公开导出入口。除根 probe 包改名，依赖 lock 不变。所有计时点在隔离副本中；两个环境开关仅供诊断，不能作为正式产品接口。

原生 `sample` 无法检查当前进程，改用边界累计 `Instant` 计时、调用计数及单变量干预。最终 APKG 发布处的同步始终保留。每次启动独立进程，变体顺序以固定种子交错；输入哈希与 APKG 哈希在计时区间外核对。

- 53 次诊断导出全部成功，且 SHA-256 均与原基准中通过完整验证和 Anki 检查的对应 APKG 相同。
- 53 次由 1 次预热、12 次单变量隔离、30 次 1000 张确认、10 次 200/500 张覆盖检查组成。中间档仅单次覆盖，不作为性能中位数。
- 再次对五场景各一个 1000 张省略同步后的包执行固定版本上游 Anki 导入/渲染检查，5/5 通过。
- 所有诊断调用计数符合预期；最终 APKG 发布同步每次恰好执行一次。
- 本次是根因诊断，不替代每单元 10 次计时、5 次独立 RSS 采样的正式基准。没有声称对修改后的正式实现完成回归测试。

## 真实调用路径

| 阶段 | 源码位置 | 行为 |
| --- | --- | --- |
| 媒体注册 | `anki_forge/src/deck/media.rs:221` | 读取来源计算 SHA-1，图片读取尺寸 |
| 来源验证和快照 | `anki_forge/src/product/project.rs:2172` | 验证注册后的来源，再复制输入快照 |
| CAS 入库 | `anki_forge/src/authoring_core/media_io.rs:195` | 读取、双哈希、写入；223 行逐文件同步 |
| staging materialize | `anki_forge/src/writer_core/media.rs:121` | CAS 再读、校验、复制；166 行逐文件同步 |
| APKG 媒体写入 | `anki_forge/src/writer_core/apkg.rs:237` | 校验 CAS 后重新打开，逐文件 zstd 编码 |
| 包指纹 | `anki_forge/src/writer_core/apkg.rs:178` | 全包读取进内存，再计算 SHA-1 |
| 产物发布 | `anki_forge/src/product/project.rs:2804` | 调用原子替换，`build/artifact.rs:125` 同步最终 APKG |

CAS 是内容寻址存储；staging 是导出期间的检查目录。APKG 媒体来自 CAS，staging 副本不是压缩输入。当前契约 `contracts/semantics/build.md:17` 要求 staging-first，53 行说明 CAS 是来源。

两套实现都完整携带相同媒体，不存在 genanki 漏媒体造成的虚假优势。genanki 默认直接 ZIP_STORED 写媒体；Rust 默认包含更多来源检查、CAS/staging、zstd 和独立包检查。生产库路径不调用 ffmpeg，也没有音频转码；图片只读取尺寸。

## 优化实施顺序

### 第一步：只优化构建拥有的临时文件同步

在 `ArtifactWorkspace`/`BuildPipeline` 处根据文件的拥有关系推导内部持久化策略，分别传给 CAS 入库和 staging 写入。建议内部使用明确的 `Ephemeral` / `Persistent` 枚举，既有入口以 Persistent 为默认，保留对外函数和选项的兼容性。无需增加公开的“关闭安全检查”选项。

| artifacts_dir | media_store_dir | CAS 逐文件同步 | staging 逐文件同步 |
| --- | --- | --- | --- |
| 未指定 | 未指定 | 省略 | 省略 |
| 未指定 | 显式指定 | 保留 | 省略 |
| 显式指定 | 未指定 | 保留 | 保留 |
| 显式指定 | 显式指定 | 保留 | 保留 |

判断依据必须是本次构建是否拥有 TempDir 及选项来源，不能按路径是否在 `/tmp` 判断，也不能只看 artifacts_dir 是否缺省。调用者显式指定的 CAS 即使放在临时目录内，也按持久存储保守处理。输出路径有无不改变这张策略表。

保留 write/flush 错误处理、大小/BLAKE3/SHA-1 校验、同名冲突与路径保护、原子发布、独立 APKG inspection、最终 APKG 同步。低层 CAS/writer 的既有入口保留原同步行为。第一步只消除不需要持久留存的临时文件屏障，不取消 staging。

本次实验给出约 74%–85% 的媒体耗时下降空间；这是制定第一步验收目标的依据，正式收益仍以受所有权约束的实现和完整基准为准。

### 第二步：降低内存峰值，并量化剩余耗时

将 `apkg.rs:178` 的整包 `fs::read()` 改为固定缓冲区流式 SHA-1。它保持包指纹和 APKG 字节不变，并消除与包体大小相等的瞬时 Vec 分配。1000 张图片包约 61 MiB，因此值得独立实施和测量；当前还没有流式版本的 RSS 实测，不能直接承诺峰值减少 61 MiB。

对取消临时同步后的版本做不重叠的阶段计时及读取字节计数：来源验证/快照、CAS 入库、staging、压缩前校验、zstd、包指纹、inspection、最终发布和清理。先处理剩余占比最高的阶段，不将全部剩余耗时归咎于压缩。

### 第三步：依据剩余占比合并数据读取

优先评估两个明确重复读取点：

1. 来源验证与输入快照/CAS 入库合并为受控流，读取时计算注册指纹并写入私有快照，校验失败则丢弃；保留 `MEDIA.SOURCE_CHANGED` 及每个 binding 的诊断。
2. CAS 校验与 zstd 写入合并为一次读取，对实际压缩的字节同步计算大小/BLAKE3/SHA-1；只有全部通过才接受候选包。避免“验证一个版本、随后重新打开另一个版本”的窗口。

这些更改涉及错误时机及来源变化处理，需各自独立提交、回归和测量。不能简单相信旧哈希或关闭完整性检查来节省时间。

### 后续：单独设计是否省略 staging 物理副本

只有前面步骤后它仍占主要成本才推进。此项涉及 staging-first 契约和显式 artifacts_dir 的可检查产物，需要单独设计契约与兼容性；不纳入第一步。

## 测试与基准验收

第一步先建立四种所有权组合的真实媒体构建测试。通过局部可注入的持久化边界，验证默认临时路径不执行同步、显式 CAS/staging 路径继续执行同步；不可只测试某个 bool，也不可引入全局环境变量控制生产行为。

必须覆盖：

- 持久 CAS 或 staging 同步失败时报告失败，临时文件清理，旧输出保持；最终 APKG 同步失败和替换失败同样覆盖含媒体用例。
- 已有 CAS 损坏、尺寸/双哈希错误及并发同对象入库，保留 `authoring_core_media_io_tests.rs` 和 `writer_core_build_tests.rs` 的行为。
- 注册后源文件变化、变空、消失，以及共享来源逐 binding 诊断；输入目标碰撞、软硬链接别名不覆盖来源。
- 同内容不同名称的媒体仍按绑定导出，包从 CAS 读取，跨目录指纹稳定。
- 流合并时用确定性 I/O 边界替换/损坏输入，验证检查的是实际写入/压缩的字节；不要依赖 sleep 制造竞态。
- 同步策略与流式包指纹阶段的 APKG 字节和 package fingerprint 必须保持一致，所有默认校验及固定版本 Anki oracle 继续通过。

性能验收恢复并冻结五场景 × 100/200/500/1000：同机、同 allocator、同依赖、同输入、交错运行优化前后版本；每单元 10 次计时，另外 5 次 RSS，保留 IQR、包体积及独立媒体数量，不跑 10K。第一步建议目标为四类默认临时媒体场景耗时下降至少 70%，同时核查纯文字没有稳定回退；这是本机验收目标，不能成为跨机器 CI 的硬编码时间门槛。

## 更正上一轮说明及局限

上一轮报告中的“写入不包含 fsync”不准确：当前 Rust 内部 CAS 和 staging 均逐文件 `sync_all()`，最终 APKG 也先同步再替换目标。新方案保留最终发布同步。这里不据此宣称完整的掉电持久性保证；本次没有测试断电恢复。

原始报告和测量证据保持原样，本文件明确记录更正。现有工作区基准入口版本不一致的问题需在正式实施前处理；本次通过二进制哈希、192 个生产文件哈希和产物字节相等避免了混用版本。

本次仅新增诊断证据与方案，未将旁路开关或插桩写入生产源码。媒体是合成纹理/音调，缓存未控制为冷缓存；三次诊断重复只用于定位根因，不能作为正式发布性能保证。独立 Anki 检查为后端导入/渲染，不包含 GUI 显示或听音。

完整原始证据位于 `benchmarks/results/20260907-media-performance-diagnosis/`。完整隔离源码、二进制及选定 APKG 保留在 `benchmarks/.work/diagnose-media-20260907/`。证据目录包含插桩 patch、adapter/计数器源码、依赖清单、运行记录、哈希身份及五份 Anki 证据，未重复复制大文件。
