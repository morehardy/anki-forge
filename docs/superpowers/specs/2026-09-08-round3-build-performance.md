# 第三轮构建性能优化

日期：2026-09-08–09（上海时间）。基于用户已经合并的 main `e2d69b8`，实现结构比较、检查文本借用和有容量限制的 SQLite 内存源库。**本机 A/B 中，常用文本导出耗时减少约 5%–13%，文本比较构建减少约 11%–14%；已测场景峰值 RSS 的最大中位增幅为 29.1%。** 大输入采用文件库，5 万条文本和约 104 MiB 原始字段输入的内存基本持平。

全部 38 组 A/B 成品逐字节相同，并通过原始 SQLite/精确媒体、完整检查报告及 Anki 导入/渲染验证。公开接口、依赖和契约包版本不变。[完整证据与复跑说明](../../../benchmarks/results/20260908-round3-performance/README.md)；[完整统计](../../../benchmarks/results/20260908-round3-performance/summary.json)。

## 实现与取舍

### 直接比较语义结构

`writer_core/diff.rs` 对 JSON 借用树递归比较，过滤原有非语义键。对象按键匹配，数组保留顺序；数字按其 JSON 表示比较，保留 `1`/`1.0`、正负零的区别。左右 selector 索引通过有序迭代器合并，去掉第三个集合和重复树查找；缺失 selector、重复 selector 的最后一项覆盖、变更排序、缺失域、APKG 媒体引用跳过规则和证据合并均保持原语义。

### 检查时只复制需要保留的文本

`writer_core/inspect.rs` 从当前 SQLite 行借用 GUID、tags、flds、data。Summary 仍按原顺序验证全部列的类型和 UTF-8；完整检查直接从借用的 flds 拆分最终字段，避免先复制整份拼接文本。已拥有的身份 JSON 子树通过移出取得。最终检查仍读取实际 APKG，不使用构建前的预期数据代替成品证据。

### 有限制的 SQLite 内存源库

`writer_core/apkg.rs` 根据字段字节数加每条笔记 2 KiB 的普通开销预估选择源库；预计超过 64 MiB 时直接使用文件。内存库另以 `max_page_count=8192` 和 8 KiB 页面限制实际源库页面总量。若真实模型超出预估并触发 `SQLITE_FULL`，先释放内存连接，再用私有文件重建一次；其他错误直接传播。

两种存储方式使用相同 schema、事务、行写入与 `VACUUM INTO`，仍生成真实压实数据库并执行成品检查、同步与发布。文件源库使用唯一临时文件，由资源所有权确保先关闭连接再清理文件。[ADR 0020](../../adr/0020-bounded-memory-collection-source.md)

**64 MiB 仅限制内存源库的数据库页面，不是整次构建 RSS 的上限。** SQLite 元数据、日志、压实过程和输入模型另有开销。用户已允许适度额外内存；本轮主要用约 16–38 MiB 的增量换取较大的文本构建收益，没有新增公开调参接口。

## 基线和测量方法

- 拉取 main 后逐一核对第二轮封存的 198 个 crate 文件，全部相同。因此复用上次按这些源码构建的基线二进制；优化版以同一个适配器、Rust 1.92 release、锁定依赖、默认 features 和 System allocator 构建。源码和二进制 SHA-256 均记录在证据中。
- 本轮为 macOS ARM64、AC Power、Codex exec 会话。使用原生 collector 测量创建进程至退出的耗时及操作系统峰值 RSS；时间和 RSS 独立采样。媒体注册、输入读取、构建、检查及输出均在子进程计时范围内。
- 默认 29 组、比较 5 组、大输入 2 组：每格每版本 2 次预热 + 7 次耗时，独立 2 次预热 + 5 次 RSS。持久化 2 组：1 + 5 次耗时，独立 1 + 3 次 RSS。合计 **1192 次调用**。
- 场景随机排序，A/B 交错；逐次核对电源来源、退出状态、产物哈希和比较完成状态。5197 个唯一媒体源在测量前后核对哈希。持久化构建每格经过预热，但每次使用新 CAS 目录，不代表暖 CAS 命中。
- 对出现波动的媒体负载另做 2 次预热 + 11 次耗时的针对性复测，共 104 次调用；保留原矩阵和复测两组结果，不替换较慢样本。
- 表格均为中位数，变化为 `(优化后 / main - 1) × 100%`。最小/最大值、IQR、逐项样本和配对差值见统计及归档。后台负载、冷缓存和温度未隔离，小幅变化不作为普遍性能承诺。
- 未重新运行 genanki 矩阵，也没有把第二轮 Battery Power 的毫秒数与本次 AC Power 成绩相减。这里直接衡量相对最新 main 的改进。

## 正确性与门禁

- 38 组基线/优化版 APKG 完整逐字节相同；1192 个矩阵调用和 104 个复测调用全部绑定到已验收的输入、二进制和产物哈希。
- 独立 Python/SQLite/zstd 读取器验证原始数据库和精确媒体；每组同时用冻结旧 inspector 和当前 inspector 读取同一个成品，完整输出逐字节相同。38 个优化版成品均通过固定 Anki oracle 的导入/渲染验收；没有重新验证 GUI 交互或真实音频播放。
- SQLite 回归覆盖内存、强制容量回退、直接文件三条路径的压实字节等价；异常身份触发硬限额；非容量 SQL 错误、连接/临时文件清理、原事务回滚、旧成品保护和修复后的再次构建通过。
- 结构比较在默认配置及 `preserve_order` + `arbitrary_precision` 下通过数字/嵌套结构回归；另对三份真实报告的 0%/1%/100% 字段修改变体，执行 198 次完整 DiffReport 旧新对照。该独立程序与产物验证同时运行，其附带计时字段不用于性能结论。
- 完整本机 CI：Rust 工作区 **1036 通过、25 忽略**；另外 **23/23** 用户能力场景通过；Node 全部门禁通过；Python **107 项及 5 个 subtests** 通过。格式、clippy、契约治理、嵌入包重建字节比较、crate 文件清单和 rustdoc 警告检查通过。
- Node 安装测试在沙箱中因不能监听 `127.0.0.1` 中断，随后在获准的本机测试环境中从该门禁继续，所有后续检查通过。发布清单检查使用脚本已有的 `ANKI_FORGE_ALLOW_DIRTY_PACKAGE=1`，检查当前未提交代码。
- Linux/Windows/macOS Intel 的远端 CI、不同设备和并发构建的性能尚未在本轮测量；无平台范围外推。

## 被修正和未采用的方案

1. **字段字节单独预估容量不足。** 首次 5 万条文本筛选先写满内存限额后重建文件库，耗时 2310.74 → 2595.70 ms（+12.3%），RSS 579.33 → 652.20 MiB。补充每条笔记 2 KiB 的普通开销估计后，大输入正式 A/B 恢复持平。原筛选与正式矩阵属于不同采样段，不能将其绝对差值当作正式改进量。
2. **32 MiB 缓存的临时文件连接未采用。** 独立五场景筛选中，四倍长字段的三种 RSS 为基线 125.50、纯内存源库 170.28、临时文件连接 203.50 MiB；后者没有更好的综合收益。
3. 新增的异常路径测试最初使用了不满足内部模型 ID 前置条件的夹具，随后改成真实 SQL 唯一键失败。旧集成测试原本打开失败后遗留的固定源数据库；现改为检查私有源库清理、旧成品保护和可重试性，原有活连接事务回滚测试保留。失败日志均封存。

持久化媒体的暖 CAS 命中、源读取合并、压缩参数、阶段并行和 Cloze/多模板计划复用仍是后续候选；本轮没有用关闭同步、降低检查强度或无界并行获取速度。
