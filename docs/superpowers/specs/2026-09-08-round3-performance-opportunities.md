# 第二轮之后的构建性能优化机会

> 后续实现见[第三轮构建性能优化](2026-09-08-round3-build-performance.md)。本文保留筛选时的源码状态与结论；用户随后合并封存版本并允许适度额外内存，实际采用的容量策略和最终验收以实现报告为准。

日期：2026-09-08。对照[第二轮报告](2026-09-08-round2-optimization-genanki.md)、封存源码和历轮实验，补做两项隔离筛选。**仍有优化空间：结构比较已显示约 5%–6% 的比较构建提速；SQLite 内存临时库显示约 5%–11% 的文本构建提速，但大输入的内存代价明显。** 持久化路径、成品数据库解码和媒体压缩还有具体可验证的候选。

本次只新增研究文档和实验材料，生产实现没有改动。原型不等于已通过合并验收的实现。全部数据及复跑材料见[证据目录](../../../benchmarks/results/20260908-round3-opportunities/README.md)。

## 先区分目标和源码版本

当前 main 为 `c665271b0af9ec7badd2be57b516bf58afac15cd`，与第二轮最终封存版本有 **11 个源码文件不同**，包括 8 KiB 页面、检查字段移动及第一轮尚未合入的其他变化。本次在隔离目录恢复第二轮最终源码，逐一核对 **198 个 crate 文件**的哈希后才构建候选。以下源码链接指向证据中保存的该版本，避免用旧 main 行号解释新成绩。[差异清单](../../../benchmarks/results/20260908-round3-opportunities/workspace-source-differences.json)

如果目标仍是让默认 20 格全部比 genanki 少耗时至少 30%，独立音频 1,000 条需要从 228.59 ms 降到 `317.97 × 0.7 = 222.579 ms`，只差 **6.011 ms，即当前 Rust 时间的 2.63%**。这是对原报告数字的计算，不是新成绩。默认音频应优先测媒体准备和检查；下面的 diff 改进只作用于 `compare_to`，不能拿来填默认音频的缺口。

| 优先方向 | 适用构建 | 证据强度 | 判断 |
| --- | --- | --- | --- |
| 结构比较，随后去掉 selector 合并的重复查找 | 带基线比较 | 片段与端到端已筛选 | 最适合先做成可合并改动 |
| 暖 CAS 去掉将被丢弃副本的同步；合并持久化路径的重复读取 | 重复/持久化媒体构建 | 源码确认，暖场景未测 | 潜在收益大，需单独测实际命中率 |

## 1. 比较阶段：继续去掉“转成 JSON 才能比较”的工作

第二轮已经把索引改成借用，也用 `FilteredValue` 避免复制整个 Value 树。但每个同 selector 的条目仍执行两次 `serde_json::to_string`，然后比较两个完整字符串。万条文本原探针中，`compare.entry_payload` 为 86.42 ms，整个 diff 为 141.44 ms。[比较入口](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/diff.rs#L51)；[序列化函数](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/diff.rs#L147)

候选直接递归比较借用的 Value：对象过滤同样的非语义键后按键匹配，数组保留顺序，字符串直接比较；数字仍按原 canonical JSON 的表示比较，防止把 `1`/`1.0` 或 `-0.0`/`0.0` 合并。没有用哈希相等代替内容相等。

片段实验用 3 份真实检查报告，分别对 Back 观测字段做 0%/1%/100% 合成修改。它们用于验证比较器，不代表重新导出并修改了笔记 revision。以下是无字段变化时 `diff_reports` 本身的中位耗时：

| 输入报告 | 原版 ms | 结构比较 ms | 片段耗时减少 |
| --- | ---: | ---: | ---: |
| 1,000 条文本 | 6.75 | 4.06 | 39.8% |
| 10,000 条文本 | 101.25 | 63.32 | 37.5% |
| 1,000 条四倍长 Back | 29.38 | 6.06 | 79.4% |

全部 9 格的片段耗时减少 37.5%–85.0%，每次 DiffReport 与原版完整核对一致。默认与 `preserve_order` 另外各通过 4,800 组标量/嵌套差分检查。

随后用相同稳定身份、单独生成的基线进行端到端构建筛选。包含启动、读取输入、构建、检查、diff、输出和退出，**只改变比较器**：

| 比较构建 | 原版 ms | 候选 ms | 耗时减少 | 更快配对 / 7 | RSS 原版 → 候选 MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| text-1000 | 97.06 | 92.18 | 5.0% | 7/7 | 48.88 → 49.05 |
| text-10000 | 878.93 | 822.59 | 6.4% | 7/7 | 312.11 → 320.56 |
| long-back-quadruple-1000 | 497.70 | 472.03 | 5.2% | 7/7 | 215.12 → 208.05 |

每次均完成比较，A/B 的 APKG 哈希一致。**不能宣称它普遍减少 RSS**：万条文本本次中位数增加约 8.45 MiB；需要更充分的独立 RSS 和阶段分配复测。片段提速也不能直接当作整次构建提速。

下一项低复杂度候选是对已经建立的两棵 `BTreeMap` 做双迭代器有序合并。当前还建立第三个 `BTreeSet` 合并 selector，再对左右 map 各查一次；可省去这份集合及逐项查找。必须保留缺失 selector 的忽略、重复 selector 的最后一项覆盖、结果排序和缺失域行为。**这一项尚未包含在上述结果中。**

## 2. 持久化媒体：先优化真实文件流，再谈更多线程

原报告冷 CAS 图片 1,000 条中，同步区间并集占约 77.2%。它说明压缩器小调整很难改变十秒级总时间；这个占比也不能直接解释为可以省掉 77.2%。

有三处更具体的工作：

1. **已有 CAS 命中时，先确认是否需要同步新副本。** `ingest_media_read_source_to_cas` 现在写完临时对象，调用 `sync_all`，才在 `finalize_temp_object` 中检查最终对象是否存在。命中时验证已有对象并丢弃刚同步的临时对象。可先结束哈希并判断命中，验证已有内容；仅在需要发布新对象时同步临时对象。新对象的同步及竞争处理不能省略，外部 CAS 的“存在”也不等于其持久性和完整性已有保证。这项早先审计提过，但仍未被暖 CAS 数据验证。[代码](../../../benchmarks/results/20260908-round3-opportunities/source/authoring_core/media_io.rs#L223)
2. **把注册后复核与 `.anki-forge-media-input` 复制合成同一次源读取。** 当前持久路径先 `verify_registered_source()`，再重新打开文件复制，接下来又从输入副本写 CAS。可在复制或写入 CAS 的那一遍计算注册指纹，验收同一遍实际读取的字节，失败时丢弃私有候选。是否可以完全去掉输入副本，要按显式 `base_dir` 和调用方可观察的目录语义分别处理。[路径准备](../../../benchmarks/results/20260908-round3-opportunities/source/product/project.rs#L2249)
3. **把 APKG 阶段的 CAS 完整性验证与编码合成一遍。** 当前 `verify_cas_object_streaming` 完整读一次，返回路径后 `write_zstd_file_entry` 又打开并读取编码。可以向私有编码 payload 同步送入 SHA-1/BLAKE3/size 检查，完成验收后再接入 ZIP。保留实际输出字节的完整检查。它不会消除 CAS/staging 的同步成本；原报告媒体编码/写入约 393 ms，仅约占十秒冷构建的 4%。[两次读取](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/apkg.rs#L373)

另一个调度细节是 staging 每 16 个条目调用一次 `parallel_io::ordered`，每批创建并 join 线程，全部结束后才提交并开始下一批。四工作者下，1,000 个条目会经历 62 个完整批次及一个串行尾批，完整批次最多创建 186 个辅助线程。可换成构建内复用的工作者和总量有界的滑动窗口，在保留按序发布的同时减少批间等待。同步开销很大时，单纯省线程创建未必有可见收益。[staging 分批](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/staging.rs#L353)；[线程生命周期](../../../benchmarks/results/20260908-round3-opportunities/source/parallel_io.rs#L19)

最小实验应分开测新 CAS、100% 命中、1%/10% 新对象、同内容不同导出名、损坏已有对象；记录实际读取/写入字节、同步次数与区间并集。当前报告每次用新目录，不能据此承诺暖构建会快多少。

## 3. 成品检查：还有一个比 SQLite 行查询更大的未拆分区间

按第二轮原始样本逐个计算 `inspect.facts − inspect.sqlite − inspect.media`，再取中位数：

| 默认构建 | facts 中尚未细分的区间 |
| --- | ---: |
| 四倍长 Back × 1,000 | 116.08 ms |
| 短文本 × 10,000 | 49.16 ms |

它包括 collection 解码、写临时 SQLite 文件、归档及临时文件管理等，**不能全部称为解压 CPU 或磁盘 I/O**。已有读取缓冲是 64 KiB，所以“加一个普通 buffer”并不自动解决这里。[解码及临时库](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/inspect.rs#L333)；[现有有界读取](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/apkg_reader.rs#L157)

先把它拆为归档打开、解码 CPU/输入等待、sink 写入、关闭、清理，再比较有限大小的内存 sink 与文件 sink。sink 实验只用于定位；正式实现还需要从真实成品读取 SQLite，并完整保留 ZIP CRC、解码预算、窗口检查及数据库列验证。不能从“写库前已知内容”直接生成检查报告。

另一个明确的分配机会：Summary 投影仍先用 `row.get` 分配 `tags`、`flds`、`data` 三份 String，然后立即进入计数分支，将它们丢弃。完整投影又会从整份 `flds` String 分割并复制每个字段。可以借用当前 SQLite 行的文本，执行相同类型及 UTF-8 检查后，只为确实要保留的字段分配；Summary 不必为未保留的长字段分配副本。借用必须在下一次 `rows.next()` 前结束，错误类型/顺序仍需对照测试。[行解码](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/inspect.rs#L1600)

完整检查的身份 JSON 还通过 `value.get("anki_forge_identity").cloned()` 提取子树，可以研究从已拥有的 JSON 对象中移出该子树。它比整个检查链条小，适合并入上述局部所有权实验，不单独承诺显著提速。

## 4. SQLite 内存临时库：有效，但需要预算

单变量原型只把 `create_latest_collection_file` 的中间连接从文件库改为 `Connection::open_in_memory()`。仍使用 8 KiB 页面、原始 SQL/事务、`VACUUM INTO` 压实和最终成品检查/发布。它避免中间源库的文件存储工作，并没有去掉最终数据库。

| 默认构建 | 原版 ms | 内存临时库 ms | 耗时减少 | RSS 原版 → 候选 MiB |
| --- | ---: | ---: | ---: | ---: |
| text-1000 | 55.04 | 51.84 | 5.8% | 29.11 → 29.72 |
| text-10000 | 414.19 | 392.79 | 5.2% | 139.83 → 161.11 |
| long-back-quadruple-1000 | 289.07 | 256.07 | 11.4% | 125.45 → 167.50 |
| image-1000 | 195.12 | 192.32 | 1.4% | 39.66 → 39.53 |

四组 A/B 的成品字节相同，也与第二轮对应的正式产物哈希相同。前三组显示文本收益；图片的 1.4% 不作为明显改善。

万条及长字段分别增加约 **21.28 / 42.05 MiB**，所以不建议全量默认启用。下一步应比较有显式总内存预算的策略：小库使用内存，大库保持文件库。不能只按 note 数设置阈值；字段字节、模型宽度、cards 数、索引和并发构建都会影响 SQLite 内存。输入估算不是硬上限，超预算如何回退也要设计和测量。

这和已否定的 `journal_mode=MEMORY` 或“扩大 SQLite page cache”是不同候选；上述收益也不能与页面调整或结构比较直接相加。

## 5. 媒体压缩：实际帧几乎没有省空间，值得测更快参数

直接从冻结 APKG 统计数字媒体条目的 zstd 帧长度，与已验证的原媒体总字节比较，排除数据库、ZIP 头和 media map：

| 场景 | 原媒体 bytes | 编码帧 bytes | 净变化 |
| --- | ---: | ---: | ---: |
| 1,000 张合成 PNG | 64,152,000 | 64,161,000 | 增加 0.014% |
| 1,000 段合成 WAV | 32,044,000 | 31,890,183 | 减少 0.480% |

这证明这些冻结媒体的空间压缩收益很小，**不证明编码一定是媒体准备中的主要 CPU 热点**，也不能外推到真实语音、静音 WAV 或其他图片。[帧长度证据](../../../benchmarks/results/20260908-round3-opportunities/media-ratios.json)

可只调整媒体帧的压缩级别，分别测试默认、较快级别和更激进的快速参数，collection 的压缩独立处理。先测音频 1,000 条能否稳定减少那约 6 ms，同时记录媒体编码 CPU、包体积、RSS 和真实媒体压缩率。格式仍应是合法独立 zstd 帧；参数变更可能改变包字节，必须做新旧完整解码内容、确定性和 Anki 导入验证。

此前编码上下文复用已完成、媒体小帧实验也没有综合收益；这里提出的是针对已量化压缩比的参数筛选，尚未实测，不建议直接新增手写压缩器或按扩展名跳过压缩协议。

## 6. 并行化整个独立阶段，比继续加同类 worker 更有潜力

当前 writer 先完成 staging manifest，才开始 SQLite 生成，两者都读取已验证、已 reconcile 的不可变数据。可以让 manifest 序列化/哈希与 SQLite 创建并行，汇合后再组装 APKG。四倍长 Back 原探针中，manifest 约 94.11 ms、SQLite 约 284.75 ms；理想情况下能隐藏的上限受较短阶段限制，即约 94 ms，占该探针总时间约 13%。**实际收益必须扣除 CPU/磁盘竞争和调度成本。**[当前顺序的调用入口](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/build.rs#L97)；[SQLite 创建](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/apkg.rs#L440)

更深入的候选是把媒体验证/编码与仅依赖笔记、模型、GUID 的数据库构建重叠。目前媒体全部准备完后，才进入 reconcile/generate。需要先明确字段媒体引用和身份计划何时固定；不能在依赖未解析时提前写库。[阶段顺序](../../../benchmarks/results/20260908-round3-opportunities/source/product/project/pipeline.rs#L156)

音频原探针 SQLite 24.71 ms、媒体准备 66.40 ms；即使完全隐藏 SQLite，理想总时间改善也只有约 9.4%。图片类似约 8.3%。这些是同一探针上的结构性上限，不是速度承诺，不能与其他候选叠加。

并行原型应先限于默认临时构建：失败时 join 并清理所有任务，保留原诊断优先级，全部检查完成才发布。新线程也必须纳入整次构建的 CPU/缓冲预算。

## 7. Basic 之外：复用 Cloze 扫描和模板计划

目前正常成功的 Cloze 构建至少有几次相同内容扫描：初始卡数统计调用 `plan_cards`；staging 分别检查 `has_malformed_cloze` 和 `plan_cards(...).is_empty()`；写 SQLite 时再次 `plan_cards`。这些函数背后重复扫描 cloze 文本并构造 ordinal 集合。[卡片规划](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/card_plan.rs#L46)；[staging 校验](../../../benchmarks/results/20260908-round3-opportunities/source/writer_core/staging.rs#L774)

可以一次返回“有效 ordinal、是否畸形、模板位置”，在构建内相同不可变 note 的计数、校验、写库之间复用紧凑结果。完整成品检查仍读取实际 cards；不能把预期计划当成成品证据。多模板的默认生成规则还会反复解析模板并渲染整个 front，可单独评估每模型预编译模板计划、每 note 复用字段非空判断。

应补长 Cloze、重复/畸形 marker、1/10/50 模板、10/100 个字段、1/10/100 模型的负载，记录扫描次数和实际 cards 数。另补常驻进程的重复构建与多个同时构建；当前按独立进程测量的 20 格无法反映复用、线程竞争和 p95 延迟。这些方向尚无新性能成绩。

## 建议的实施顺序与验收

若优先服务现有比较构建，先将**结构比较**做成独立小改动，补异常报告、重复 selector、数字边界、完整观察模型和 RSS 复测；再单独验证有序索引合并。

若优先补齐默认 genanki 矩阵，先测**音频压缩参数和 Summary 行解码**，把目标设成音频 1,000 条稳定减少至少约 3% 的端到端耗时。SQLite 内存库保留为预算型候选；涉及内部阶段重排的并行方案放到这些局部实验之后。

若实际用户主要构建持久化媒体，则单独优先**暖 CAS 和重复读取**，用命中率与同步区间判断，不以默认临时模式的成绩代表它。

本轮端到端各格为 2 次预热 + 7 次交错耗时，独立 1 次预热 + 3 次 RSS；AC Power、缓存/温度未隔离，因此只视为候选筛选。采用前仍需正式时间/RSS 重测、原始 SQLite/媒体与报告等价、资源预算/失败清理/来源变化回归及跨平台门禁。没有重新运行完整 genanki 矩阵、完整 CI 或新的 Anki 导入会话；4 个默认场景的产物已匹配第二轮经过验收的完整 APKG 哈希。
