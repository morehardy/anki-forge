# Anki Forge website

The public homepage, examples, blog, and documentation. Built as a static Astro site with Starlight, Markdown/MDX, native CSS, and small TypeScript scripts for the animations and card demos. No application server is required.

## Develop locally

Use Node 24 or later and Rust 1.92 or later. From the repository root:

```sh
cd website
nvm use
npm ci
npm run dev
```

Open `http://127.0.0.1:4321/anki-forge/`. If you do not use nvm, select Node 24 with your preferred version manager before running npm.

The predev and prebuild commands compile and execute the Rust showcase. A first build needs network access for Cargo and npm dependencies. Later builds reuse the Cargo cache.

```sh
npm test
npm run check:ai
npm run check:docs
npm run check:examples
npm run check
npm run build
npm run check:machine
npm run check:schema
npm run check:site
npm run preview
```

Production preview runs at `http://127.0.0.1:4321/anki-forge/` by default. Starlight’s Pagefind search index is generated by the production build, so test search with `preview`.

Astro runs the preview server in the background. Use `npm run preview:stop` when finished.

## Machine-readable content

Each production build creates `llms.txt` and `zh-cn/llms.txt`, plus an
`index.md` next to every published documentation page and blog article. These
files are generated from the actual rendered HTML after Astro and Pagefind finish;
they are not source documents and should never be added under `public/docs/`,
`public/blog/`, their `zh-cn` equivalents, or as hand-maintained `llms.txt`
files. The generator rejects conflicts and cleans stale exports from these
reserved namespaces. Drafts must have the same draft status in both languages.

Curated topic IDs and group order live in `machine-content.config.mjs`; titles,
descriptions and URLs come from the registered pages and rendered content. Edit
localized labels and summaries in the message catalogs. Public versions,
installation commands and runtimes come from `../docs/ai-quickstart.json`. The
two indexes have a 24 KiB limit: shorten descriptions or reduce the curated
links if a build exceeds it. Source-build and historical-article links have
different purposes from the current published package documentation.

Use `npm run build` before `npm run preview`: the development server does not
generate these post-build resources. On the default base, for example, inspect
`http://127.0.0.1:4321/anki-forge/llms.txt` and
`http://127.0.0.1:4321/anki-forge/docs/quickstart/index.md`. `generate:machine`
can rerun the export against a complete existing `dist/`; rerun the build to
refresh the release manifest. `check:machine` checks actual HTML, exported code,
source fixtures, discovery links and local targets; `check:schema` checks the
HTML graphs and their independently maintained metadata. `check:gates` tests
deliberately damaged copies of the artifact and leaves `dist/` intact.

For release acceptance, keep the separately uploaded verified manifest and run
`npm run check:live -- verified/site-manifest.json` after deployment. Record the
manifest commit and input hash, local and CI results, and the live result
separately. The live check rejects redirects, invalid UTF-8, forced downloads,
and MIME types other than `text/plain` for llms and `text/markdown` or
`text/plain` for Markdown. A local preview's headers do not establish GitHub
Pages' headers; a hosting MIME failure leaves publication unverified.

For independent AI reading acceptance, give the reviewing agent only the llms URL and
ask them to locate Python installation, the Node API, JSON updates and
compatibility constraints. Record each question, the URLs actually read, the
answer, and the independent technical review against the same manifest. Local reading is useful
for development but does not replace this post-deployment check.

## English and Chinese content

`site-model.mjs` owns stable topic IDs, routes, locale metadata, navigation order,
document groups, authoritative sources and required capabilities. Each public page
type has one component; route wrappers only choose the language and content.
All documentation uses native Starlight locales and Pagefind. Missing translations
are build errors; English fallback cannot satisfy the translation contract.

The model currently contains 32 topics in both languages. This is an inventory,
not a permanent count: source and artifact checks independently discover new,
missing or unregistered content. Chinese documentation is authored in
`../docs/zh-cn/`; `prepare:site` generates ignored Starlight files. Edit links point
to the authored source. Blog posts require a matching `translationKey`, `locale`,
date and category in both language directories.

Short UI messages, including clipboard failures, screen-reader feedback, social
image text and search failures, live in `src/i18n/{en,zh-CN}.json`. Starlight and
Pagefind overrides live in `src/content/i18n/`. Both catalogs enforce identical
keys and interpolation parameters. Shared SDK commands, executable examples,
APKGs and benchmark values remain independent of translated prose.

`locale-model.mjs` separates configured languages from `release-locales.json`.
Only the latter drives the next complete artifact. Configuring a language does
not read or publish incomplete sources. Historic published languages and routes
are protected independently by `check:surface`; CI reads the base revision's
contracts, with pinned independent captures for this first migration.

Source review is per topic and locale in `content-reviews.json` schema 2. Generate
a pending evidence candidate with `scripts/content-review-candidates.mjs`, have
independent AI reviewers read the actual prose, UI, metadata and dependency
snapshots, then import the completed reports with `record-content-review.mjs`.
Technical and linguistic axes require concrete evidence; never refresh hashes to
pretend a review happened. Search and task coverage is a contract before build;
actual results are attached to the artifact afterward. `section-contracts.json`
maps stable tasks explicitly and `legacy-sections.json` retains historic anchors.
Translations may change heading depth, order and table presentation when facts
and task dependencies remain complete. Switching uses a build-validated target
section inventory without fetching every translated page.

`CONTENT_REVIEW_MODE=preview` permits isolated editorial rendering. It cannot
produce a release manifest or authorize deployment. A release uses normal strict
source checks and freezes its locale snapshot before building.

## Search and release evidence

`search-terms.json` contains independently authored, source-backed terms per page
and locale. They are emitted as Pagefind metadata. `generate:search` derives a
small current-language directory from actual built HTML and copies the shared
browser retrieval engine; Pagefind retains the complete body index. The search
dialog loads only its current locale and preserves native keyboard, focus,
loading and recovery behavior. Concept normalization and metadata ranking handle
local expressions; `search-queries.json` is a separate frozen acceptance set,
not a production query routing table or measured search-volume data.

After a strict build, use `npm run verify:release`, followed by
`npm run check:release` immediately before artifact upload. The first command
actually executes source, site, historic surface, machine, schema, fault
injection, browser and search checks. Reports and logs stay under
`../target/website-localization/{root,prefix}`; they bind the manifest, current
inputs and all artifact bytes without changing them. The second command rejects
changed source, resources, manifest or evidence. CI runs this sequence for both
deployment bases and uploads the evidence separately. Passing it establishes
artifact engineering acceptance; production identity and HTTP behavior still
require `check:live` against the independently uploaded manifest after deployment.

Useful checks:

```sh
npm run check:content
npm run check:gates       # controlled failures against the current dist/
npx playwright install chromium
npm run test:browser      # serves the real built files over local HTTP
```

To use a local Chrome installation, set `CHROME_EXECUTABLE` to its executable.
Browser checks cover real Pagefind, clipboard permission denial/recovery,
keyboard actions, media, themes, responsive layouts and JavaScript-disabled
content. Screenshots are written under `../target/website-i18n-62/`.

`npm run check:public-recipe` installs public packages in temporary apps, runs the
shared JSON/media/update recipe and saves evidence in `../target/geo-public-consumers/`.
It requires Node, Rust, Python/venv and network access. CI runs this on Linux x64
separately from source-package checks and gates deployment on success.

## Content and examples

- `src/components/HomePage.astro`: shared homepage, with a card animation, export benchmarks, and an interactive code-to-card workbench.
- `src/components/HomeShowcase.astro` and `src/scripts/showcase.ts`: the four-card stacking and APKG packing sequence. One ten-second loop keeps the layers in sync, doubles packing speed, pauses outside the viewport, and respects reduced motion.
- `src/components/PerformanceEvidence.astro`: export metrics selected by `docs/benchmark-presentation.json`, with links to its methodology and limitations.
- `src/components/AiQuickstart.astro`: language tabs, a local task input, plain-text AI briefs and installation copying, with complete no-script templates.
- `src/components/ExamplesPage.astro`: all examples and package downloads.
- `src/content/blog/`: Markdown or MDX posts, each with `title`, `description`, `date`, `category` (`Tutorial` or `Engineering`), `locale`, `translationKey`, and optional `draft: true`.
- `src/content/docs/docs/`: introductory site docs. Task guides, language guides and references are generated from the repository sources listed in `site-model.mjs`. Edit those source files; each generated page links to its editable source.
- `src/styles/tokens.css`: the shared light/dark palette; `global.css` styles the public pages, `home.css` and `showcase.css` style the homepage, and `docs.css` adapts Starlight.

`scripts/prepare-site.mjs` runs `anki_forge/examples/website_showcase.rs`. The Rust program builds Basic, Cloze, media, Image Occlusion, a combined four-card showcase deck, and two-version update packages. It checks inspected counts and verifies preserved identity in the update report. The preparation script extracts displayed source regions from that same file and records package hashes in `generated/showcase.json`.

The previews share the notes’ fields with the Rust examples. They simplify Anki’s rendering and do not emulate its scheduler or import behavior. The media example’s full source includes its custom note type and synthesized waveform/tone; the displayed snippet concentrates on attaching the media.

Generated content, packages, favicon, and social image are ignored by Git and recreated by the build. Do not edit `src/generated/`, imported documentation files, or `public/generated/` by hand.

Documentation code blocks marked with `<!-- source: ... -->` are compared to their executable source at build time. `npm run sync:docs` updates these blocks after intentional source changes. The documentation workflow also verifies Basic/Cloze counts, custom Cloze bundles, Image Occlusion and both APKG/lockfile update paths. `check:examples` runs complete Rust examples and creates a separate path-dependency consumer. Website CI additionally runs Python documentation programs and Node's installed-package/example checks. See [documentation maintenance](../docs/documentation.md).

Public installation versions are maintained independently of source package metadata. Executable quickstart snippets are shared across READMEs and guides. Benchmark selection is shared with README chart generation; site checks compare rendered values against the CSV.

AI briefs and installation commands come from `../docs/ai-quickstart.json`.
After editing that data, run `npm run sync:ai` and review the marked README
blocks. `check:ai` also checks Skill references and public installation guides;
site preparation regenerates ignored site data without rewriting the READMEs.
See [AI assistant setup](../docs/ai-assistants.md) for loading paths and release prerequisites.

The brand mark is maintained in `../docs/assets/brand/ankiforge.svg`. The header,
documentation title, favicon, social image, and both root READMEs use this design.
The build creates its dark variant in `../docs/assets/brand/ankiforge-dark.svg` and
regenerates the favicon and social image. The front card has an opaque fill to
cover the overlapping rear outline in both themes.

Interface icons come from Phosphor. Its MIT license is included in the generated assets.

## GitHub Pages

The production URL is `https://ankiforge.dev/`; local builds default to the GitHub project prefix for base-path verification. The workflow in `.github/workflows/website.yml` checks pull requests and deploys successful builds from `main`.

Before the first deployment, set the repository’s **Settings → Pages → Build and deployment → Source** to **GitHub Actions**. A pushed workflow or manual workflow run can then publish the static output. The local implementation does not change repository settings automatically.

CI builds and checks both `/anki-forge/` and the production root, including
browser tests and deliberate contract violations. `build` writes
`dist/generated/site-manifest.json` from actual output with the source commit,
input fingerprint, routes, observed capabilities and file hashes. The manifest
is uploaded separately from the Pages artifact. After deployment, `check:live`
requires that verified manifest, checks every normal URL and resource against it,
and independently checks metadata, search, sitemap and genuine unknown URLs.
The deploy job also runs live browser checks. A local pass is not evidence that
production has been updated.

GitHub Pages serves one static `404.html` for all unknown paths. With JavaScript,
that document selects the requested language and recovery links. Without
JavaScript it deliberately displays both languages. This is not server-side
localized error routing; Pages cannot provide that per-path capability here.

The configuration keeps page links, assets, canonical URLs, RSS, the sitemap, and the social image under the same base. `check:site` walks the built HTML to catch missing local targets, broken anchors, duplicate IDs, incorrect metadata, and mismatched deck downloads.

## Custom domain

Production uses these repository **Actions variables** (and matching workflow defaults):

| Variable | Example value |
| --- | --- |
| `SITE_URL` | `https://ankiforge.dev` |
| `SITE_BASE` | `/` |
| `SITE_CUSTOM_DOMAIN` | `ankiforge.dev` |

`SITE_URL` is an origin without a path. `SITE_BASE` is the deployment path. `SITE_CUSTOM_DOMAIN` must match the hostname and generates `CNAME`. Configure the same custom domain and DNS records in GitHub Pages, then rebuild and deploy. `SITE_DEPLOYMENT=production` rejects another origin, a non-root base or a missing CNAME; local/preview builds retain flexible configuration.

For a local domain-configuration check, copy `.env.example` to `.env`, fill in these values, and run `npm run build` followed by `npm run check:site`. Shell environment variables take precedence over `.env`. Restart the development server after changing the configuration.

The site produces canonical URLs, Open Graph metadata, a sitemap, and an RSS feed. `robots.txt` is effective when served from the domain root; on the default repository path, the host’s root robots file remains authoritative. Submit the generated sitemap to the search engines after the public domain is ready.

The same `dist/` directory can be hosted on Cloudflare Pages or another static host. Build the project from the repository root with access to both Rust and Node; use `SITE_BASE=/` for root hosting.
