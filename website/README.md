# Anki Forge website

The public homepage, examples, blog, and documentation. Built as a static Astro site with Starlight, Markdown/MDX, native CSS, and a small TypeScript script for the card demos. No application server is required.

## Develop locally

Use Node 24 or later and Rust 1.92 or later. From the repository root:

```sh
cd website
nvm use
npm ci
npm run dev
```

Open `http://127.0.0.1:4321/anki-forge/`. If you do not use nvm, select Node 24 with your preferred version manager before running npm.

The predev and prebuild commands compile and execute the Rust showcase. A first build needs network access for Cargo and npm dependencies. Later builds reuse the Cargo cache.

```sh
npm test
npm run check:docs
npm run check:examples
npm run check
npm run build
npm run check:site
npm run preview
```

Production preview runs at `http://127.0.0.1:4321/anki-forge/` by default. Starlight’s Pagefind search index is generated by the production build, so test search with `preview`.

Astro runs the preview server in the background. Use `npm run preview:stop` when finished.

## Content and examples

- `src/pages/index.astro`: homepage, with an interactive code-to-card workbench.
- `src/pages/examples/index.astro`: all examples and package downloads.
- `src/content/blog/`: Markdown or MDX posts, each with `title`, `description`, `date`, `category` (`Tutorial` or `Engineering`), and optional `draft: true`.
- `src/content/docs/docs/`: introductory site docs. Task guides, language guides and references are generated from the repository sources listed in `scripts/content-links.mjs`. Edit those source files; each generated page links to its editable source.
- `src/styles/tokens.css`: the shared light/dark palette; `global.css` styles the public pages and `docs.css` adapts Starlight.

`scripts/prepare-site.mjs` runs `anki_forge/examples/website_showcase.rs`. The Rust program builds Basic, Cloze, media, and two-version update packages, checks the inspected counts, and verifies preserved identity in the update report. The preparation script extracts displayed source regions from that same file and records package hashes in `generated/showcase.json`.

The previews share the notes’ fields with the Rust examples. They simplify Anki’s rendering and do not emulate its scheduler or import behavior. The media example’s full source includes its custom note type and synthesized waveform/tone; the displayed snippet concentrates on attaching the media.

Generated content, packages, favicon, and social image are ignored by Git and recreated by the build. Do not edit `src/generated/`, imported documentation files, or `public/generated/` by hand.

Documentation code blocks marked with `<!-- source: ... -->` are compared to their executable source at build time. `npm run sync:docs` updates these blocks after intentional source changes. The documentation workflow also verifies Basic/Cloze counts, custom Cloze bundles, Image Occlusion and both APKG/lockfile update paths. `check:examples` runs complete Rust examples and creates a separate path-dependency consumer. Website CI additionally runs Python documentation programs and Node's installed-package/example checks. See [documentation maintenance](../docs/documentation.md).

Source SDK versions on the language page are generated from package metadata. Version statements in the compatibility table and root READMEs are checked against those values; release status remains a separately maintained claim.

Icons come from Phosphor. Its MIT license is included in the generated assets.

## GitHub Pages

The default public URL is `https://morehardy.github.io/anki-forge/`. The workflow in `.github/workflows/website.yml` checks pull requests and deploys successful builds from `main`.

Before the first deployment, set the repository’s **Settings → Pages → Build and deployment → Source** to **GitHub Actions**. A pushed workflow or manual workflow run can then publish the static output. The local implementation does not change repository settings automatically.

The configuration keeps page links, assets, canonical URLs, RSS, the sitemap, and the social image under the same base. `check:site` walks the built HTML to catch missing local targets, broken anchors, duplicate IDs, incorrect metadata, and mismatched deck downloads.

## Custom domain

After purchasing and configuring a domain, set these repository **Actions variables** together:

| Variable | Example value |
| --- | --- |
| `SITE_URL` | `https://your-domain.example` |
| `SITE_BASE` | `/` |
| `SITE_CUSTOM_DOMAIN` | `your-domain.example` |

`SITE_URL` is an origin without a path. `SITE_BASE` is the deployment path. `SITE_CUSTOM_DOMAIN` must match the hostname and generates `CNAME`. Configure the same custom domain and DNS records in GitHub Pages, then rebuild and deploy. The placeholder above is not a registered project domain.

For a local domain-configuration check, copy `.env.example` to `.env`, fill in these values, and run `npm run build` followed by `npm run check:site`. Shell environment variables take precedence over `.env`. Restart the development server after changing the configuration.

The site produces canonical URLs, Open Graph metadata, a sitemap, and an RSS feed. `robots.txt` is effective when served from the domain root; on the default repository path, the host’s root robots file remains authoritative. Submit the generated sitemap to the search engines after the public domain is ready.

The same `dist/` directory can be hosted on Cloudflare Pages or another static host. Build the project from the repository root with access to both Rust and Node; use `SITE_BASE=/` for root hosting.

References: [Astro’s GitHub Pages guide](https://docs.astro.build/en/guides/deploy/github/), [Starlight configuration](https://starlight.astro.build/reference/configuration/).
